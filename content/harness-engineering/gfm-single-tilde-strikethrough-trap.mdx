## 증상

위키 시작 가이드 표의 한 셀에 이렇게 썼다.

```markdown
| 주 시리즈 | Harness Journal (000~039) + iOS Journal (000~029) |
```

빌드는 통과했고 MDX 검증 스크립트도 경고가 없었다. 그런데 배포된 페이지에서는 `039) + iOS Journal (000` 부분에 **취소선**이 그어져 있었다. 실제 HTML은 이렇게 나왔다.

```html
Harness Journal (000<del>039) + iOS Journal (000</del>029)
```

## 원인

GitHub Flavored Markdown의 취소선 확장은 물결표 **두 개**(`~~x~~`)가 표준이다. 하지만 `remark-gfm`(내부적으로는 `micromark-extension-gfm-strikethrough`)은 **물결표 하나짜리도 취소선으로 받는 것이 기본값**이다. 옵션 이름은 `singleTilde` 이고 기본값은 `true` 다.

한국어 기술 글은 범위를 물결표로 쓰는 경우가 많아서(`1~3단계`, `30~50분`) 이 기본값과 정면으로 부딪힌다.

## 어떤 경우에 깨지나 — 실측

`remark-parse` + `remark-gfm` + `remark-rehype` 로 직접 렌더해서 확인했다.

| 입력 | 기본값 (`singleTilde: true`) | `singleTilde: false` |
|---|---|---|
| `(000~039) + (000~029)` 같은 줄 | **깨짐** | 정상 |
| `1~3, 5~7` | **깨짐** | 정상 |
| 줄바꿈을 사이에 둔 같은 문단의 `1~3` 과 `5~7` | **깨짐** | 정상 |
| 표 한 셀 안에 두 개 | **깨짐** | 정상 |
| 물결표 하나뿐인 `3~5분` | 정상 | 정상 |
| 표의 서로 다른 셀에 하나씩 | 정상 | 정상 |
| 인라인 코드 안 | 정상 | 정상 |
| `~/a 와 ~/b` (뒤가 문장부호) | 정상 | 정상 |
| `~~정식 취소선~~` | 취소선 | 취소선 |

핵심은 **"한 줄에 두 개"가 아니라 "한 인라인 영역(문단·셀)에 짝이 맞는 두 개"** 라는 점이다. 줄을 바꿔도 같은 문단이면 깨진다.

## 왜 오래 숨어 있었나

```mermaid
flowchart LR
    A["물결표 범위 표기"] --> B["MDX 컴파일 성공"]
    B --> C["검증 스크립트 통과"]
    C --> D["빌드·배포 성공"]
    D --> E["화면에서만 취소선"]
```

컴파일 에러가 아니라 *문법적으로 유효한 다른 의미*로 해석되기 때문에 파이프라인의 어떤 단계도 실패하지 않는다. 사람이 그 문단을 눈으로 읽을 때만 드러난다. [shell-pipe-exit-code-trap](/wiki/harness-engineering/shell-pipe-exit-code-trap)이나 [fixture-silent-failure-trap](/wiki/harness-engineering/fixture-silent-failure-trap)과 같은 계열의 조용한 실패다.

처음에는 문제가 된 한 글만 en dash(`–`)로 고쳤다. 그 뒤 같은 패턴을 위키 전체에서 찾아봤다. 313개 글을 파싱해서 물결표 하나로 시작하는 `delete` 노드를 세어 보니 **20개 글, 23곳**이 이미 프로덕션에서 깨져 있었다. 이 중 3개 페이지는 실제 배포 HTML에서도 `<del>` 개수가 똑같이 확인됐다. 하나를 고쳤다고 끝난 게 아니었다.

## 해결 — 원인 레벨에서 끄고 테스트로 잠근다

### 1. 렌더러 옵션

렌더러 설정을 한 파일로 분리하고 옵션을 껐다.

```ts
// src/lib/remark-plugins.ts
import remarkGfm from "remark-gfm";
import type { PluggableList } from "unified";

export const remarkPlugins: PluggableList = [[remarkGfm, { singleTilde: false }]];
```

```tsx
// src/app/wiki/[...slug]/page.tsx
mdxOptions: {
  remarkPlugins,
  rehypePlugins: [/* ... */],
},
```

정식 취소선 `~~x~~` 은 계속 동작한다. 위키에서 의도적으로 취소선을 쓴 3곳은 옵션을 바꾼 뒤에도 그대로 렌더되는 걸 확인했다.

### 2. 회귀 테스트

옵션이 나중에 누군가의 리팩터링으로 빠지면 다시 조용히 깨진다. 그래서 같은 `remarkPlugins` 를 import해서 렌더 결과를 검사하는 테스트를 붙였다.

```ts
it("같은 줄의 범위 표기 두 개가 취소선이 되지 않는다", () => {
  expect(render("Harness (000~039) + iOS (000~029)")).not.toContain("<del>");
});
it("정식 취소선 ~~x~~ 은 유지된다", () => {
  expect(render("~~폐기된 안~~")).toContain("<del>폐기된 안</del>");
});
```

테스트가 실제로 잠그고 있는지도 확인했다. 옵션을 `true` 로 되돌리면 3개 중 2개가 실패하고, `false` 면 전부 통과한다.

### 3. 옵션을 바꿀 수 없는 환경이라면

GitHub 웹, 노션 등 렌더러 설정을 바꿀 수 없는 곳에서는 콘텐츠 쪽에서 피해야 한다.

- 범위는 en dash `–` 나 하이픈으로 쓴다. 예: `000–039`
- 경로·명령의 물결표는 인라인 코드로 감싼다.
- 문서 전체를 감사하려면 마크다운 AST에서 `delete` 노드를 찾고, 원문이 `~~` 로 시작하지 않는 것만 걸러낸다. 정규식보다 정확하다. 정규식은 문단·셀 경계를 모른다.

## 체크리스트

- [ ] remark-gfm을 쓰는 렌더러라면 `singleTilde` 기본값이 `true` 임을 안다.
- [ ] 한국어 콘텐츠 렌더러는 `singleTilde: false` 로 설정하고 회귀 테스트를 붙인다.
- [ ] 렌더링 버그는 한 건 고친 뒤 반드시 **전체 콘텐츠를 AST로 감사**한다. 같은 패턴이 이미 다른 곳에 있다.
- [ ] 배포 확인은 실제 HTML에서 깨진 요소(`<del>`) 개수를 세는 것으로 한다.
