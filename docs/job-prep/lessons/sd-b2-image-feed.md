```
✅ 무한 스크롤 · 좋아요 · 댓글 보기(읽기전용) · 이미지 표시
❌ 업로드 · DM · 스토리 · 검색  ← "이번 범위 밖으로 두겠습니다"
```

## ③ 비기능
오프라인(이전 피드 열람 + 좋아요 큐) · 스크롤 60fps · 메모리 예산 내 · 배터리/데이터(프리페치 제한, WiFi 적응)

## ④ 규모추정 (B1 소리내기)
```
아이템 = 메타 2KB + 이미지 300KB (이미지가 200배)
페이지 20개 = 메타 40KB + 이미지 6MB
디코딩 비트맵 4.5MB/장 → 200장 = 900MB = 앱 사망
→ 이 숫자가 아래 모든 결정의 근거
```

## ⑤ 로컬 스키마
```
FeedItem: itemId(PK) · authorId · text · likeCount · commentCount
          · isLikedByMe · imageURL · createdAt
          · cursorNext        (페이지네이션 위치)
          · pendingLike(Bool) ⭐ 오프라인 대기 표시 = 로컬 전용 필드
```

## ⑥ API 계약
```
GET  /feed?cursor=<opaque>&limit=20  → { items, nextCursor }
POST /posts/{id}/like   Header: Idempotency-Key: <uuid> ⭐ 재시도 안전
```
**왜 cursor(offset 아님):** offset=40인데 새 글 3개 추가되면 위치가 밀려 **중복/누락(page drift)**. cursor는 "이 아이템 다음부터"라 절대 기준 → drift 없음.

## ⑦ 하이레벨 (BFS)
```
View(@MainActor) ↕ ViewState
ViewModel (Task 수명 소유)              ← arch-a2
   │ async
```

## ⑧ Deep Dive 3

### 🅰 이미지 파이프라인
```
① 메모리 히트 → 즉시  ② 디스크 히트 → 디코딩(다운샘플링) → 메모리
③ 네트워크 → 디스크(압축) → 디코딩 → 메모리
포인트: 표시크기 다운샘플링(100배절감) · 디코딩은 백그라운드(메인=프레임드랍)
       · 셀 재사용 시 Task 취소 + URL 일치 검증 · 메모리 cost 상한 / 디스크 LRU
```

### 🅱 오프라인 좋아요
```
탭 → ① UI 즉시(optimistic) → ② 로컬DB pendingLike=true
   → ③ SyncQueue 적재(Idempotency-Key) → ④ 복구 시 배치 전송
   → ⑤ 실패 시 지수백오프, 최종 실패면 롤백 + 알림
충돌: 좋아요=저가치 → LWW 충분. (CRDT/OT는 오프라인 멀티디바이스 편집처럼
      자동 수렴이 필요할 때 — 여기선 과잉)  ← 도구 구분 = 성숙도 신호
```

### 🅲 스크롤 60fps
프리페치는 끝 3~5개 남을 때 · 화면 밖 이미지 방출 · 메타/이미지 분리 렌더(체감↑) · 무거운 작업 백그라운드, UI만 메인

## ⑨ 트레이드오프 (소리내야 점수)
```
프리페치 공격성 ↔ 배터리/데이터 (WiFi 적응)
캐시 신선도    ↔ 대역폭
optimistic    ↔ 일시적 부정확(롤백 UX)
무한스크롤 메모리↔ UX (상한 500 + 오래된 것 방출)
로컬DB SSOT   ↔ 구현 복잡도 (오프라인 분기 제거로 상쇄)
```
**one-way vs two-way door:** *"캐시 정책·프리페치 수치는 나중에 조정 가능(two-way)이지만, Repository를 SSOT로 두느냐는 구조 결정이라 되돌리기 비싸(one-way) 초반에 신중히 정합니다."*

## 💪 압박 방어 — "View가 API 응답 직접 받으면 간단한데 왜 로컬DB SSOT?"
```
① 코드 경로 통일 ⭐  View는 로컬DB만 관찰 → 데이터 출처(API/캐시)를 몰라도 됨
                    → 온라인/오프라인 분기(if isOnline)가 코드에서 사라짐
                    → "간단하다"의 반전: 오히려 View가 단순해진다
② 오프라인        앱 재시작·비행기모드에도 이전 피드 열람 + optimistic 좋아요 보존
③ 부분 실패 내성   4페이지 실패해도 1~3페이지는 그대로 보이고 실패분만 재시도
                    (API 직접이면 화면 날아가거나 빈 상태)
```
**모범답안:** "오히려 View가 더 단순해집니다. View는 로컬 DB만 관찰하고 그 데이터가 네트워크에서 왔는지 캐시인지 알 필요가 없습니다. 그래서 온라인/오프라인 분기가 코드에서 사라집니다 — API 직접 방식이면 화면마다 '네트워크 있나?' 분기가 퍼집니다. 그리고 부분 실패에 강합니다. 4페이지 로딩이 실패해도 저장된 1~3페이지는 그대로 보이고 실패한 부분만 재시도합니다. 대가는 구현 복잡도와 마이그레이션 관리인데 오프라인 분기를 없애는 것으로 상쇄된다고 봅니다. **다만 읽기 전용이고 오프라인이 불필요한 화면이면 과잉이라 API 직접도 씁니다.**"
> 🗝️ 마지막 문장 = 시니어 결정타(무조건 SSOT가 아니라 **언제 과잉인지도 안다**). ARCH-SD 레드플래그 "패턴을 종교처럼 옹호" 회피.
