# L0 — 분산 시스템 전제: exactly-once는 불가능하다

```
   메시지 전달 보장의 3등급
   ─────────────────────────────────────────────
   at-most-once   재시도 없음 → 유실 가능 (결제 요청 자체가 사라짐)
   at-least-once  재시도 있음 → 중복 가능 (이중결제)
   exactly-once   ⛔ 네트워크에서 원천적으로 불가능

   왜 불가능한가: 요청을 보냈는데 응답이 없을 때
                 "도착했는데 응답만 유실"과 "도착 자체가 실패"를 구별할 방법이 없다

   ✅ 현실의 해법:  at-least-once 전달  +  멱등 처리  =  "효과적 exactly-once"
                   (재시도는 마음껏, 대신 서버가 중복을 흡수)
```
> 🗝️ **이 문단을 말할 수 있으면 결제 질문은 이미 절반 이긴다.** 대부분은 "재시도하면 되죠"에서 멈춘다.

## 멱등키의 정확한 계약

```
Idempotency-Key: <클라가 만든 UUID>

서버 계약 3조:
① 같은 키로 재요청 → 첫 처리 결과를 그대로 반환 (재실행 X)
② 같은 키 + 다른 페이로드 → 에러 (키 재사용 오염 방지) ⭐ 이걸 아는 사람이 적다
③ 키 유효기간 존재 (예 24h). 만료 후 같은 키는 새 요청으로 취급

클라 규칙 3조:
① 키는 "결제 시도 1건"에 귀속 → 로컬DB에 저장 ⭐
② 재시도할 때 **저장된 같은 키**를 재사용
③ 유저가 명시적으로 "다시 결제"를 누르면 **새 키** (다른 의도이므로)

⛔ 실무 최다 버그: 재시도 루프에서 UUID를 새로 만든다 → 멱등성 완전 무효화
   증상: 네트워크 불안정 지역에서만 이중결제 → 재현 어려움 → 장기 미해결 버그
```

## 서버 측 멱등성의 실체 (물어보면 답할 수 있어야)

```
   애플리케이션 로직만으로 막으면 경합에서 뚫린다
   (동시에 같은 키 2건 도착 → 둘 다 "없음" 조회 → 둘 다 처리)

   ✅ DB 유니크 제약이 최종 방어선
      idempotency_key 컬럼에 UNIQUE INDEX
      → 두 번째 삽입이 제약 위반으로 실패 → 그 트랜잭션은 첫 결과를 조회해 반환
   ✅ 처리 중 상태도 기록 (in_flight) → 동시 요청은 대기 or 409
```

# L1 — 상태머신 (그리면 시니어)

```
   draft ──► held ────────► paying ────────► paid ──► active ──► completed
             (차량 점유)       │                │                      │
             │ TTL 만료        │ 실패            │                      │ 정산
             ▼                ▼                │                      ▼
          expired         payFailed             │                  settled
             │                │                 │                      │
             └── 보상: hold 해제 ◄──────────────┘                 부분취소/추가결제
                                                                  (L4)
   cancelled ──► refunded          ambiguous ──(조회)──► paid | payFailed
                                   ⭐ "모르는 상태"를 명시적 상태로 둔다
```

## ⭐ 설계 포인트 4개

```
① held + TTL 없으면 재고 사망
   결제 화면에서 이탈한 유저가 차량을 영구 점유 → 다른 유저가 못 잡음
   TTL(예 10분) + 서버 만료 잡. TTL 값은 ⭐ 서버 설정값 (앱 배포는 비가역)

② paying = "우리도 모르는 구간"을 상태로 인정
   이 상태가 없으면 코드가 "성공 아니면 실패"로만 분기 → 모르는 경우를 처리할 곳이 없다
   ⭐ 모르는 상태를 상태머신에 넣는 것 자체가 설계 성숙도

③ 상태는 반드시 디스크에 (메모리 X)
   iOS는 OS가 언제든 앱을 죽인다 → 결제 직전에 로컬DB 기록이 선행돼야 복구 가능

④ 상태 전이는 서버가 유일한 권위
   클라가 "paid로 바꿔줘"를 보내지 않는다. 클라는 조회만.
```

# L2 — 이중결제 4중 방어 (층별로 왜 필요한지)

```
1층  클라 UI 락        버튼 즉시 비활성 + 중복 진입 차단
     역할: 실수 탭 방어.  한계: 앱 재시작·프로세스 킬에 무력 → ⛔ 이것만 믿으면 사고

2층  Idempotency-Key   재시도 = 같은 키 → 서버가 첫 결과 반환
     역할: 네트워크 재시도 방어 (가장 중요) ⭐

3층  서버 상태머신      paying/paid 상태에서 새 결제 요청 거부
     역할: 다른 기기·다른 세션에서의 중복 시도 방어 (키가 달라도 막힌다)

4층  reconcile         앱 시작/포그라운드마다 미확정 결제 정리
     역할: 앱이 죽어서 재시도조차 못 한 경우 ⭐ 감별점 — 여기까지 가는 사람이 드물다
```

> 🗝️ **층을 나눠 말하는 게 핵심:** *"각 층이 막는 실패 모드가 다릅니다. UI 락은 실수 탭을, 멱등키는 네트워크 재시도를, 상태머신은 다른 세션을, reconcile은 앱 종료를 막습니다. 그래서 하나를 다른 것으로 대체할 수 없습니다."*

## reconcile 루틴 상세 (외워둘 가치 있음)

```
결제 시작 "직전"에 로컬DB 기록:
   { reservationId, idempotencyKey, state: .attempting, startedAt }
   ⭐ 순서가 중요하다 — 요청을 보낸 뒤 기록하면 그 사이에 죽으면 흔적이 없다

앱 시작 / 포그라운드 진입 시:
   ① 로컬에 .attempting 인 건이 있나?
   ② 있으면 서버에 조회 (GET, 절대 POST 아님)
   ③ 서버 응답에 따라:
        paid     → 로컬 정리 + "결제가 완료되었습니다" + 예약 화면
        failed   → 로컬 정리 + 재시도 안내 (새 키 발급)
        paying   → 폴링 계속 + "확인 중" UI (백오프, 상한 있음)
        없음/만료 → 로컬 정리 + 처음부터
   ④ ⛔ 절대 임의로 재결제하지 않는다 (조회로만 확정)
   ⑤ 상한 초과 시 운영 알림 + 고객센터 경로 노출
```

# L3 — 실패 분류 (재시도 가능 여부가 전부)

```
🟢 재시도 가능 (retryable)      네트워크 타임아웃 · 5xx · PG 일시 오류 · rate limit
   → 지수백오프 + jitter로 자동 재시도 (같은 멱등키)

🔴 재시도 무의미 (terminal)      카드 한도 초과 · 유효기간 만료 · 카드 거절 · 인증 실패
   → 즉시 유저에게 사유 표시 + 다른 수단 유도. 자동 재시도 ⛔ (거절만 반복)

🟡 모호 (ambiguous) ⭐          요청은 보냈는데 응답이 없음 / 타임아웃 후 상태 불명
   → 재시도 ❌  조회 ✅
   → 이 분류가 없으면 "타임아웃이니 재시도"로 처리해서 이중결제가 난다
```
> 🗝️ **면접 결정타:** *"저는 실패를 세 가지로 나눕니다. 재시도 가능, 재시도 무의미, 그리고 **모호**입니다. 모호를 재시도 가능과 같이 취급하는 게 이중결제의 가장 흔한 원인입니다. 모호에서는 재시도가 아니라 **조회**를 해야 합니다."*

## 에러 코드 계약은 서버와 미리 합의
```
❌ 에러 메시지 문자열로 분기 (문구 바꾸면 앱이 깨진다)
✅ 안정적인 에러 코드 + retryable 플래그를 서버가 명시해서 내려준다
   { code: "PG_TIMEOUT", retryable: true, userMessage: "...", supportCode: "..." }
   → 새 실패 유형이 생겨도 앱 배포 없이 대응 (앱 배포는 비가역)
```

# L4 — 2단 결제: 승인(hold) → 매입(capture) ⭐ 카셰어링 도메인 핵심

```
   일반 이커머스:  주문 = 확정 금액 → 한 번에 결제
   카셰어링:      예약 시점에 최종 금액을 모른다 ⚠️
                 (실제 주행거리·연장·연료·페널티가 반납 후에 확정)

   ✅ 2단 구조
   ┌──────────────┐         ┌──────────────────┐
   │ 예약 시       │         │ 반납 후            │
   │ authorize    │  ────►  │ capture           │
   │ (예상금액 hold)│         │ (실사용금액 매입)   │
   └──────────────┘         └──────────────────┘

   실사용 < 예상  → 부분 매입 (차액은 hold 해제)
   실사용 > 예상  → 매입 + 추가 결제 (또는 미납으로 이월) ⭐
   미사용/취소    → hold 전액 해제
```

**여기서 나오는 난제 3개:**
```
① hold 유효기간 vs 대여 기간
   카드사 hold는 유효기간이 있다(수일~). 장기 대여가 이걸 넘으면 hold가 풀린다
   → 장기 예약은 중간 재승인 또는 분할 청구 전략 필요 (측정필요: 우리 PG 정책 확인)

② 추가 결제 실패 → 미납(unpaid) ⭐
   이미 차는 썼고 반납도 했는데 카드가 거절되면?
   → 강제로 못 받는다. 미납 채권으로 전환 + 다음 예약 차단 게이트 (L6)

③ 부분 취소/환불의 멱등성
   환불도 결제와 똑같이 멱등키가 필요하다 (이중환불 = 손실)
   → 환불 요청도 refundKey로 멱등 처리
```

# L5 — 웹뷰 결제 아키텍처 (⭐ 내 실무의 실제 구조)

> 국내 앱에서 매우 흔한 구조: **결제 UI/플로우는 웹, 네이티브는 브릿지와 디바이스 기능만.**

## 왜 웹뷰인가 (방어 논리)

```
✅ PG·간편결제 파편화를 웹 1벌로 흡수
   카드/계좌/간편결제 N종 × iOS/Android = 조합 폭발 → 웹이면 1벌
✅ 결제 정책·약관·화면이 자주 바뀐다 → 앱 배포는 비가역, 웹은 즉시 배포 ⭐
✅ 규제·약관 문구 변경에 즉시 대응
✅ PCI 범위 축소 (카드 정보가 네이티브 코드를 통과하지 않게)
```

## 대가 (이걸 말해야 균형 잡힌 답변)

```
⚠️ 앱 생명주기와 웹 상태의 불일치
   웹은 "페이지"인데 앱은 "프로세스" → 백그라운딩·메모리 경고·프로세스 킬에 웹 상태가 날아감
⚠️ 콜백 유실
   결제 완료 콜백을 웹→네이티브로 넘기는 순간에 앱이 죽으면 결과를 모른다
⚠️ 외부 앱 왕복 ⭐ 가장 까다로운 부분
   웹 → 간편결제/카드사 앱(스킴 전환) → 우리 앱 복귀
   이 왕복에서 웹뷰 세션·리다이렉트 체인이 끊기기 쉽다
⚠️ 세션/토큰 브릿지
   네이티브 로그인 세션을 웹으로 안전하게 넘겨야 함 (URL 쿼리에 토큰 ⛔)
⚠️ 디버깅 난도
   실패 지점이 앱·웹·PG·카드사 4곳으로 분산 → 관측 설계가 없으면 원인 규명 불가
```

## 네이티브가 반드시 책임져야 하는 5가지

```
① 세션 브릿지        토큰을 안전한 경로로 주입 (쿼리스트링 ⛔ → 헤더/포스트/쿠키 등)
② 디바이스 기능 제공  카드 OCR 스캔·생체인증·카메라 — 웹이 못 하는 것만 ⭐
③ 외부 앱 전환 처리   결제 앱 스킴/유니버설 링크 허용 목록 + 복귀 딥링크 처리
④ 복귀 시 reconcile  포그라운드 진입 → ⭐ 서버에 상태 재조회 (웹 콜백을 진실로 삼지 않음)
⑤ 실패 관측          단계별 이벤트 로깅 (웹 진입·외부앱 전환·복귀·콜백 수신·서버 확정)
```

> 🗝️ **가장 중요한 원칙:** *"웹뷰 콜백은 **빠른 경로**로만 쓰고 **진실로는 쓰지 않습니다.** 진실은 항상 서버 조회입니다. 왜냐하면 콜백은 유실될 수 있고, 유실됐을 때 앱은 그 사실조차 알 수 없기 때문입니다."*

## 3중 확인 경로

```
   ① 웹뷰 콜백    가장 빠름. 성공 시 즉시 UI 전환 (단, 확정으로 취급 X)
   ② 서버 webhook  PG → 우리 서버. 가장 신뢰 (앱과 무관하게 도착)
   ③ 클라 폴링     ①이 안 오고 ②의 결과를 앱이 모를 때의 안전망 (백오프 + 상한)

   → 세 경로가 같은 상태머신을 향해 수렴한다. 어느 경로로 알게 됐든 결과는 하나.
```

# L6 — 후불 정산과 미납 게이트 (카셰어링 특유)

```
   카셰어링은 "쓰고 나서 정산"이 섞인다 → 미납이 구조적으로 발생한다

   반납 → 실사용 금액 확정 → capture 시도
                              ├ 성공 → settled
                              └ 실패 → 🔴 미납(unpaid) 채권 발생

   미납이 있는 유저:
     ⛔ 새 예약 차단 (또는 제한)
     ✅ 진입 시점에 "미납 결제" 플로우로 유도
     ✅ 미납 금액·발생 사유를 명확히 표시 (분쟁 예방)
```

## ⭐ 순차 자격 검증 게이트 패턴

```
   예약 시작 전에 통과해야 하는 게이트들이 순서대로 있다

   로그인 ─► 본인인증 ─► 면허 등록/유효 ─► 결제수단 등록 ─► 미납 없음 ─► 예약 가능
      │         │            │              │              │
      └─ 각 게이트는 "막는 이유 + 해결 경로"를 함께 제시해야 한다

   ⛔ 안티패턴: 예약 마지막 단계에서 한꺼번에 검증 → 유저가 다 입력하고 튕김
   ✅ 진입 시점에 순차 검증 + 실패한 게이트로 바로 이동
   ✅ 게이트 정의는 서버에서 (규정 변경에 앱 배포 불필요)
```
> 🗝️ 이 패턴은 결제뿐 아니라 **모빌리티 앱 전반의 구조**다. 면접에서 "예약 플로우 설계"를 물으면 이 게이트 사다리를 먼저 그리면 도메인 이해가 즉시 전달된다.

# 💪 압박 방어 6종

### ① "재시도하면 그만이잖아요, 뭐가 어렵죠?"
> *"재시도 자체는 쉽습니다. 어려운 건 **재시도해도 안전한가**입니다. 왜냐하면 첫 요청이 서버에 도착했는지 앱은 알 수 없기 때문입니다. 응답만 유실됐을 수도 있습니다. 그래서 멱등키를 클라가 만들어 재시도마다 같은 키를 보내고, 서버는 같은 키에 첫 결과를 그대로 반환합니다. 그리고 타임아웃은 재시도가 아니라 **조회**로 처리합니다."*

### ② "멱등키만 있으면 이중결제는 끝나는 거 아닌가요?"
> *"멱등키는 **재시도 경로**만 막습니다. 다른 기기나 다른 세션에서 새 키로 요청하면 통과합니다. 그래서 서버 상태머신에서 이미 paying이나 paid인 예약의 새 결제 요청을 거부해야 합니다. 그리고 서버 쪽 멱등성도 애플리케이션 로직만으로는 경합에서 뚫리기 때문에 **멱등키에 DB 유니크 제약**을 걸어야 최종 방어가 됩니다."*

### ③ "결제를 웹뷰로 하는 건 좀 구식 아닌가요?"
> *"트레이드오프가 명확한 선택입니다. 얻는 건 두 가지입니다. 결제수단이 N종이고 플랫폼이 둘인데 조합을 웹 1벌로 흡수합니다. 그리고 결제 정책과 약관이 자주 바뀌는데 **앱 배포는 비가역**이라 구버전 유저가 영구히 남습니다. 웹은 즉시 배포됩니다.
> 대가는 앱 생명주기와 웹 상태의 불일치, 콜백 유실, 외부 결제 앱 왕복입니다. 그래서 저는 **웹 콜백을 진실로 쓰지 않고** 앱 복귀 시 항상 서버에 상태를 되묻는 구조로 방어합니다. 만약 결제수단이 한두 개로 고정되고 정책이 안정적이라면 네이티브가 UX상 더 낫다고 봅니다."*
> 🗝️ 마지막 문장 = "언제는 반대 선택을 한다"까지 말하는 시니어 신호 (`sd-b2` SSOT 방어와 같은 마무리).

### ④ "간편결제 앱으로 넘어갔다가 안 돌아오면요?"
> *"돌아오지 않는 경우를 정상 시나리오로 취급합니다. 외부 앱으로 전환하는 순간 우리 앱은 백그라운드로 가고, 그 사이에 프로세스가 죽을 수도 있습니다. 그래서 전환 **직전에** 시도 정보를 로컬DB에 기록합니다. 그리고 앱이 어떤 경로로 다시 켜지든 포그라운드 진입 시 미확정 결제를 조회해서 정리합니다. 복귀 딥링크는 빠른 경로일 뿐이고, 그것에 의존하지 않는 게 핵심입니다."*

### ⑤ "결제 화면에 optimistic UI를 쓰면 체감이 빠를 텐데요?"
> *"저는 결제와 차량 제어에는 optimistic을 쓰지 않습니다. 왜냐하면 실패의 비대칭이 크기 때문입니다. 좋아요는 롤백하면 되지만, '결제 완료'를 먼저 보여주고 실패하면 유저는 이미 차로 걸어가고 있습니다. 대신 체감 속도는 **진행 상태를 구체적으로 보여주는 것**으로 확보합니다. 무한 스피너 대신 '카드사 확인 중'처럼 단계와 예상 시간을 보여줍니다."*

### ⑥ "이미 차를 다 쓴 뒤에 카드가 거절되면 어떻게 하시겠습니까?"
> *"기술로 못 막는 지점입니다. 이미 제공된 서비스라 되돌릴 수 없습니다. 그래서 이건 **미납 채권으로 전환**하고 다음 예약 진입을 차단하는 정책 문제로 넘깁니다. 앱이 할 일은 세 가지입니다. 미납 금액과 발생 사유를 분쟁 없게 명확히 보여주고, 미납 결제 경로를 진입 시점에 노출하고, 그리고 애초에 이 확률을 줄이기 위해 **예약 시점에 예상 금액으로 승인(hold)을 잡아두는 것**입니다. 승인이 잡히지 않는 카드면 예약 자체를 막는 게 사후 미납보다 낫습니다."*

# 🔬 실무 코드 대조 (2026-08-03)

> **출처:** 사내 카셰어링 iOS 앱 + 사내 웹 프론트 레포 직접 확인. **익명화 규약 적용**(식별자·경로·프로토콜 상세 제외).

## ⭐ 발견 1 — 결제는 네이티브에 없다. 웹뷰 + 브릿지 구조다

```
재확인:  git grep -nIiE "idempoten" -- '*.swift'          → 0건
        git grep -nIiE "pay|payment" -- '<브릿지·웹뷰 모듈>' → 다수
```
**사실:**
```
· 네이티브 "거래" 모듈은 **이용내역 조회 전용**이다 (결제 실행 코드 없음)
· 결제수단 등록은 웹 URL로 이동시킨다
· 네이티브는 **카드 OCR 스캔**을 웹에 제공한다 ⭐ = "웹이 못 하는 것만 네이티브"의 교과서적 예
· 멱등키 문자열이 iOS 코드에 0건 → 멱등성은 웹/서버 책임 계층에 있다
  (⚠️ 가설: 웹·서버에 있는지는 **미확인**. 면접에서 단정 금지 — "네이티브에는 없었고,
   웹/서버 계층 책임이었습니다. 그쪽 구현은 제가 확인해봐야 합니다.")
```
> 🗝️ **면접 활용:** L5 웹뷰 결제 섹션은 **내가 실제로 겪은 구조**다. 남들은 이 구조를 책으로만 알고, 나는 카드 스캔 브릿지·외부앱 왕복·복귀 처리를 실제로 다뤘다. → **③번 압박 방어가 내 최강 답변**이 된다.

## ⭐ 발견 2 — 순차 자격 게이트가 실제로 구현돼 있다

**사실:** 예약/메뉴 진입 전에 **결제수단 등록 여부 플래그**로 분기하고, 미등록이면 웹 등록 화면으로 보낸다. **미납 잔액** 분기도 별도로 존재한다.

```
   확인된 게이트:  결제수단 등록 여부  ·  미납 잔액 존재 여부
   → L6의 "순차 자격 검증 게이트" 패턴이 실무에서 이미 돌고 있다 ✅
   → 내가 만든 게 아니라도 "왜 이 구조인가"를 설명할 수 있으면 딥다이브 방어가 된다
```

## ⭐ 발견 3 — 간편결제 연동은 웹 레포에서 진행된다

**사실:** 웹 프론트 레포의 최근 작업이 **간편결제 연동 구조 설계 + 리소스 정의**다.
→ 결제수단 확장이 **웹에서 이뤄진다**는 L5의 방어 논리("웹 1벌로 흡수")를 실제 커밋이 증명한다. ✅

## ⭐ 발견 4 — 2단 결제(hold→capture)는 코드로 확인 못 했다

```
❓ 미확인:  authorize/capture 분리, hold TTL, 부분 매입, 추가 결제 흐름
   → 서버·PG 계층 책임이라 iOS 코드에서 안 보이는 게 자연스럽다
   → 면접 답변: "클라 관점에서는 예약 시 승인, 반납 후 확정 금액 청구로 보였습니다.
                다만 승인·매입 분리와 hold 유효기간 정책은 서버·PG 계약이라
                제가 직접 확인한 범위는 아닙니다."
   ⭐ 이렇게 답하면 정직하면서도 구조를 이해한다는 게 전달된다
```

## 📌 확정 / 미확인 정리

```
✅ 확정: 결제 실행은 웹뷰 · 네이티브는 브릿지 + 카드 OCR 제공 · 이용내역만 네이티브 ·
        결제수단 등록 게이트 + 미납 게이트 존재 · 간편결제 확장은 웹에서 · iOS에 멱등키 0건
❓ 미확인: 웹/서버의 멱등키 구현 · authorize/capture 분리 · hold TTL 정책 ·
          webhook 이중화 여부 · reconcile 루틴 존재 여부 ⭐(가장 궁금한 지점)
```
> 🗝️ **다음 액션 (실무에서 확인할 것):** reconcile 루틴이 실제로 있는지. 없다면 이건 **내가 제안해서 만들 수 있는 개선**이고, 그 자체가 강력한 면접 소재가 된다("문제를 발견하고 제안했다").
