## 🔴 오답 교정 ① — "협업 여부가 설계를 가장 크게 바꾼다"

세 축은 **서로 다른 것을 결정한다.** 같은 저울에 올리면 안 된다.

```
 디바이스 수 ──────► 충돌이 "존재하는가"      (1대면 문제 자체가 소멸)
 편집 단위   ──────► 충돌해소 "알고리즘"      (문서 / 블록 / 문자)
 협업        ──────► 토폴로지와 "실시간성"    (서버=저장소? 중계자?)
```

협업이 바꾸는 건 **토폴로지**(WebSocket 중계 · presence · 커서공유 · 권한). 크다. **하지만:**

```
   ⚠️  협업이 0명이어도 충돌은 이미 발생한다
   나 혼자 · 아이폰과 아이패드 · 둘 다 비행기 모드에서 편집 → replica 2개 → divergence
```

> **충돌해소 난이도를 결정하는 건 협업이 아니라 `오프라인 × replica ≥ 2`.**

이걸 놓치면 나는 사고: *"협업 없으니 `updatedAt` 최신 것으로 덮으면 됨"* → 아이패드에서 쓴 문단이 조용히 사라짐. **에러 0건.** 유저는 자기가 안 쓴 줄 알고 리포트도 안 한다.

**면접 답변:** *"협업 여부는 토폴로지를 가장 크게 바꿉니다. 다만 충돌해소 설계는 협업과 무관하게 이미 필요합니다. 왜냐하면 멀티디바이스 오프라인 편집만으로 replica가 2개가 되기 때문입니다."*

## ⭐ 오늘의 정답 — 편집 단위 3택 → 충돌해소 매핑

> **핵심 법칙: 잘게 쪼갤수록 자동 병합률 ↑, 메타데이터·복잡도 ↑.**

```
Ⓐ 문서 전체            Ⓑ 블록/문단             Ⓒ 문자
┌──────────────┐      ┌──────────────┐       ┌──────────────┐
│▓▓▓▓▓▓▓▓▓▓▓▓▓▓│      │▓▓▓▓▓│░░░░░│▓▓│       │▓│░│▓│░│▓│░│▓│
└──────────────┘      └──────────────┘       └──────────────┘
 충돌단위=문서          충돌단위=블록           충돌단위=문자
 자동병합률 최저         대부분 자동병합          거의 100% 병합
 메타데이터 0            블록ID + 순서키          문자당 ID + tombstone
 = iCloud Drive 파일    = Notion                = Google Docs
```

| | Ⓐ 문서 전체 | Ⓑ 블록 | Ⓒ 문자 |
|---|---|---|---|
| **해소 방법** | LWW / 충돌UI / fork("(충돌본)") | 블록별 LWW + **순서 CRDT** | OT 또는 텍스트 CRDT(RGA) |
| **대가** | 한 글자 달라도 전체 충돌 → 유실 or 사용자 노동 | 블록 ID 발급·추적. **순서 병합이 진짜 난제** | 메타데이터 폭발(원문의 수배), 라이브러리 의존 |
| **얻는 것** | 구현 압도적 단순 | 실무 충돌 대부분 자동 해소 | 같은 문장 동시편집도 병합 |
| **언제** | 편집 세션 짧고 동시편집 드묾 | **오프라인 멀티디바이스 (스위트스팟)** | 실시간 협업이 *핵심 기능*일 때만 |

### 🗝️ 함정: 텍스트 병합보다 **순서 병합**이 어렵다

```
   둘 다 "2번째 위치에 블록 삽입"하면?

   iPhone: [A] [새로운X] [B]        iPad: [A] [새로운Y] [B]
   병합 결과가 [A][X][Y][B] 인가 [A][Y][X][B] 인가?
   → 순서 배열의 index는 CRDT가 될 수 없다 (index는 다른 replica 삽입에 밀린다)
```

**해법:** index 대신 **정렬키(order key)** 를 값으로 갖는다.
- **fractional indexing** — 블록 사이를 소수로 (`1.0`, `1.5`, `2.0`). 단순하지만 반복 삽입 시 정밀도 소진 → 주기적 재정렬 필요
- **CRDT 방식** — `(orderKey, replicaId)` 튜플로 타이브레이크 → 어느 순서로 병합해도 **결정적으로 같은 결과**

### 오늘의 선택: **Ⓑ 블록 단위**
```
Ⓒ 탈락: 실시간 협업을 스코프에서 뺐으므로 메타데이터 폭발 비용을 정당화 못 함
Ⓐ 탈락: 비기능 요구 "유실 0" 위반 (LWW는 유실, 충돌UI는 사용자에게 노동 전가)
```

## 🧠 CRDT 딥다이브 — 왜 "자동으로" 수렴하는가

**CRDT = Conflict-free Replicated Data Type.** 병합 함수가 이 3성질을 만족하면 **어떤 순서로 병합해도 같은 결과**로 수렴한다.

```
   교환법칙 commutative   merge(a,b) == merge(b,a)      순서 무관
   결합법칙 associative   merge(merge(a,b),c) == merge(a,merge(b,c))   묶는 방법 무관
   멱등성   idempotent    merge(a,a) == a               중복 전달 안전 ⭐ 재전송/네트워크 재시도에 강함
```

> **LWW가 CRDT가 아닌 게 아니다.** LWW-Register도 CRDT다. 문제는 **수렴은 하지만 정보를 버린다**는 것. "수렴 ≠ 유실 없음"이 핵심 구분.

```
   수렴한다 ─┬─ 정보를 버리며 수렴  → LWW-Register  (한쪽이 사라짐)
             └─ 정보를 보존하며 수렴 → OR-Set, RGA  (둘 다 살아남음)
```

### 필요한 CRDT 4종 (이 앱에 쓰는 것만)
```
LWW-Register   블록 본문 텍스트   최신 하나만 필요한 스칼라 (제목, 본문)
OR-Set         태그 집합         추가/삭제 둘 다 있는 집합 (tombstone 필요)
RGA/시퀀스     블록 순서         삽입 위치가 결정적으로 정해져야 함
PN-Counter     (참고) 카운터     증감이 교환가능 → 오프라인 카운트에 안전
```

### ⭐ Tombstone — 삭제는 "지우기"가 아니라 "삭제 표시"
```
   ❌ 진짜 삭제:  iPhone에서 블록 삭제 → 서버 sync
                  iPad는 그 블록을 아직 갖고 있음 → 다시 올림 → 🧟 좀비 부활

   ✅ tombstone:  deletedAt 마킹만 하고 레코드 유지
                  "이건 삭제된 것"이 명시적 사실 → 부활 불가

   대가: 무한 증가 → GC 필요
   GC 조건: "모든 replica가 이 tombstone을 봤다"가 확정된 뒤에만 삭제
           (마지막 sync 시각 최소값 기준 + 유예기간)
```

### ⭐ 시계를 믿지 마라 — Lamport / HLC

**"`updatedAt` 비교하면 되지 않나요?"** 가 이 시나리오 최다 오답이다.

```
   ❌ 기기 wall clock: 유저가 설정에서 바꿀 수 있고, drift 있고, 타임존 사고
      → 아이패드 시계가 5분 빠르면 아이패드가 영원히 이긴다

   ✅ Lamport clock:  각 replica가 카운터 보유. 이벤트마다 +1,
                      메시지 수신 시 max(내것, 받은것)+1
      → "인과관계 순서"를 보장 (동시성은 replicaId로 타이브레이크)

   ✅ HLC (Hybrid Logical Clock): 물리시각 + 논리카운터
      → 사람이 읽을 수 있는 시각 + 인과성 둘 다. 실무 추천
```

### OT vs CRDT (물어보면 답할 수 있어야)
| | OT (Operational Transform) | CRDT |
|---|---|---|
| 서버 | **중앙 권위 필수** (연산 변환·순서 결정) | 불필요 (P2P 가능) |
| 메타데이터 | 작다 | 크다 (ID·tombstone) |
| 구현 | 변환 함수 조합 폭발 → 까다로움 | 라이브러리로 해결 (Automerge/Yjs) |
| 오프라인 | 약함 (서버 왕복 전제) | **강함** ⭐ |
> **모바일 오프라인 우선 = CRDT 유리.** 서버 없이도 병합되기 때문.

## ④ 로컬 스키마

```
Note   : id(UUID, ⭐클라 생성) · titleReg(LWW) · createdAt · deletedAt(tombstone)

         · deletedAt(tombstone)
```

## ⑧ Deep Dive 3

### 🅰 충돌해소 3단 사다리 (단계적 도입 = 방어 가능한 설계)
```
1단계  블록별 LWW(HLC) + tombstone    ← 서로 다른 블록 편집은 이미 자동병합 (실무 충돌 80%+ 해소)
2단계  순서 CRDT (orderKey + replicaId 타이브레이크)   ← 삽입 충돌 해소
3단계  같은 블록 동시편집 → 텍스트 CRDT 또는 "두 버전 보관"  ← 협업 필요해지면
```
> 🗝️ **면접 결정타:** "처음부터 3단계를 다 짓지 않습니다. 1·2단계로 실무 충돌 대부분을 덮고, 3단계는 협업 요구가 생길 때 도입합니다. 다만 **데이터 모델에 `lamport`·`replicaId`·`orderKey`·`tombstone`은 처음부터 넣습니다.** 왜냐하면 이건 나중에 추가하면 전체 마이그레이션이라 one-way door이기 때문입니다."

### 🅱 동기화 엔진 (배터리·flaky 내성)
```
트리거: 앱 포그라운드 · 편집 후 debounce(2~5s) · 네트워크 복구 · BGTaskScheduler
❌ 상시 폴링 금지 (네트워크 = 로컬 대비 ~100x 전력, sd-b1)
배칭: 연산 N개를 한 요청으로 (타이핑 1글자마다 요청 = 배터리 사망)
실패: 지수백오프 + jitter. OpLog는 append-only라 재시도 안전 (멱등성)
부분 실패: 성공한 op만 syncedAt 마킹 → 나머지 재시도
관측: 미동기 op 수 · 마지막 성공 sync 시각 → UI에 노출("동기화 대기 3개")
```

### 🅲 대용량 노트 · 첨부
```
노트 1000개 × 블록 50개 = 50,000 블록 → 전체 로드 금지, 노트 단위 lazy
tombstone GC: 모든 replica 확인 후 + 유예기간(예 30일)
첨부: blob은 sync 채널 분리 + resumable 업로드 + 참조만 op에 → 큰 파일이 sync 전체를 막지 않게
```

## ⑨ 트레이드오프 (소리내야 점수)

```
편집 단위 잘게        ↔ 메타데이터·복잡도 (Ⓑ가 스위트스팟)
자동 병합            ↔ 예측 가능성 (자동 병합 결과가 유저 의도와 다를 수 있음)
tombstone 보관       ↔ 저장 공간 (GC 조건 설계 비용)
sync 자주            ↔ 배터리·대역폭 (debounce + 배칭)
CRDT 라이브러리      ↔ 바이너리 크기 + Swift 바인딩 성숙도
```
**one-way vs two-way door:**
> *"sync 주기·배칭 크기·debounce 수치는 나중에 조정 가능합니다(two-way door). 반면 **편집 단위와 ID 발급 주체(클라 vs 서버)** 는 데이터 모델 자체라 바꾸면 전체 마이그레이션입니다(one-way door). 그래서 이 둘만 초반에 신중히 정하고 나머지는 빠르게 갑니다."*

## 💪 압박 방어 ① — "CRDT는 오버엔지니어링 아닌가요? 그냥 최신 것으로 덮으면?"

```
① 질문을 되돌린다   "유실을 허용하는 데이터인지 먼저 봅니다"
                     좋아요 카운트 = 덮어도 됨. 회의록 문단 = 안 됨.
② 비용을 정정       CRDT의 비용은 '어렵다'가 아니라 메타데이터와 라이브러리 의존입니다
③ 단계적 도입 제시   1·2단계(블록 LWW + 순서키)로 충돌 대부분 덮고,
                     텍스트 CRDT는 협업 요구가 생길 때
④ 양보할 수 없는 선  단, lamport·replicaId·tombstone 필드는 처음부터. one-way door라서.
```
**모범답안:** *"덮어쓰기로 충분한 데이터도 많습니다. 좋아요 카운트라면 저도 LWW를 씁니다. 다만 노트 본문은 유실이 조용히 발생하고 에러도 안 나기 때문에 리포트조차 안 들어옵니다. 그래서 최소한 '두 버전 다 보관'까지는 필요하다고 봅니다. 그리고 전체 CRDT를 처음부터 짓지는 않습니다. 블록 단위 LWW와 순서키로 시작하고, 데이터 모델에만 논리시계와 tombstone을 미리 넣습니다. 왜냐하면 이 필드들은 나중에 추가하면 전체 마이그레이션이기 때문입니다."*
