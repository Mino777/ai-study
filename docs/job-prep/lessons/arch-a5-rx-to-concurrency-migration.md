## ❌ 주니어 답 vs ✅ 시니어 답
```
❌ "async/await가 더 좋으니 마이그레이션 해야죠"  → 위험·비용·순서 없음
✅ 4틀: 상황 → 결정(점진) → 트레이드오프 → mitigation + 팀 설득 축
```

## ① 상황
Rx 기반 코드베이스(Repository→Rx 스트림, disposeBag 수명관리). 문제 신호:
- 스레드 정책이 스트림 연산 중간에 흩어져 "지금 어느 스레드?" 추적 비용
- disposeBag 누락 시 누수 — **컴파일러가 못 잡음**(런타임에야 발견)
- 신규 입사자 러닝커브(Rx 연산자)
- Swift 6 strict concurrency 방향과 어긋남 = 미래 부채

## ② 결정 — Strangler Fig (빅뱅 X)
```
❌ 전면 재작성 → 회귀 위험 폭발 + 기능 개발 정지
✅ 점진 이행   → 새 코드는 async, 기존은 유지 + 경계에 브릿지 공존
```
**전환 우선순위(아무거나 먼저 X):**
```
1순위  일회성 요청 (Single/Completable → async throws)  ← 1:1 매핑, 위험 최소
2순위  신규 피처 전체를 async로
3순위  Data 계층 Repository (actor로 공유 캐시 격리)
후순위 복잡한 스트림 조합(debounce·merge·combineLatest) ← Rx가 여전히 강함
⛔ 안 건드림  잘 돌고 변경 없는 레거시 (ROI 없음)
```
**브릿지:** `try await single.value` (Rx→async) / `Observable.create { Task {...} }` (async→Rx)

## ③ 트레이드오프
```
얻음 ✅  구조적 취소(disposeBag 수동→스코프 자동, 누수 구조적 불가)
        격리가 타입 선언에 명시 → 컴파일러 검증 = 코드리뷰 가능
        신규 입사자 진입장벽↓(언어 표준 문법)
비용 ❌  공존 기간 인지 부하(두 패러다임) · 브릿지 코드 자체가 부채
        스트림 조합 표현력 일시 후퇴(AsyncSequence < Rx 연산자) · iOS/Swift 버전 제약
```

## ④ 방어(mitigation) ⭐ 결정타
```
인지 부하  → "새 코드는 async" 컨벤션·린트로 못박아 경계 명확화
브릿지 부채 → 브릿지는 계층 경계 1곳에만 + 목록 관리(확산 방지)
스트림 후퇴 → 복잡 조합은 Rx/Combine 유지 = 적재적소(억지 이행 X)
회귀 위험  → 전환 단위마다 테스트 우선 + 점진 릴리스
```

## 🗣️ 팀 설득 축 (리더십 신호)
"기술이 좋아서"는 설득 안 됨 → **팀 언어로 번역**: 누수 버그 재발률 · 신규 입사자 온보딩 시간 · Swift 6 대응 비용. **작은 성공 먼저**(한 피처 전환 → 결과 공유 → 합의 확산). 🔗 `ARCH-SD.md` A8 "팀 설득 과정"과 연결.

## 💪 압박 질문 방어 2개

### Q1. "전환을 아예 안 하는 것도 선택지 아닌가요? Rx로 잘 돌는데 왜 리스크를?"
> **기존 코드와 신규 코드를 분리**해서 답한다.
> "기존 코드는 전면 재작성할 이유가 없습니다 — 리스크만 큽니다. 다만 **리스크를 감수하지 않아도 되는 신규 피처부터** async로 씁니다. Rx도 debounce·merge 같은 조합에선 여전히 이점이 있지만, **Swift 6가 strict concurrency로 방향을 정했고 actor·Sendable 검사가 언어 레벨로 들어왔습니다. 서드파티는 이 컴파일러 보증을 못 받습니다** — 시간이 갈수록 언어 표준이 안전성에서 앞서갑니다. 그리고 공존은 오히려 자산입니다: 신규 입사자가 기존 코드로 Rx를 배우고 새 코드에선 async를 자유롭게 쓰는 환경이 됩니다."
>
> 🗝️ **핵심 기술:** "내 취향(의견)" 대신 **"플랫폼 방향성(사실)"** 으로 근거를 옮긴다 → 반박하려면 애플 로드맵을 반박해야 함. + 공존을 비용이 아닌 **온보딩 자산**으로 재프레이밍.

### Q2. "그럼 언제 전환을 멈추죠? 끝이 안 나는데?"
> "'완전 제거'를 목표로 두지 않습니다. **신규 = async 라는 경계만 유지**하면 Rx 비중은 자연 감소합니다. 억지로 마지막 1%를 걷어내는 비용이 이득을 넘는 지점에서 멈추는 게 맞습니다."
>
> 🗝️ **"끝을 정의하지 않는 것도 전략"** = 시니어 시그널.

## 🎤 60초 모범답안 (암송)
> "전면 재작성은 안 했습니다. Rx는 잘 돌고 있었고 재작성은 회귀 위험만 큽니다. **Strangler Fig로 점진 이행**했습니다 — 새 코드는 async, 기존 Rx는 경계에 브릿지를 두고 공존. 순서는 1:1 매핑인 **일회성 요청(Single→async throws)부터**, 다음 신규 피처, Data 계층은 actor로 캐시 격리. 반면 **debounce·merge 같은 복잡 조합은 Rx에 남겼습니다** — AsyncSequence가 아직 그만한 표현력이 없어 억지 이행이 손해라 봤습니다. 얻은 건 **구조적 취소** — disposeBag 누락 누수가 구조적으로 불가능해지고 격리가 타입에 드러나 컴파일러가 검증합니다. 대신 공존 인지 부하를 냈고, 이건 '새 코드는 async' 컨벤션 + 브릿지를 계층 경계 1곳으로 제한해 막았습니다. 팀에는 최신 기술이 아니라 **누수 재발률·온보딩 시간**으로 설명하고, 한 피처를 먼저 전환해 결과를 공유한 뒤 합의를 넓혔습니다."

**박제 한 줄:** *빅뱅 X, Strangler Fig. 일회성→신규피처→Data(actor). 복잡 스트림은 Rx 유지(적재적소). 얻음=구조적 취소 / 비용=공존 인지부하 → 컨벤션+브릿지 1곳. 설득은 기술이 아니라 지표로. 근거는 의견이 아니라 플랫폼 방향성으로.*
