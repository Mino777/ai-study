## 🧭 지도가 어려운 진짜 이유 (3층으로 분리해서 말하라)

```
L0~L1  좌표·타일 계층    "지구를 평면 정수 격자로 접는 문제"      ← 대부분 여기를 모른다
L2~L4  공간 쿼리·집계    "수만 개 중 뷰포트 200개만 고르는 문제"   ← 규모 감각이 드러난다
```

# L0 — 좌표계와 투영 (여기를 아는 사람이 드물다)

## 두 개의 좌표계를 구분하라

```
WGS84 (EPSG:4326)                 Web Mercator (EPSG:3857)
─────────────────────             ─────────────────────────
위도/경도 (도 단위)                 평면 미터 (x, y)
GPS가 주는 것                       지도 타일이 쓰는 것
lat ∈ [-90, 90]                    y ∈ 약 ±20,037,508 m
lon ∈ [-180, 180]                  x ∈ 약 ±20,037,508 m
구면(타원체)                        평면 (등각 투영)

   GPS 좌표 ──[투영]──► 화면 픽셀
   이 변환을 SDK가 해주지만, 왜 왜곡되는지는 알아야 한다
```

## ⭐ Mercator 왜곡 — 면적은 거짓말한다

```
   Web Mercator는 "등각(conformal)" 투영 = 각도는 보존, 면적은 왜곡
   확대 배율 = 1 / cos(위도)

   위도 0°  (적도)     배율 1.00   ← 기준
   위도 37.5° (서울)    배율 1.26   ← 26% 확대
   위도 60°            배율 2.00   ← 2배
   위도 85°            배율 11.5   ← 그린란드가 아프리카만큼 커 보이는 이유
```

**실무에 주는 3가지 결과:**
```
① 같은 zoom에서 미터/픽셀이 위도마다 다르다
   → "zoom 14는 몇 미터인가"에 정답은 위도를 물어야 나온다
② 격자 기반 클러스터링을 화면 픽셀로 하면 OK,
   미터로 하면 고위도에서 격자가 찌그러진다  ← 흔한 버그
③ 면적 기반 집계(㎢당 차량 수)를 Mercator y로 계산하면 틀린다
   → 면적은 등면적 투영이나 H3 같은 셀 시스템으로
```

> 💬 **압박 대응:** *"우리 서비스는 국내라 위도 범위가 33~38도로 좁습니다. 그래서 cos 보정 없이도 오차가 크지 않아 초기엔 근사로 갑니다. 다만 격자 크기를 미터로 하드코딩하지 않고 **화면 픽셀 기준**으로 잡습니다. 왜냐하면 픽셀 기준은 위도에 무관하게 사용자가 보는 밀도와 일치하기 때문입니다."*

## 타일 좌표 변환 (알아두면 확실히 차별화)

```
   zoom z 에서 타일 격자는 2^z × 2^z 장

   tileX = floor( (lon + 180) / 360 × 2^z )
   tileY = floor( (1 − ln(tan(φ) + sec(φ)) / π) / 2 × 2^z )      φ = 위도(라디안)

   → 이게 z/x/y 타일 URL의 정체:  https://.../{z}/{x}/{y}.png
   → 서버 캐시·CDN 키가 되고, 우리 bbox 쿼리의 격자 스냅 단위로도 재사용된다 (L3)
```

# L1 — 타일 시스템과 해상도 예산

## 확정 상수 (암기 가치 있음)

```
   지구 적도 둘레 ≈ 40,075,017 m
   기본 타일 = 256 × 256 px
   → zoom 0 에서 1 px = 40,075,017 / 256 ≈ 156,543 m

   미터/픽셀(적도) = 156,543 / 2^z
   미터/픽셀(위도φ) = 156,543 / 2^z × cos(φ)
```

## zoom 감각표 (서울 φ=37.5°, cos≈0.793)

| zoom | m/px (적도) | m/px (서울) | 타일 1장 폭(서울) | 보이는 것 | 타일 총수 4^z |
|---|---|---|---|---|---|
| 10 | 152.9 | 121 | ~31 km | 수도권 전체 | 1.05M |
| 12 | 38.2 | 30.3 | ~7.8 km | 시/구 | 16.8M |
| 14 | 9.55 | 7.58 | ~1.9 km | 동 단위 | 268M |
| 15 | 4.78 | 3.79 | ~970 m | 블록 | 1.07B |
| 16 | 2.39 | 1.90 | ~486 m | 건물 구분 | 4.29B |
| 18 | 0.60 | 0.48 | ~122 m | 주차 구획 | 68.7B |

**여기서 나오는 설계 결정:**
```
① 화면 하나 = 타일 6~12장 (기기 해상도·@2x/@3x에 따라)
   타일 1장 raster 20~50KB → 화면 1회 = 150~600KB
   → 팬을 10번 하면 수 MB. 타일 캐시가 없으면 셀룰러 데이터 사망
② "차량 개별 마커가 의미 있는 최소 zoom"이 클러스터링 경계가 된다 (L4)
   z≤12: 30m/px → 차량 10대가 1px 안에 겹침 → 개별 표시 무의미
   z≥15: 4m/px → 차량 간 구분 가능 → 개별 표시 의미 있음
③ 오프라인 지도는 zoom 범위 × 영역으로 용량이 폭발
   → 전국 z18 사전 다운로드는 불가. "예약한 차량 주변 z16까지"처럼 좁혀야
```

## raster vs vector 타일

```
raster (PNG/JPEG)              vector (MVT/pbf)
────────────────               ─────────────────
서버가 그림 완성                좌표+속성만, 클라가 그림
✅ 클라 CPU 저렴                ✅ 용량 작다, 스타일 런타임 변경
✅ 구현 단순                    ✅ 회전/기울기 자유, 라벨 충돌 회피
❌ 스타일 고정(다크모드 = 별 타일셋) ❌ 클라 렌더 비용 (GPU 필요)
❌ 확대 시 흐림                  ❌ 구현/SDK 의존 큼

모빌리티 선택: 대부분 SDK가 정해준다. 다크모드·테마 요구가 있으면 vector가 유리.
```

# L2 — 공간 인덱싱 (4종 비교 + 함정)

> **문제:** 차량 수만 대에서 "이 bbox 안"을 어떻게 빠르게 고르나. 그리고 "이 지역 집계"를 어떻게 미리 계산하나.

```
🅐 geohash            문자열 prefix = 사각 셀. lon/lat 비트 교차 인터리브 → base32
   장점: 문자열 prefix 검색만으로 범위 쿼리 (일반 DB·KV에서도 동작) ⭐ 도입 쉬움
   단점: 셀이 직사각(위도에 따라 찌그러짐) · ⚠️ 경계 함정(아래)

   정밀도 감각 (표준표):
     4자 ≈ 39 × 20 km      5자 ≈ 4.9 × 4.9 km
     6자 ≈ 1.2 × 0.6 km    7자 ≈ 153 × 153 m     8자 ≈ 38 × 19 m

🅑 quadtree / 타일 z/x/y   지도 타일과 좌표계가 완전 일치 ⭐
   장점: 클라 뷰포트·서버 집계·CDN 캐시 키가 같은 격자 → 캐시 정합성 최고
   단점: 셀 크기가 zoom 단계로만 (2배씩) 점프

🅒 S2 (Google)         구면을 큐브 6면 → Hilbert 곡선으로 1D 매핑
   장점: 구면 왜곡 적음 · Hilbert 곡선이라 인접성 보존 우수 · 셀 레벨 세밀
   단점: 라이브러리 필요, 개념 학습 비용

🅓 H3 (Uber)           육각형 셀, 해상도 0~15
   장점: ⭐ 6개 이웃이 모두 등거리 (사각형은 변-이웃 4 vs 꼭짓점-이웃 4가 거리 다름)
        → 확산·커버리지·수요 히트맵 집계에 수학적으로 깔끔. 모빌리티 업계 표준화 추세
   단점: 육각형은 완전 계층 분할이 불가(자식이 부모 경계를 살짝 넘음) → 정확한 롤업에 주의
```

## ⚠️ geohash 경계 함정 (이걸 말하면 실제로 써봤다는 신호)

```
   두 지점이 물리적으로 1m 떨어져 있어도 prefix가 완전히 다를 수 있다

        │ geohash "wydm7"        │ geohash "wydm5"
   ─────┼────────────────────────┼─────────
        │      🚗 A              │  🚗 B      A와 B는 5m 거리
        │                        │            그런데 prefix 공유 0
                            셀 경계

   → prefix 검색만 하면 경계 근처 차량이 누락된다 ⛔
   ✅ 해법: 8방향 이웃 셀(neighbors)까지 함께 조회 → 9셀 union 후 정확 거리 필터
   ✅ 또는 bbox를 덮는 셀 집합을 계산해서 조회 (cover 알고리즘)
```

## 선택 기준 (면접에서 이렇게 답한다)

```
"실시간 차량 조회"    → 타일 z/x/y (quadtree). 이유: 클라 뷰포트·CDN 캐시 키와 격자가 같아
                       캐시 정합성이 공짜. 별도 라이브러리도 불필요.
"수요·공급 히트맵 집계" → H3. 이유: 등거리 이웃이라 확산·커버리지 계산이 왜곡 없음.
"기존 DB로 빨리 시작"  → geohash. 이유: 문자열 prefix라 특별한 인덱스 없이 동작.
                       단, 경계 이웃 셀 조회를 반드시 넣는다.
"PostGIS/공간 인덱스 있다" → 그냥 R-tree + ST_Within. 인덱싱 직접 안 짜는 게 낫다 ⭐
```
> 🗝️ **마지막 줄이 시니어 결정타:** *"DB가 공간 인덱스를 지원하면 저는 직접 격자를 설계하지 않습니다. 왜냐하면 직접 만든 격자는 경계 처리와 재집계를 우리가 영구히 유지보수해야 하기 때문입니다. 격자를 직접 도입하는 건 캐시 계층이나 사전집계가 필요해진 뒤입니다."*

# L3 — 뷰포트 쿼리 설계 (요청 폭발을 막는 곳)

## 나이브 구현이 죽는 과정

```
❌ 지도 didChangeVisibleRegion 마다 요청
   드래그 1회 = 델리게이트 30~60회 → 요청 30~60개 → 서버·배터리·레이스 전부 붕괴
   게다가 응답이 순서대로 안 온다 → 오래된 응답이 최신 화면을 덮어씀 (stale write)
```

## ✅ 5단 방어

```
① debounce 300~500ms      드래그가 "멈춘 뒤" 1회. (팬 중에는 요청 X)
                          단, 첫 진입은 즉시 (leading edge) → 체감 지연 방지

② bbox 격자 스냅 ⭐        요청 bbox를 타일 격자에 맞춰 확장(스냅)
                          → 1픽셀 움직여도 같은 키 → 캐시 히트
                          키 = (z, tileXRange, tileYRange, filterHash)

③ 포함 관계 스킵           새 bbox ⊂ 이미 받은 bbox 이고 신선하면 요청 생략

④ over-fetch 마진         화면보다 20~30% 넓게 받음
                          → 살짝 팬해도 재요청 없음 (대가: 페이로드 +40~70%)

⑤ 최신 요청만 채택         seq/generation 번호 부여, 이전 Task 취소
                          → 오래된 응답 폐기 (셀 재사용 레이스와 같은 구조 ⭐ ios-04)
```

## 요청/응답 계약

```
GET /vehicles?z=15&tiles=27334,12703-27336,12705&filter=<hash>
  또는  ?bbox=minLat,minLon,maxLat,maxLon&z=15

→ {
    mode: "individual" | "cluster",     ⭐ 서버가 모드를 정한다 (L4)
    vehicles: [ {id, lat, lon, ...} ],
    clusters: [ {cellId, count, lat, lon} ],
    ttl: 5,                             ⭐ 캐시 수명을 서버가 제어
    generation: 1234                    ⭐ 클라의 stale 판정용
  }
```
> ⭐ **`mode`를 서버가 정하는 이유:** 클러스터링 경계 zoom을 앱에 하드코딩하면 조정할 때 앱 배포가 필요하다. **앱 배포는 비가역**이므로 임계값은 서버로 뺀다. (모빌리티 3원칙 ③)

## 좌표 페이로드 최적화

```
차량 1대 = {id, lat, lon, model, fuel, price} ≈ 200B (JSON)
500대 = 100KB

절감 3수:
① 좌표 양자화     소수점 5자리 = 약 1.1m 정밀도로 충분 (7자리는 11cm — 과잉)
                  → "37.51234" (5자리). 문자열 길이 절감 + gzip 효율↑
② 델타 전송       2회차부터 변경분만 {id, lat, lon} (모델·요금은 안 변함)
③ 필드 분리       마커 렌더에 필요한 최소 필드만 목록 API,
                  상세는 탭 시점에 개별 조회 (⭐ 목록 API를 상세 스키마로 만들지 않는다)
```

# L4 — 클러스터링 (감별점 정점)

## 결정 트리

```
                     이 zoom에서 개별 차량이 의미 있나?
                     (차량 간 거리 > 마커 크기?)
                        │
              ┌─────────┴─────────┐
             아니오                 예
              │                     │
        서버 사전집계 클러스터      개별 차량 + 클라 클러스터링
        (z ≤ ~13)                  (z ≥ ~14, 측정필요)
        페이로드 = 셀 수십 개        페이로드 = 차량 수백 개
        필터 조합마다 서버 계산      필터 즉시 재계산 (왕복 0)
```

## 왜 하이브리드인가 — 각 방식의 죽는 지점

```
클라 단독:  전국 z10 → 5만 대 전송 → 5만 × 200B = 10MB + 클라 클러스터링 CPU
            → 셀룰러에서 수 초 정지, 메모리 스파이크. ⛔ 규모 감각 실패
서버 단독:  z16에서 필터(차종·요금대) 바꿀 때마다 왕복
            → 필터 UX가 즉각 반응 못 함. 필터 조합 폭발로 서버 캐시 히트율 붕괴
하이브리드: 각자 강한 구간만 담당. 경계 zoom은 서버 설정값 ⭐
```

## 클러스터링 알고리즘 3종

```
🅐 격자 기반 (grid)        셀 하나 = 클러스터 하나
   ✅ O(n), 결정적, 서버 사전집계 가능(같은 셀이면 같은 결과 → 캐시 가능) ⭐
   ❌ 셀 경계에 걸친 밀집이 둘로 쪼개짐 · 클러스터 중심이 격자에 묶여 어색

🅑 거리 기반 / supercluster (KD-tree 계층)
   ✅ 시각적으로 자연스러움 · zoom별 계층 사전계산 → 조회 O(log n)
   ✅ 클라 라이브러리 성숙 (수만 점 실시간 가능)
   ❌ 점 집합이 바뀌면 계층 재구축 (실시간 위치 변화와 궁합 주의) ⚠️

🅒 SDK 내장 클러스터링
   ✅ 구현 비용 0 (MapKit은 annotation에 clusteringIdentifier 지정)
   ❌ 정책 제어 약함(그룹 기준·표현 커스터마이즈 제한) · 대량에서 성능 한계
   → 프로토타입엔 최적. 요구가 생기면 교체 (two-way door)
```

## ⭐ 클러스터 "안정성" — 대부분 놓치는 품질 이슈

```
문제: 위치가 3초마다 갱신되면 클러스터가 매번 재계산되어
      숫자가 깜빡이고(12→11→12) 중심이 흔들린다 → 지도가 "떨린다"

해법 4수:
① 셀 고정        격자 기반이면 셀 ID가 안정적 → 중심을 셀 중심에 고정 (차량 평균 위치 X)
② count만 갱신    클러스터 뷰를 재생성하지 말고 라벨 숫자만 업데이트
③ 히스테리시스   경계에서 왕복하지 않도록 임계값에 여유(예: 병합 40px / 분리 55px)
④ 애니메이션 억제  갱신 주기 < 애니메이션 길이면 애니메이션을 끈다 (겹쳐서 더 지저분)
```
> 🗝️ 이걸 말하면 *"실제로 화면 보면서 튜닝한 사람"* 이 된다. 알고리즘만 아는 사람과 갈린다.

# L5 — 렌더 성능 (16.6ms 예산)

## 프레임 예산

```
60fps = 16.67ms/frame  (120Hz 기기는 8.3ms — ProMotion 고려하면 더 빡빡)
   지도 팬/줌 중에는 SDK가 타일 렌더로 이미 상당 부분을 쓴다
   → 우리 마커 작업은 프레임당 수 ms 이내여야 한다
   → 결론: 갱신 시 "전체 재구성" 금지. diff 만.
```

## ⭐ 마커 갱신 = 셀 재사용과 같은 문제 (ios-04 재활용)

```
❌ 나이브:  removeAnnotations(all) → addAnnotations(new)
   결과: 깜빡임 · 선택 상태 소실 · 콜아웃 닫힘 · 뷰 재생성 폭발 · GC 압력

✅ diff 갱신:
   기존 id 집합 vs 신규 id 집합
     ├ 추가된 id  → add
     ├ 사라진 id  → remove
     └ 남은 id    → 좌표만 갱신 (뷰 재사용, 필요시 위치 애니메이션)

✅ 비동기 레이스 방어 (셀 재사용과 동일 구조)
   마커 뷰에 비동기로 이미지/상세를 채울 때
   → 응답 도착 시 "이 뷰가 아직 그 차량의 뷰인가" 식별자 재검증 ⭐
   → 재사용 풀에서 다른 차량에 배정됐으면 폐기
```

## 마커 뷰 비용 절감

```
① 아이콘 사전 렌더 + 캐시    타입×상태 조합(예: 차종3 × 상태3 = 9종)을 UIImage로 미리 구워 캐시
                            ⛔ 매 마커마다 draw/텍스트 렌더 = 프레임 드랍
② 재사용 풀 사용            SDK가 제공하는 dequeue 계열을 반드시 쓴다 (테이블뷰와 동일 사고)
③ 화면 밖 마커 제거         뷰포트 + 마진 밖은 모델에서도 내린다 (메모리·diff 비용 절감)
④ 상한선 강제               개별 마커 상한(예 300~500, 측정필요) 초과 시 강제 클러스터 모드
                            ⭐ "상한이 없는 렌더"는 반드시 언젠가 터진다
⑤ 라벨/그림자 주의          투명도·그림자·복잡 레이어는 오프스크린 렌더 유발 → 팬 중 프레임 드랍
```

## 대량 표현이 정말 필요할 때 (마커의 한계)

```
마커(annotation)는 개별 뷰 = 수백 개가 실질 상한
수천~수만 점을 동시에 보여야 하면:
   → 타일 오버레이 (서버가 점을 미리 그린 이미지 타일) ⭐ 히트맵/전국 분포에 최적
   → 또는 커스텀 렌더 레이어 1개에 배치 드로잉 (뷰 N개 → 레이어 1개)
"마커로 안 되면 오버레이/타일로 내려간다"는 사다리를 아는 게 depth 신호.
```

# L6 — 실시간 위치 스트리밍

## 폴링 → push 승격 사다리 (⭐ 처음부터 WebSocket이 정답이 아니다)

```
1단계  폴링 3~5s + 델타         구현·디버깅 쉬움, 프록시/재연결 이슈 없음 ⭐ 여기서 시작
2단계  적응 폴링                포그라운드/지도 노출 시만, 정지 시 백오프
3단계  WebSocket 뷰포트 구독    실시간성이 "요구사항"으로 올라올 때 승격
4단계  (필요시) 서버 델타 압축   좌표 델타 + 바이너리
```
> 🗝️ *"갱신 주기가 수 초 허용이면 폴링이 two-way door입니다. WebSocket은 재연결·백프레셔·프록시 문제를 영구히 안게 되므로, 실시간성이 명시 요구가 된 뒤에 도입합니다."*

## WebSocket으로 갈 때 프로토콜 설계

```
클라 → 서버:  {op:"subscribe", z:15, bbox:[...], filter:{...}, gen:7}
              팬/줌 시 gen 증가시켜 재구독 (이전 구독 자동 해지)
서버 → 클라:  {op:"snapshot", gen:7, vehicles:[...]}      첫 응답 = 전체
              {op:"delta",    gen:7, upd:[{id,lat,lon}], del:[id]}   이후 = 변경분

필수 장치:
  · gen 불일치 응답은 폐기 (팬 중 도착한 이전 구독 데이터)
  · 백그라운드 진입 → unsubscribe + 소켓 해제 ⭐ (안 하면 배터리 학살)
  · 재연결 = 지수백오프 + jitter, 복귀 시 snapshot부터 다시
  · 백프레셔: 서버 델타가 클라 처리보다 빠르면 coalesce(같은 id는 최신만 유지)
  · 하트비트로 죽은 연결 탐지 (모바일은 조용히 끊긴다)
```

# L7 — 위치 품질 (GPS는 거짓말을 한다)

## 원시 GPS의 3가지 거짓말

```
① 정확도 편차     horizontalAccuracy 5m ~ 수백 m. 실내·터널·고층빌딩 협곡에서 급락
② 점프           도심에서 갑자기 100m 밖으로 튀는 샘플 (멀티패스 반사)
③ 오래된 좌표     캐시된 fix가 즉시 배달됨 → timestamp가 수십 초 전
```

## 필터링 파이프라인 (내 위치 표시·트립 기록 공통)

```
① accuracy 게이트   horizontalAccuracy < 0 → 무효값이므로 버림
                    임계 초과(예 > 50m, 측정필요) → 표시엔 쓰되 기록엔 제외
② 신선도 게이트     timestamp가 현재로부터 오래됐으면 버림 (예 > 5s)
③ 속도 타당성       이전 좌표와의 거리 / 시간 = 속도.
                    물리적으로 불가능(예 300km/h)하면 이상치로 폐기 ⭐ 점프 제거의 핵심
④ 스무딩           이동 평균 또는 칼만 필터. 표시용은 스무딩, 기록용은 원본 보존 ⭐
⑤ (내비면) 맵 매칭  도로망에 스냅 (snap-to-road). 서버/SDK 기능 사용
```
> ⭐ **원본과 표시를 분리**하는 게 핵심: 스무딩한 좌표를 저장하면 요금 계산의 근거가 훼손된다. **저장은 원본, 표시는 가공.**

## 내 위치 마커의 heading 2종 구분

```
course (이동 방향)   GPS 연속 좌표에서 계산. 정지 시 무의미(값이 요동)
heading (기기 방향)  자기 나침반. 정지 상태에서도 유효, 실내 자기 간섭에 취약

→ 주행 중: course 사용 / 정지·도보: heading 사용 / 전환에 히스테리시스
   (안 하면 정지할 때마다 화살표가 팽이처럼 돈다)
```

# L8 — 거리 계산과 정렬

```
🅐 haversine (대권거리)   구면 정확. 정렬·필터에 충분. 계산 저렴
🅑 등장방형 근사          짧은 거리에서 haversine보다 더 저렴 (수천 건 정렬에 유효)
                          dx = Δlon × cos(평균위도) × R,  dy = Δlat × R
🅒 도로 거리 (경로 API)    실제 이동거리. ⚠️ 비용·지연 발생 → 목록 전체에 쓰지 않는다

실무 정책:
  목록 정렬·필터 → 🅐/🅑 직선거리 (수백 건 즉시 계산)
  상세 화면 1건  → 🅒 도로거리/ETA 1회 조회
  ⛔ 목록 20건마다 경로 API 호출 = 비용·지연 폭발
  ⚠️ 요금은 직선거리로 계산하지 않는다 (M5 — 서버가 실제 주행 경로로)
```
> 💬 *"직선거리와 실제 거리가 다르다는 걸 UI에서 속이지 않습니다. 목록에는 '직선 300m'로 표시하고, 상세에서 도보/주행 경로 기준을 별도로 보여줍니다. 왜냐하면 강 건너 200m가 실제로는 2km인 경우가 있기 때문입니다."*

# L9 — 권한과 프라이버시 (거부를 정상 경로로 설계)

```
권한 사다리:
  notDetermined → 요청 시점 선택 (⭐ 앱 첫 실행 즉시 요청 = 거부율 최악)
  whenInUse     → 대부분의 기능 가능 (지도·주변검색)
  always        → 트립 트래킹·지오펜스에 필요. 요청은 필요해진 순간에, 이유를 먼저 설명
  denied        → ⭐ 여기가 설계 대상. "지도 못 씀"이 아니라 degradation

정밀도 (iOS 14+):
  reducedAccuracy (근사 위치, 수 km) 가 기본일 수 있다 ⛔ "정확한 위치"를 가정하지 말 것
  → 근사 위치로도 동작하는 화면(지역 단위 차량 목록)과
    정밀 필요 화면(차량까지 걸어가기)을 분리하고, 후자에서만 일시적 정밀 권한 요청

degradation 설계 (거부 시):
  · 지도 중심을 마지막 알려진 위치 → 또는 지역 선택 UI로 대체
  · "내 주변" 대신 "지역 검색"을 1급 기능으로 노출
  · 권한 재요청 배너는 은근하게, 설정 앱 딥링크 제공
  ⛔ 권한 없으면 빈 화면 + 무한 스피너 = 최악
```

# L10 — 배터리 (이 도메인 최대 소비원)

```
소비 순위(일반적 경향):  상시 GPS > 화면·지도 렌더 > 네트워크 > CPU
   → 지도 화면은 이 셋을 동시에 켜는 화면이다 ⚠️

절감 레버 5개:

측정 방법 (실측 필요 — 추측 금지):
  · Xcode Energy/Instruments Location·Network 항목으로 시나리오별 비교
  · A/B: "주기 3s" vs "주기 10s" 를 동일 시나리오 30분 주행에서 배터리 % 비교
  · 면접에서는 "실측해서 정했다"까지만. 구체 수치를 지어내지 않는다 ⭐
```

# L11 — SDK 선택과 오프라인 지도

```
선택 축 (기능이 아니라 제약으로 고른다):
  · 국내 상세 지도 품질/주소 체계 (국내 서비스는 이게 결정적일 수 있음)

  · 번들 크기 · 개인정보 처리(SDK가 무엇을 전송하나) · 라이선스 제약(타일 캐시 허용 여부 ⚠️)

  ✅ 지도가 안 떠도 기능은 죽지 않게: 차량 목록·주소·전화는 지도와 독립 (graceful)
```

# 📐 냅킨 계산 — 지도판 (소리내어)

```
가정: 서울 뷰포트(z15, 약 1km²) 안 차량 200대 · 지도 화면 체류 5분 · 갱신 4s

첫 로드:  타일 8장 × 35KB     = 280KB
          차량 200 × 200B     = 40KB
                              ─────── 약 320KB
갱신:     델타(이동한 30대 × 40B) = 1.2KB / 4s
          5분 = 75회 × 1.2KB      = 90KB
팬 5회:   타일 마진 재요청 5 × 100KB = 500KB (캐시 히트로 절감 대상)
                              ───────
          5분 세션 총 ≈ 0.9MB   → 셀룰러 허용 범위 ✅

여기서 나오는 결정:
  · 델타가 전체 대비 3% → ⭐ 델타 전송이 최대 레버 (전체 재전송하면 75 × 40KB = 3MB)
  · 타일이 총량의 80%+ → ⭐ 타일 캐시가 두 번째 레버
  · 차량 메타는 병목 아님 → 목록 필드를 무리하게 줄일 필요 없음 (⭐ 안 할 최적화 판단)
```
> 🗝️ **"하지 않을 최적화"를 명시하는 게 시니어 신호.** 숫자로 우선순위를 정했다는 증거.

## ⭐ 발견 2 — 2단 폴리곤: active 안 && inactive 밖 (도넛 구조)

**사실:** 반납 가능 판정이 두 겹의 폴리곤 집합으로 구성된다.

```
   가능 = (point ∈ activeGeom 중 하나)  AND  (point ∉ inactiveGeom 전부)

   ┌───────────────────────────────┐
   │   activeGeom (서비스 가능)      │
   │     ┌──────────┐              │
   │     │inactive  │   🚗 A  ✅    │   A: active 안 · inactive 밖  → 가능
   │     │ (제외)   │              │
   │     │  🚗 B ❌ │              │   B: active 안이지만 inactive 안 → 불가
   │     └──────────┘              │
   └───────────────────────────────┘
        🚗 C ❌  active 밖 → 불가

   왜 두 겹인가: "구 단위로 크게 허용하되, 그 안의 특정 지역(공항·터널·사유지)은 제외"
   → 단일 폴리곤으로는 구멍을 표현할 수 없어서 집합 차집합으로 모델링
```

**설계 평가:**
```
✅ 좋은 점: 정책을 서버 GeoJSON으로 내려받음 → 구역 변경에 앱 배포 불필요
           (모빌리티 3원칙 ③ "임계값은 서버로" 를 이미 만족)
⚠️ 주의:   판정 순서가 성능을 결정한다. active를 먼저 걸러야
           대부분의 점이 1차에서 탈락 (short-circuit) — 실제 코드도 이 순서다 ✅
```

## ⭐ 발견 3 — GeoJSON 좌표 순서 함정 (실제 코드가 증거)

**사실:** 폴리곤 링을 만들 때 `coordinate[1]` → latitude, `coordinate[0]` → longitude 로 매핑한다.

```
   GeoJSON 표준 좌표 순서 =  [경도, 위도]   ( [lon, lat] )
   사람이 말하는 순서       =  "위도, 경도"   ( lat, lon )
                             ▲ 정반대 ⚠️

   뒤집으면 서울 (37.5, 127.0) 이 (127.0, 37.5) 가 된다
   → 위도 127° 는 존재하지 않는 값 (유효범위 ±90)
   → 라이브러리에 따라 throw 없이 그냥 "판정 false" 로 조용히 실패 ⛔
   → 증상: "반납 버튼이 아무 데서도 안 눌림" (에러 0건)
```

> 🗝️ **이건 `sd-b4`의 silent-nil과 같은 계열의 사고다.** 에러가 안 나고 기능만 조용히 죽는다.
> **방어:** 좌표 변환 지점을 한 함수로 모으고, 유효범위 단정(`assert(-90...90)`)을 넣는다. 그리고 파싱 라운드트립 테스트를 둔다.

## ⭐ 발견 4 — 판정 빈도가 진짜 병목 (개선 제안)

**사실(구조):** 판정은 `activeGeom` 폴리곤 배열을 순회하며 각각 point-in-polygon을 수행한다 → `O(폴리곤 수 × 정점 수)`.
**가설(미실측):** 카메라 이동/핀 드래그마다 호출되면 프레임 예산을 잡아먹을 수 있다. → **실측 필요**(Instruments Time Profiler로 판정 함수 비중).

```
개선 레버 4개 (비용 낮은 순):
① 이동 임계값 게이트     이전 판정 좌표에서 N m(예 3~5m) 미만 이동이면 재판정 스킵

④ 폴리곤 단순화         정점 수 감축(Douglas-Peucker)
   ⚠️ 마지막 수단. 반납 가능 판정은 정산·분쟁과 연결되므로 경계를 흐리면 위험.
      단순화하려면 "안전한 방향"으로만 (가능 구역을 축소하는 쪽) — 넓히면 사고
```

## ⭐ 발견 5 — 클라 판정 vs 서버 판정 (결제와 같은 구조)

**사실:** 판정이 클라에서 수행된다(위 코드). **가설:** 서버 최종 검증도 있을 것 — 확인 필요.

```
   클라 판정만 있으면?  → 조작 가능 + 지오메트리 버전 불일치 시 분쟁
   서버 판정만 있으면?  → 핀 드래그 중 실시간 피드백 불가 (왕복 지연)

   ✅ 정답은 둘 다, 역할 분리:
      클라 = 즉각 피드백(UX). "여기는 반납 불가" 실시간 표시
      서버 = 최종 진실. 실제 반납 처리 시 재검증 ⭐
      + 지오메트리 버전(geomVersion)을 요청에 동봉 → 불일치 시 갱신 유도
```
> 🗝️ **M5 요금과 완전히 같은 원칙이다:** *"클라 계산은 표시용, 서버가 진실."* 지도 구역 판정도 **돈과 연결되면 서버가 진실**이어야 한다. 이 원칙을 두 도메인에 걸쳐 말하면 일관된 설계 철학으로 들린다.

```
재확인:  git grep -cE "startUpdatingLocation" -- '*.swift'   → 13곳
        git grep -cE "stopUpdatingLocation"  -- '*.swift'   → 1곳
        git grep -nE "desiredAccuracy|distanceFilter" -- '*.swift'
```

**사실 3가지:**
```
① 거의 모든 호출부가  최고정확도 + 거리필터 없음  으로 설정한다
   → 가장 비싼 조합. "주변 차량 목록"에는 수십 m 정확도면 충분한데도 동일 설정
② start 13곳 : stop 1곳 — 켜는 곳은 많고 끄는 곳은 사실상 없다
③ 화면(VC)마다 위치 매니저를 개별 생성한다 → 전역 조율 주체가 없다
   분석 SDK들도 각자 위치 갱신을 켠다
```
> ⚠️ **정직 표기:** 이건 **구조적 리스크**이고, 실제 배터리 소모량은 **미실측**이다. 면접에서 "몇 % 개선했다"고 말하지 않는다. 대신 *"구조를 보면 끄는 경로가 없어서 실측을 먼저 했겠다"* 로 말한다.

**개선안 (L10의 원칙을 그대로 적용):**
```
   단일 LocationService (actor) ⭐
     ├ 구독 카운팅: 화면이 붙으면 +1, 떨어지면 −1, 0이 되면 stopUpdatingLocation
     ├ 정확도 프로파일: .coarse(목록·지도) / .fine(핀 드래그·반납 판정) / .navigation(주행)
     │  → 구독자들의 최대 요구치로 자동 승격, 요구가 사라지면 자동 강등
     ├ 백그라운드 진입 시 전면 중단
     └ 저전력 모드 시 프로파일 한 단계 강등
   + 위치 소스를 protocol로 (테스트에서 좌표 시퀀스 주입 — L12)
```
> 🗝️ **면접 서사:** *"위치는 켜는 코드가 13곳인데 끄는 코드가 1곳이었습니다. 그래서 저는 화면마다 매니저를 만드는 구조를 **구독 카운팅을 하는 단일 서비스**로 바꾸는 방향을 제안합니다. 마지막 구독자가 사라지면 자동으로 끄는 게 핵심입니다. 왜냐하면 개별 화면이 끄는 책임을 지는 구조는 화면이 늘어날 때마다 반드시 새는 곳이 생기기 때문입니다."*

## ⭐ 발견 8 — 근사 위치(reducedAccuracy) 대응은 있으나 degradation이 아니다

**사실:** `CLAccuracyAuthorization`을 관찰해서 `.reducedAccuracy`면 **권한 안내 화면**으로 유도하는 코드가 실제로 있다.

```
✅ 좋은 점: iOS 14+ 근사 위치를 인지하고 있다 (많은 앱이 이걸 놓친다)
⚠️ 갭:     대응이 "정밀 권한을 다시 달라"는 재요청뿐이다
           = L9가 말하는 degradation(근사 위치로도 되는 화면 분리)은 미구현
           → 유저가 계속 거부하면 진행이 막힌다

개선: 화면을 두 등급으로 분리
      근사로 충분  → 지역 단위 차량 목록·지도 개요 (그대로 동작)
      정밀 필요    → 반납 위치 판정·차량까지 도보 안내
                    → 이때만 일시적 정밀 권한 요청 + 거부 시 "지도에서 직접 지정" 대체 경로
```
