# 🏛️ A4+A8 — "MVVM 죽었나?" 논쟁 방어 + 레거시 전환·팀 설득

> **작성:** 2026-08-03 (세션8f) · **선행:** `arch-a2`(계층 격리) `arch-a3`(DI) `arch-a5`(Rx→Concurrency) `ios-01`(@Observable) `arch-a7`(네트워크)

> ⚠️ **익명화 규약** 적용.

# L1 — ⭐ 5축 번역표 (이 표 하나로 모든 아키텍처 질문에 대응)

| 축 | MVVM(+Coordinator) | TCA | **RIBs (내 경험)** |
|---|---|---|---|
| **상태 소유** | ViewModel이 화면 상태 보유 | Store 하나가 트리 전체 상태 | Interactor가 비즈니스 상태, Presenter가 표현 상태 |
| **이벤트 방향** | 양방향 바인딩 허용(느슨) | 단방향 강제 (Action→Reducer→State) | 단방향 지향 (Action→Interactor→PresentableState) |
| **DI** | 수동/컨테이너, 규율에 의존 | Dependency 클라이언트 주입 | **Builder 체인이 컴파일 타임에 강제** ⭐ |
| **화면 전환** | Coordinator (별도 개념, 누락 가능) | Reducer 안 상태로 표현 | **Router가 1급 시민** — 붙이고 떼는 게 구조 |
| **테스트 이음새** | protocol 주입 (개발자 재량) | Reducer가 순수 함수 → 최고 | Interactor를 Listener/Presentable mock으로 격리 |
| **모듈 경계** | 자유 | 자유 | **RIB 단위가 곧 모듈 경계에 매핑** |
| **러닝커브** | 낮음 | 높음 | **매우 높음** (보일러플레이트 최다) |

## 이 표에서 나오는 핵심 문장 3개

```
① "RIBs 는 MVVM + Coordinator 를 컴파일 타임에 강제한 버전에 가깝습니다."
   → Coordinator 를 '깜빡할 수 있는' MVVM 과 달리 Router 가 구조적으로 필수
② "TCA 와 RIBs 는 상태 소유 위치가 반대입니다."
   → TCA = 중앙 Store 하나 / RIBs = RIB 단위로 상태가 분산
③ "세 개 다 목적은 같습니다 — 상태 소유를 명확히 하고 단방향으로 흐르게 하는 것."
   → 이름 논쟁이 무의미해지는 지점
```

# L2 — "MVVM 죽었나?" 정면 답변

```
   ❌ "죽었습니다" (유행 따라가는 답)
   ❌ "아니요 여전히 좋습니다" (트렌드 모르는 답)
   ✅ 무엇이 죽고 무엇이 살았는지 구분한다
```

> **모범답안:** *"클래식 MVVM은 죽었다고 봅니다. `ObservableObject` + `@Published` 조합이 객체 단위로 변경 신호를 쏘기 때문에 과잉 렌더링이 구조적으로 발생합니다. 다만 죽은 건 그 **구현**이고 패턴 자체는 `@Observable`로 진화했습니다. 그리고 논쟁 자체가 단방향 데이터 흐름으로 수렴했다고 봅니다 — MVVM이든 TCA든 결국 '상태를 한 곳이 소유하고 이벤트는 한 방향으로 흐른다'는 같은 결론에 도달했습니다.
> 2026 프로덕션 기본값을 고른다면 저는 **@Observable 기반 MVVM + Coordinator + DI + SPM 모듈화**로 갑니다. 이유는 팀 확장성입니다. 러닝커브가 낮아서 새 팀원이 붙는 비용이 가장 작습니다."*

## 왜 `ObservableObject`가 구조적으로 과잉 렌더링인가 (꼬리질문 대비)
```
objectWillChange = 객체당 1개 · 인자 없는 신호
   → "이 객체의 뭔가가 바뀐다"만 전달, 어느 프로퍼티인지 모름
   → 구독한 모든 뷰가 무효화
@Observable = 매크로가 get/set 을 감싸 뷰가 접근한 keyPath 를 추적
   → 그 값이 바뀔 때만 무효화
비유: 📢 방송국(전체 공지) vs 🕸️ 의존성 그래프(관련자만)
```
> 상세는 `ios-01`. **이 설명을 못 하면 2026 기준 명시적 레드플래그**다.

## ✅ 정직하면서 강한 답변 (경험 없음을 판단력으로 전환)

> *"프로덕션에는 아직 도입하지 않았습니다. 최소 타깃이 iOS 17 미만이라 조건이 안 됐고, 그 시점에 저희 우선순위는 RxSwift 기반 화면을 SwiftUI로 옮기는 것이었습니다. 도입한다면 신규 화면부터 `@Observable`로 시작하고 기존 `ObservableObject`는 손대지 않습니다. 두 방식이 한 화면에 섞이는 게 가장 위험하기 때문입니다.
> 개념적으로는 차이를 알고 있습니다 — 구버전은 `objectWillChange`가 객체 단위 신호라서 구독한 뷰 전체가 무효화되고, `@Observable`은 매크로가 접근한 keyPath만 추적해서 정밀합니다. 그래서 제가 기대하는 이득은 리렌더 감소이고, 대가는 iOS 17 최소 타깃과 매크로 디버깅 난도입니다."*

```
이 답변의 구조 (경험 갭이 있는 모든 주제에 재사용 가능한 틀) ⭐
① 안 했다고 먼저 말한다        (숨기면 꼬리질문에서 무너진다)
② 왜 안 했는지 = 제약을 댄다    (게으름이 아니라 판단이었음)
③ 도입하면 어떻게 할지 말한다   (신규부터 / 섞지 않는다 = 마이그레이션 감각)
④ 개념은 정확히 설명한다        (모르는 게 아니라 안 쓴 것임을 증명)
⑤ 기대이득과 대가를 같이 말한다  (트레이드오프 습관)
```
> 🗝️ **이 5단 틀이 A4의 진짜 산출물이다.** TCA·SwiftData·Swift 6 등 "안 써본 최신 기술" 질문 전부에 적용된다.

# L4 — TCA는 언제 쓰나 (국소 적용 논리)

```
✅ 도입 정당한 곳:  상태 전이가 복잡하고 명세가 확실한 피처
                    예) 결제 플로우(M2 상태머신: held→paying→paid→…)
                        다단계 폼 · 예약 변경 플로우
                    → Reducer 가 순수 함수라 상태머신 테스트가 압도적으로 쉽다 ⭐
❌ 오버킬:          단순 목록/상세 화면. 상태가 "로딩/성공/실패" 3개뿐인 곳

대가 (반드시 같이 말한다)
  보일러플레이트 (Observation 으로 완화됨) · Reducer 순회 성능 ·
  double diffing · 러닝커브 · 팀 전체 학습 비용 ⭐ 가장 큰 실비용

⭐ 결정 기준 한 줄: "상태 전이 다이어그램을 그려야 하는 화면인가?"
   그려야 한다면 TCA 가 그 다이어그램을 코드로 강제해준다. 아니면 과잉.
```
> ⚠️ **부분 도입의 함정도 말해야 완성:** *"한 앱에 두 아키텍처가 공존하면 새 팀원이 화면마다 다른 규칙을 배워야 합니다. 그래서 국소 도입을 하려면 **경계를 문서화하고 '어떤 조건에서 TCA를 쓴다'는 기준을 팀 합의로 못 박아야** 합니다. 기준 없이 취향으로 섞이면 그게 최악입니다."*

# 💪 압박 방어 6종

### ① "MVVM 안 쓰셨으면 우리 코드베이스에 적응 가능하세요?"
> *"가능합니다. RIBs를 썼는데 RIBs는 MVVM에 Coordinator를 컴파일 타임에 강제한 형태에 가깝습니다. 상태 소유와 단방향 흐름, 그리고 화면 전환을 별도 객체가 책임진다는 개념은 동일합니다. 오히려 제가 적응할 부분은 **강제가 약해진 환경에서 규율을 스스로 지키는 것**이라고 봅니다. RIBs는 Builder 체인이 실수를 컴파일 에러로 잡아주는데, MVVM은 그걸 규약과 리뷰로 지켜야 하기 때문입니다."*
> 🗝️ 자기 경험의 **약점까지 말하는 것**이 신뢰를 만든다.

### ② "RIBs 쓰신 건 범용성이 없는 경험 아닌가요?"
> *"RIBs 자체는 특정 조직에 국한된 선택이라는 데 동의합니다. 다만 제가 얻은 건 프레임워크 사용법이 아니라 **모듈 경계를 컴파일 타임에 강제하면 무엇이 좋아지는지**에 대한 감각입니다. Builder 체인이 의존성 누락을 빌드 에러로 만들어주는 경험을 하면, DI 컨테이너를 런타임에 조립하는 방식이 왜 위험한지가 체감으로 남습니다. 그 판단 기준은 어떤 아키텍처에서도 씁니다."*

### ③ "TCA 도입하자는 팀원이 있으면 어떻게 하시겠어요?"
> *"먼저 어느 화면에 쓰려는지 묻습니다. 결제나 다단계 폼처럼 상태 전이 다이어그램을 그려야 하는 화면이면 저도 찬성합니다. Reducer가 순수 함수라 상태머신 테스트가 훨씬 쉬워집니다. 반대로 목록·상세처럼 상태가 세 개뿐인 화면이면 반대합니다. 그리고 도입하기로 하면 **'어떤 조건에서 TCA를 쓴다'는 기준을 먼저 팀 합의로 못 박습니다.** 기준 없이 취향으로 섞이는 게 아키텍처가 두 개인 것보다 나쁩니다."*

### ④ "@Observable 안 써보셨네요?" (레드플래그 방어)
> → L3의 5단 틀 그대로. **① 안 했다 → ② 제약 → ③ 도입 계획 → ④ 개념 설명 → ⑤ 이득·대가**

### ⑤ "전환을 왜 끝까지 안 하셨어요?"
> *"끝내지 않기로 한 결정입니다. 복잡한 Rx 스트림 조합과 핵심 결제·반납 플로우는 남겼습니다. 전환 이득보다 회귀 위험이 크기 때문입니다. 저는 전환에서 가장 중요한 게 **언제 멈출지를 미리 합의하는 것**이라고 봤습니다. 그게 없으면 전환이 끝나지 않는 프로젝트가 되고, 그 상태가 두 아키텍처 공존보다 훨씬 비쌉니다."*

### ⑥ "그래서 지금 다시 설계하면 뭘 고르시겠어요?"
> *"신규 앱이면 `@Observable` 기반 MVVM + Coordinator + SPM 모듈화로 갑니다. 러닝커브가 낮아 팀 확장 비용이 가장 작고, 플랫폼 방향과도 일치합니다. RIBs는 팀 규모가 크고 모듈 경계를 컴파일 타임에 강제해야 할 때만 고려합니다. TCA는 상태 전이가 복잡한 피처에 국소 적용합니다. 다만 어떤 선택이든 **'왜 이걸 골랐는지'를 문서로 남기는 게 프레임워크 선택보다 중요**하다고 봅니다. 사람은 바뀌고 코드는 남습니다."*

# 🔬 방법론 교훈 — 여러 줄 선언이 grep을 속인다

이 카드를 쓰면서 내 측정이 한 번 틀렸다. 박제할 가치가 있다.

```
1차 측정:  git grep ": Reactor" / ", Reactor"  →  2 파일  → "ReactorKit 거의 안 쓴다"❌
교차 검증: git grep "mutate(action" → 22 파일 · "Pulse" → 69 파일  → 모순 발견
원인:      제네릭 상위 클래스가 여러 줄로 걸쳐서 준수 선언이 단독 행에 있었다

   final class XInteractor: PresentableInteractor<
     ...여러 줄...
   >,
   Reactor {          ← 여기. ": Reactor" 도 ", Reactor" 도 매칭 안 됨

교훈 3개
① 줄 단위 grep 은 여러 줄 선언에 취약하다 → 심볼 사용(메서드명)으로 교차 검증
② "검색 0건 = 기능 부재"로 단정하지 않는다 (하네스 규칙과 동일)
③ 모순되는 두 신호가 나오면 그게 측정 오류 신호다 (import 45 vs 준수 2 = 모순)
```
> ⚠️ 그리고 `git grep -E` 에서 `\s`·`\b` 는 POSIX ERE 에 없어 조용히 오작동한다 — 여기서도 카운트가 0으로 나왔다. **측정 도구 자체를 의심하는 습관**이 이 카드의 부수 소득.
