# 🔴 오답 교정 — 카셰어링 앱은 주행 중 GPS를 기록하지 않는다

세션 7의 M3 요약에서 나는 이렇게 썼다: *"터널에서 GPS를 로컬 버퍼에 append-only로 쌓고 복귀 시 배치 업로드"*.
**실무 코드를 확인한 결과 이 앱은 그렇게 하지 않는다.** 그리고 그게 **더 나은 설계**다.

```
재확인:  git grep -nIiE "allowsBackgroundLocationUpdates" -- '*.swift'  → 0건
        git grep -nIiE "significantLocationChange"        -- '*.swift'  → 0건
        git grep -nIiE "mileage|주행거리"                  -- '*.swift'  → 서버 응답 DTO 에만 존재 ⭐
```

**사실:** `실제주행거리`는 **서버가 내려주는 응답 필드**다. 앱이 계산하지 않는다.

```
   ❌ 내가 가정했던 구조 (= 라이드헤일링/배달 앱 패턴)
   기사 폰 GPS ──► 로컬 버퍼 ──► 배치 업로드 ──► 서버가 거리 계산
   (폰이 유일한 센서라서 어쩔 수 없이 이렇게 한다)

   ✅ 카셰어링의 실제 구조
   차량 텔레매틱스 장치 ──► 서버 ──► 앱은 결과만 받는다
   (차에 이미 센서가 달려 있다. 폰을 쓸 이유가 없다)
```

## ⭐ 왜 차량이 측정하는 게 압도적으로 나은가 (5가지)

```
① 조작 불가        폰 GPS는 위치 스푸핑이 가능하다. 요금·정산의 근거를 조작 가능한
                  소스에 두면 안 된다 ⭐ (돈이 걸린 데이터의 제1원칙)
② 앱과 무관        유저가 앱을 지워도·폰이 죽어도·기내모드여도 주행은 기록된다
                  앱 의존이면 "앱 껐으니 요금 안 냄"이 가능해진다
③ 배터리 0         M1의 최대 소비원(상시 GPS)이 아예 발생하지 않는다
④ 정확도          차량은 오도미터·연료·시동 상태 같은 폰이 못 보는 신호를 갖는다
⑤ 다중 운전자      한 예약에 여러 사람이 번갈아 운전해도 차량 기준이면 일관된다
```

> 🗝️ **면접 결정타 (도메인 이해가 즉시 전달된다):**
> *"카셰어링에서 주행 데이터는 앱이 수집하지 않습니다. 차량 텔레매틱스가 수집하고 서버가 계산합니다. 왜냐하면 요금의 근거가 되는 데이터를 **사용자 기기라는 조작 가능한 소스**에 둘 수 없기 때문입니다. 앱이 GPS를 기록하는 건 기사 폰이 유일한 센서인 라이드헤일링이나 배달 앱의 패턴입니다. 차에 장치가 있으면 그걸 쓰는 게 맞습니다."*

## 그럼 앱의 위치 책임은 무엇인가 — 딱 하나다

```
   앱이 위치를 쓰는 목적 =  ⭐ "반납 시점에 여기가 반납 가능한 곳인가"

   즉 M1의 2단 폴리곤 구역 판정이 전부다.
   주행 추적이 아니라 순간 판정. 그래서:
     · 백그라운드 위치 권한 불필요 (whenInUse 로 충분)
     · 상시 갱신 불필요 (해당 화면에서만)
     · 정확도는 높아야 함 (구역 경계 판정이니까 — M1 L9의 "정밀 필요 화면")
```
> ⚠️ 단, M1 발견 7의 **`start` 13곳 : `stop` 1곳 비대칭은 여전히 유효한 문제**다. 주행 추적이 없다는 게 "위치를 안 켠다"는 뜻은 아니다. 지도·검색·반납 화면에서 최고정확도로 켜고 끄지 않는다.

## 📎 그럼 append-only = 공짜 CRDT 는 틀린 지식인가?

아니다. **개념은 유효하되 적용처가 다르다.**

```
✅ 유효한 적용처:  차량 → 서버 텔레매틱스 스트림 자체가 append-only 다
                  (지하주차장 통신 단절 → 재전송 → 중복 도착)
                  → 서버가 (차량ID, 시퀀스) 로 dedup 하면 합집합 병합으로 수렴
                  → 즉 CRDT 성질은 **서버 수신 계층**에서 쓰인다. 클라가 아니라.
❌ 틀린 적용처:   "앱이 GPS를 버퍼링한다" (카셰어링에는 해당 없음)
```

# L1 — 텔레매틱스 파이프라인의 실패 모드 (클라가 알아야 할 이유)

앱이 데이터를 만들지 않아도, **그 데이터가 늦거나 안 오는 상황을 UI가 처리해야 한다.**

```
   차량 ──[이동통신]──► 수집 서버 ──► 요금 엔진 ──► 앱 조회
          │
          └─ 실패 모드 4종
             ① 통신 단절     지하주차장·터널·산간 → 버퍼 후 나중에 전송
             ② 지연 도착     반납 직후 몇 분 뒤에야 최종 데이터 도착 ⭐
             ③ 순서 뒤바뀜   재전송분이 최신보다 늦게 도착
             ④ 유실          장치 고장·전원 차단 → 데이터 자체가 없음
```

## ⭐ ②번(지연 도착)이 UI 설계를 지배한다

```
   유저는 반납 버튼을 누른 직후 "얼마 나왔어?"를 보고 싶다
   그런데 최종 주행 데이터는 아직 서버에 안 왔을 수 있다

   ❌ 나이브: 반납 직후 요금 화면 → 데이터 없음 → 0원 또는 에러 또는 무한 스피너
   ✅ 3단 상태로 설계:
        ⏳ 집계 중     "주행 정보를 확인하고 있습니다" (예상 소요 안내)
        🟡 임시 확정   예상 요금 표시 + "최종 금액은 변동될 수 있습니다" 명시 ⭐
        ✅ 최종 확정   실제 주행 기준 확정 + breakdown + 영수증

   ⭐ 절대 하면 안 되는 것: 임시 금액을 "확정"처럼 보여주기
      → 나중에 금액이 바뀌면 유저는 "몰래 올렸다"고 인식한다 (신뢰 붕괴)
```

## ④번(유실) 대비 — 폴백 정책은 정책 문제다
```
   주행 데이터가 아예 없으면 요금을 어떻게 매기나?
   → 이건 기술이 아니라 정책 결정이다. 앱이 할 일은:
      · 확정 불가 상태를 정직하게 표시
      · 운영/CS 경로 노출
      · ⛔ 앱이 임의로 추정 금액을 청구하지 않는다
   🗝️ 면접 답변: "데이터가 없을 때 앱이 추정해서 청구하면 분쟁에서 이길 수 없습니다.
                 그래서 확정 불가를 명시적 상태로 두고 정책·운영으로 넘깁니다."
```

# L2 — ⭐ 구간별 주행거리 (실무 코드에서 발견한 도메인 핵심)

**사실:** 응답 DTO에 주행거리가 **하나가 아니라 여러 개**다.

```
   실제주행거리 (총합)
   ├ 구간1 실 주행거리
   ├ 구간2 실 주행거리
   └ 구간 외 실 주행거리     ⭐ "구간 외"가 따로 있다
```

## 이게 의미하는 것

```
   편도 서비스에서 요금은 "총 몇 km" 로 정해지지 않는다.
   ⭐ 어느 구간을 얼마나 달렸는지에 따라 단가가 다르다.

   예시 모델 (일반화):
     구간1 (출발지→중간 지정 지점)   단가 A  ← 예상 경로. 프로모션 대상일 수 있음
     구간2 (중간 지점→목적지)        단가 B
     구간 외 (지정 경로를 벗어난 주행) 단가 C  ← 보통 가장 비싸거나 별도 과금

   → 즉 요금 = Σ(구간별 거리 × 구간별 단가) + 기본요금 + 부가항목
```

## 여기서 나오는 3가지 설계 결과

```
① ⭐ 클라는 절대 요금을 계산할 수 없다
   구간 정의(지오메트리)·단가·구간 판정 규칙이 모두 서버 정책이다
   앱이 이걸 복제하면 정책 변경 때마다 앱 배포 = 비가역
   → M5의 "서버 단일 계산"이 선택이 아니라 **필연**임을 증명하는 근거 ⭐

② breakdown UI 를 서버 주도로 만들어야 한다
   구간 수가 2개일지 3개일지, "구간 외" 항목이 노출될지는 예약 유형에 따라 다르다
   → 앱이 항목을 하드코딩하면 새 요금 유형마다 앱 배포
   ✅ breakdown 배열을 그대로 리스트 렌더 (라벨·금액·부호를 서버가 결정)

③ "구간 외"는 UX가 민감하다
   유저는 자기가 경로를 벗어났다는 걸 모른 채 추가 요금을 본다
   → 주행 중 안내는 차량/내비 책임이지만, 사후 화면에서 **왜 이 금액인지**
     구간별로 분해해서 보여주는 게 분쟁을 줄인다 (breakdown의 진짜 목적)
```

> 🗝️ **면접 활용 (도메인 깊이 최고 지점):**
> *"요금이 총 주행거리 하나로 정해지지 않았습니다. 예상 경로 구간과 그걸 벗어난 구간의 단가가 달라서, 응답에 구간별 실주행거리가 따로 내려왔습니다. 그래서 클라가 요금을 계산하는 건 애초에 불가능했습니다. 구간 정의와 단가와 판정 규칙이 전부 서버 정책이기 때문입니다. 앱은 서버가 준 항목 배열을 그대로 렌더하는 역할만 했고, 저는 그게 맞는 분리라고 봅니다. 요금 정책은 앱보다 훨씬 자주 바뀌는데 앱 배포는 되돌릴 수 없기 때문입니다."*

# L3 — 요금 확정 시퀀스 (M2 hold→capture와 맞물리는 지점)

```
   예약 시점                주행 중              반납 직후            최종
   ────────                ──────              ────────            ────
   예상 요금 quote          (앱은 관여 X)        임시 집계            확정 요금
   → hold(승인)                                 → 표시만            → capture(매입)
      금액 = 예상                                  "변동 가능"          금액 = 실제
        │                                                              │
        └──────────────── 이 간극이 미납·부분취소의 원인 ─────────────────┘

   실제 < 예상  →  부분 매입 (차액 hold 해제)
   실제 > 예상  →  추가 결제 시도 → 실패하면 미납 채권 (M2 L6)
   확정 불가    →  ⭐ capture 보류 + 정책/운영 (임의 추정 청구 ⛔)
```

## quote(예상 요금)의 수명 관리
```
   quote 는 스냅샷이다 → 조건이 바뀌면 무효화해야 한다
   무효화 트리거: 대여 시간 변경 · 차량 변경 · 반납 장소 변경 ⭐ · 쿠폰 적용/해제
   → 반납 장소가 바뀌면 구간 정의가 바뀌므로 요금이 바뀐다 (편도의 핵심)
   ✅ quote 에 TTL + quoteId + policyVersion → 결제 시 서버가 재검증, 만료면 재확인 UI
   ⛔ 화면에 남아있던 오래된 quote 로 결제 진행 = 금액 불일치 CS
```

# L4 — 반납(return) 시퀀스 심층 ⭐ 되돌릴 수 없는 작업

**사실(코드 확인):** 반납 위치 유형이 여러 가지이고(차고지 / 자유 구역 / 지정 장소), 반납 위치 **변경** 경로가 유형별로 따로 있다. 반납 전 확인 항목(차량 상태·사진 등)도 별도로 존재한다.

```
   반납 플로우
   ① 현재 위치 취득 (정밀 필요)
   ② ⭐ 반납 가능 구역 판정 (M1 2단 폴리곤)
   ③ 반납 유형 분기 (차고지 / 자유구역 / 지정장소) — 유형별 규칙·요금이 다르다
   ④ 사전 확인 (차량 상태·사진·연료 등)
   ⑤ ⛔ 반납 처리 (one-way door — 되돌릴 수 없다)
   ⑥ 요금 집계 대기 → 확정
```

## ⭐ ⑤가 one-way door 라는 게 설계를 바꾼다

```
   반납은 취소가 안 된다 (차 문이 잠기고 예약이 종료된다)
   → 그래서 결제와 같은 등급의 방어가 필요하다:

   ⛔ optimistic 금지        "반납 완료"를 먼저 보여주면 안 된다 (M2와 동일 원칙)
   ✅ ack 확인 필수          서버·차량이 실제로 처리했다는 응답까지
   ✅ 멱등성                 반납 요청 재시도가 이중 처리되지 않아야 함 (반납 멱등키)
   ✅ 확인 단계              돌이킬 수 없음을 유저에게 명시 (체크리스트 UX)
   ✅ 실패 시 명확한 상태     "반납되지 않았습니다 + 차량은 아직 대여 중입니다"
                            ⛔ 애매한 실패 = 유저가 차를 두고 떠남 → 계속 과금 → 최악 사고
```
> 🗝️ **면접 결정타:** *"반납은 결제와 같은 등급으로 취급했습니다. 되돌릴 수 없고, 실패했는데 성공한 것처럼 보이면 유저가 차를 두고 떠나서 계속 과금됩니다. 그래서 optimistic을 쓰지 않고, 차량과 서버의 확인 응답까지 받은 뒤에만 완료로 표시합니다."*

## 반납 장소 변경이 왜 어려운가
```
   반납 장소 변경 = 요금 재계산 + 구역 재판정 + (편도면) 구간 정의 변경
   → 단순 "주소 바꾸기"가 아니라 예약 조건 변경이다
   → quote 무효화 + 재승인(hold) 필요할 수 있음
   ✅ 그래서 유형별로 별도 플로우가 있는 게 합리적이다 (코드가 그렇게 돼 있다)
```

```
파이프라인 지연 (앱이 못 고쳐도 반드시 계측해야 하는 것) ⭐
   · 반납 → 임시 집계까지 지연 p50/p95
   · 반납 → 최종 확정까지 지연 p50/p95
   · 확정 불가(데이터 유실) 발생률
   · 임시 금액 → 최종 금액 변동폭 분포 ⭐ (변동이 크면 예상 요금 로직 문제)

요금 정합성
   · 표시 금액 ≠ 청구 금액 발생 건수 (0이어야 함 — 아니면 P0)
   · quote 만료 후 결제 시도율 (높으면 TTL·UX 문제)
   · "구간 외" 요금 발생률 + CS 문의 연관도

⚠️ 로그에 정확한 좌표·주행 경로를 남길 때 개인정보 취급 주의 (위치는 민감정보)
```

# 💪 압박 방어 5종

### ① "주행 거리를 앱에서 GPS로 측정하면 안 되나요?"
> *"기술적으로는 가능하지만 저는 반대합니다. 왜냐하면 **요금의 근거가 되는 데이터를 사용자 기기에 두면 안 되기** 때문입니다. 위치 스푸핑이 가능하고, 앱을 지우거나 폰이 꺼지면 데이터가 사라집니다. 게다가 상시 GPS는 배터리 최대 소비원입니다. 차량에 이미 텔레매틱스 장치가 있으면 그쪽이 조작 불가하고 앱과 독립적이며 오도미터 같은 더 정확한 신호도 갖습니다. 앱이 GPS를 기록하는 건 기사 폰이 유일한 센서인 라이드헤일링 패턴입니다."*

### ② "반납 직후에 요금이 안 나오면 유저가 답답할 텐데요?"
> *"그래서 상태를 세 단계로 나눕니다. 집계 중, 임시 확정, 최종 확정입니다. 임시 단계에서 예상 금액을 보여주되 **변동 가능함을 명시**합니다. 제가 절대 안 하는 건 임시 금액을 확정처럼 보여주는 것입니다. 나중에 금액이 바뀌면 유저는 몰래 올렸다고 인식하고, 그건 지연보다 훨씬 비싼 대가입니다."*

### ③ "요금 계산을 클라에서 하면 서버 부하도 줄고 빠를 텐데요?"
> *"이 도메인에서는 애초에 불가능했습니다. 요금이 총 주행거리 하나로 정해지지 않고 예상 경로 구간과 벗어난 구간의 단가가 달랐습니다. 구간 정의 지오메트리와 단가와 판정 규칙이 전부 서버 정책입니다. 앱이 이걸 복제하면 정책이 바뀔 때마다 앱을 배포해야 하는데 **앱 배포는 비가역**이라 구버전 유저가 영구히 남습니다. 그래서 앱은 서버가 준 항목 배열을 렌더만 합니다."*

### ④ "텔레매틱스 데이터가 아예 안 오면요?"
> *"확정 불가를 명시적 상태로 두고 정책·운영으로 넘깁니다. 앱이 임의로 추정해서 청구하면 분쟁에서 이길 근거가 없습니다. 대신 앱이 할 일은 세 가지입니다. 상태를 정직하게 표시하고, CS 경로를 노출하고, 그리고 이 상황의 발생률을 **계측**해서 장치·통신 문제로 에스컬레이션하는 것입니다."*

### ⑤ "반납 버튼을 눌렀는데 네트워크가 끊기면요?"
> *"가장 위험한 시나리오입니다. 반납은 되돌릴 수 없는 작업인데 결과를 모르는 상태가 되기 때문입니다. 결제와 완전히 같은 구조로 방어합니다. 반납 요청에 멱등키를 붙여 재시도가 이중 처리되지 않게 하고, optimistic으로 완료를 먼저 표시하지 않고, 실패했을 때는 **'반납되지 않았습니다. 차량은 아직 대여 중입니다'** 라고 명확히 알립니다. 애매하게 실패하면 유저가 차를 두고 떠나서 계속 과금되는 최악의 사고가 납니다. 그리고 앱 복귀 시 예약 상태를 서버에 다시 조회합니다."*

## 🗣️ 표현 코칭
**"~합니다. 왜냐하면 ~입니다."** 이 카드는 특히 **"누가 측정하고 누가 계산하나"** 라는 한 문장 프레임으로 시작하면 강하다.

**박제 한 줄:** *카셰어링의 주행·요금 = **차량이 측정하고 서버가 계산하고 앱은 렌더한다.** 이유는 요금 근거를 조작 가능한 기기에 두지 않기 때문. 요금은 총거리가 아니라 **구간별 거리 × 구간별 단가**라 클라 계산이 원천적으로 불가능. 반납은 **결제와 같은 등급의 one-way door**(멱등키 + ack + optimistic 금지). 지연은 **집계중 / 임시(변동 명시) / 최종** 3단으로 정직하게.*
