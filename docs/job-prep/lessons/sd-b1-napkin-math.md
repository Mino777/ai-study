# 🅱️ SD 카드 B1 — 모바일 규모추정 냅킨 계산 (+ 이미지 디코딩 배율)

> **왜:** 모바일 SD 초반 10분을 지배하는 스킬. "규모=서버 QPS 아님"이 감별점.
> **최초 학습:** 2026-07-28 (세션6) · **상태:** 프레임+계산 실습 완료 · **복습:** `REVIEW.md`

---

## 🧠 "규모"의 정의가 다르다
```
백엔드 SD                    모바일 SD
"QPS 얼마? DB 몇 TB?"        "사용자 1명당 자원 예산 얼마?"
서버를 몇 대 늘릴까            한 디바이스에서 어떻게 버틸까
```
🔑 모바일은 **스케일 아웃 불가**(아이폰 1대가 전부) → 추정 목적이 인프라 사이징이 아니라 **자원 예산 배분**.

## 📏 기준값 5개 (계산 재료)
```
① 메모리 예산   앱 ~200~500MB (초과 시 OS가 킬 = jetsam)
② 디스크 캐시   이미지 ~200~400MB + LRU 상한
③ 페이지 크기   피드 한 페이지 20~50 아이템
④ 요청 크기     API 응답 1개 < ~1MB
⑤ 전력         네트워크 = 로컬 연산의 ~100배 ⚡
```

## 🧮 실전: 이미지 피드 계산
```
Step 1 아이템 1개
  메타(JSON) 1~2KB  /  이미지(1080px JPEG) 200~500KB
  → 이미지가 메타의 ~200배 (병목이 즉시 드러남)

Step 2 한 페이지(20개)
  메타 40KB (가벼움) / 이미지 6MB (무거움)
  → 결정: 메타·이미지 분리 로드 (텍스트 먼저 렌더 → 이미지 lazy)

Step 3 세션 누적(10페이지=200개)
  메타 400KB (메모리 보유 OK)
  이미지 압축 60MB
  ⚠️ 디코딩 비트맵: 장당 4.5MB × 200 = 900MB → 앱 즉사(jetsam)
  → 결정: 화면 밖 해제 + 메모리 캐시 용량 상한 + LRU(NSCache)

Step 4 대역폭·배터리
  60MB 다운로드 → WiFi 여부로 프리페치 조절, 1~2페이지만(전력 100배)
```

## 🎯 계산 → 설계 결정 번역 (여기가 점수)
```
이미지가 메타의 200배      → 메타/이미지 분리 로드
디코딩 4.5MB/장           → 메모리 캐시 상한 + LRU + 화면밖 해제
페이지 20개 × 6MB         → cursor 페이지네이션(offset 아님)
누적 60MB                 → 디스크 캐시 300MB로 재방문 흡수
네트워크 100x 전력         → 프리페치 1~2페이지, WiFi 적응
```

## 🖼️ 핵심 지식: 왜 300KB JPEG가 메모리에서 4.5MB인가 ⭐

**JPEG는 "그림"이 아니라 "그림을 만드는 압축 레시피".** 화면에 그리려면 픽셀로 펼쳐야(디코딩) 함.
```
1080 × 1080 = 1,166,400 픽셀
픽셀당 RGBA 4 bytes
→ 1,166,400 × 4 ≈ 4.5 MB
```
🔑 **비트맵 크기는 파일 용량과 무관 — 오직 해상도(픽셀 수)로 결정.**
```
품질 100% 파일 2MB   → 디코딩 4.5MB
품질 30%  파일 100KB → 디코딩 4.5MB  (똑같음!)
압축을 세게 해도 메모리 점유는 동일 💥
```

### 캐시 설계 시사점
```
① 2계층 분리
   디스크 = 압축 상태(300KB) → 300MB에 ~1000장
   메모리 = 디코딩 상태(4.5MB) → 100MB에 ~20장 (200배 차이!)
② 메모리 상한은 "장수" 아니라 "총 바이트"
   "50장까지" ❌ → "총 50MB까지" ✅ (NSCache totalCostLimit에 비트맵 크기를 cost로)
③ 다운샘플링이 최강 최적화 ⭐
   100×100 자리에 1080×1080 디코딩 = 4.5MB 낭비
   표시 크기로 디코딩 = 100×100×4 = 40KB → ~100배 절감
   (ImageIO thumbnail 옵션 / Kingfisher·SDWebImage downsampling)
```

🗣️ **면접 멘트:** "압축 파일 용량과 메모리 점유는 다릅니다. 비트맵은 해상도×4바이트로 정해져서 JPEG를 300KB로 압축해도 디코딩하면 4.5MB입니다. 그래서 **디스크는 압축 상태, 메모리는 디코딩 상태**로 캐시를 분리하고, 메모리 상한은 장수가 아니라 **총 바이트(cost)**로 걸고, 무엇보다 **표시 크기에 맞춰 다운샘플링**해서 디코딩합니다."

## ✅ 냅킨 계산 4스텝 (모든 SD 문제 재사용)
```
① 아이템 1개 무게 쪼개기 (메타 vs 미디어 → 병목 드러남)
② × 페이지 크기 = 한 요청 무게
③ × 세션 누적 = 메모리·디스크 압박 (⚠️ 디코딩 배율 잊지 말기)
④ 각 숫자를 설계 결정으로 번역  ← 점수 구간
```

**박제 한 줄:** *모바일 규모추정 = QPS 아닌 per-user 자원예산. 아이템→페이지→세션→결정번역. 이미지는 메타의 ~200배, 디코딩하면 해상도×4B(4.5MB/장, 파일크기 무관). → 디스크=압축/메모리=디코딩 분리, cost 기반 상한, 다운샘플링.*
