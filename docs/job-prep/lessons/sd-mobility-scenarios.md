# 🚗 SD 모빌리티 도메인 시나리오 뱅크 (M1~M6)

> **신설:** 2026-07-29 (세션7) · **선행:** `sd-b1`(냅킨) `sd-b2`(피드·SSOT) `sd-b4`(충돌·오프라인) `ios-05`(로컬 저장소)
> **왜 신설:** B1~B10 사다리는 SNS/이커머스 편향. **내 실무 도메인(모빌리티·카셰어링)이 뱅크에 0개**였다.
> Reverse SD("네가 만든 걸 설명하라")가 빈번해진 2026 트렌드에서, **내 도메인이 최강 무기**다.
> 남들은 이미지 피드를 외워서 온다. 나는 **지도·결제·차량제어를 실제로 만들어봤다.**

## 🧭 모빌리티 SD가 SNS SD와 다른 점 (이 표가 도메인 depth 신호)

| 축 | SNS/피드 SD | **모빌리티 SD** |
|---|---|---|
| 데이터 성격 | 컨텐츠(불변·캐시 친화) | **실세계 상태**(차량 위치·예약 점유) — 초 단위로 변하고 캐시하면 거짓말 |
| 오류의 대가 | 피드 새로고침 | **돈이 잘못 빠지거나, 유저가 차 앞에서 발이 묶인다** |
| 위치 | 없음 | **1급 시민** — 배터리 최대 소비원 |
| 결제 | 있으면 부가 | **핵심 경로** — 멱등성·이중결제·정산 정합성 |
| optimistic UI | 좋아요 = 권장 | **결제·차량제어 = 금지 구역** ⭐ |
| 오프라인 | 열람 편의 | **지하주차장·터널에서 반드시 동작해야** |
| 동시성 | 유저별 독립 | **차량 1대를 여러 유저가 경쟁**(점유 충돌) |
| 규제 | 없음 | 위치정보 동의 · 결제 규정 · 주행 중 UI 제약 |

> **한 줄:** *"모빌리티 앱은 컨텐츠 소비자가 아니라, **실세계의 물리적 자원을 예약·점유·제어하는 분산 시스템의 노드**."*

## 📐 per-user 자원예산 — 모빌리티판 기준값

```
뷰포트 내 차량 마커        200~500대 (그 이상은 클러스터링 강제)
차량 1대 메타              ~200B (id·좌표·모델·연료·요금) → 500대 = 100KB
위치 갱신 주기             지도 화면 3~10s · 주행 트래킹 1~5s
GPS 포인트 1개             ~40B (lat·lon·ts·speed·accuracy)
주행 2시간 @1s 샘플        7,200 포인트 ≈ 288KB → 배칭 필수
지도 타일 1장              20~50KB · 화면당 6~12장
상시 GPS 소비              앱 전체 배터리의 최대 단일 항목 (네트워크보다 위)
```
> 🗝️ **"서버 QPS"로 답하면 백엔드 답변.** 모빌리티는 **per-user 자원예산 + 배터리**로 답한다.

# 🗺️ M1 — "지도에 주변 차량을 실시간으로 표시하세요" (도메인 최빈출)

> 📖 **초심층 확장판: [`sd-m1-map-deep.md`](./sd-m1-map-deep.md)** — L0 좌표계/투영 → L12 관측까지 13층 + **실무 코드 대조 8건**(2단 폴리곤 구역판정 · GeoJSON `[lon,lat]` 함정 · 위치 start13:stop1 · God object 1,800줄). 아래는 요약이다.

## ① 스코핑 질문
```
차량 규모(전국 몇 대? 뷰포트 최대 몇 대?) · 실시간성(초 단위? 수 초 허용?)
· 지도 SDK 제약(MapKit? 서드파티?) · 오프라인 지도 필요? · 필터(차종·연료·요금) 있나?
```

## ② 기능 / ③ 비기능
```
✅ 뷰포트 내 차량 마커 · 팬/줌 시 갱신 · 차량 탭 → 상세 · 필터
❌ 경로안내(내비) · 실시간 교통 · AR   ← 명시 배제

비기능: 팬/줌 60fps · 갱신 수 초 허용(eventual) · 배터리 보수적 · 지하/터널 graceful
```

## ⭐ 핵심 난제 3개
```
🅐 마커 수천 개        → 클러스터링 (어디서 할 것인가?)
🅑 팬/줌마다 쿼리      → debounce + bbox 캐시 (안 하면 요청 폭발)
🅒 위치 갱신 vs 배터리 → 폴링 주기 적응
```

### 🅐 클러스터링을 어디서? (⭐ 감별점)
```
클라 클러스터링                     서버 클러스터링
─────────────────────────          ─────────────────────────
전체 차량 받아서 클라가 묶음         서버가 zoom별 집계해서 클러스터만 내려줌
✅ 줌 반응 즉각(왕복 없음)           ✅ 페이로드 작다 (전국 = 클러스터 20개)
✅ 필터 즉시 재계산                  ✅ 클라 CPU/메모리 절약
❌ 전국 5만 대 받으면 사망 ⛔        ❌ 줌마다 왕복 · 필터 조합마다 서버 계산

결정: 하이브리드 ⭐
  낮은 줌(전국·시도) → 서버 집계 클러스터 (개별 차량 의미 없음)
  높은 줌(동네)      → bbox 개별 차량 + 클라 클러스터링 (필터 즉응)
  경계 줌 레벨을 서버 설정값으로 → 앱 배포 없이 조정 (앱은 비가역!)
```
> **레드플래그:** *"전체 차량 목록 받아서 클라에서 필터"* — 규모 감각 없음으로 즉시 감점.

### 🅑 뷰포트 쿼리 설계
```
GET /vehicles?bbox=<minLat,minLon,maxLat,maxLon>&zoom=15&filter=...
   → { vehicles: [...], clusters: [...], ttl: 5 }

· 팬/줌 debounce 300~500ms (드래그 중 매 프레임 요청 금지)
· bbox를 격자(geohash/quadtree)로 스냅 → 캐시 히트율 ↑ (미세 이동에 재요청 X)
· 이전 bbox 포함되면 요청 스킵
· 응답 ttl로 클라 캐시 수명 서버가 제어
```

### 🅒 갱신 주기 적응
```
지도 보고 있음 + 포그라운드 → 3~5s 델타 폴링 (또는 WebSocket 델타 push)
지도 안 봄 / 백그라운드      → 중단 ⭐
정지 상태(팬 없음) 오래       → 주기 늘림 (백오프)
델타만: {id, lat, lon} 변경분 (전체 재전송 금지)
```

## ⑦ 마커 렌더링 = 셀 재사용과 같은 문제 (`ios-04` 재활용)
```
❌ 매 갱신마다 마커 전부 remove/add → 깜빡임 + GC 폭발 + 60fps 붕괴
✅ diff 적용: 신규만 add · 사라진 것만 remove · 남은 것은 좌표만 애니메이션
✅ 마커 뷰 재사용 풀 (MKAnnotationView dequeue) — 셀 재사용과 동일
✅ 아이콘은 사전 렌더 이미지 캐시 (매번 그리면 프레임 드랍)
```
> 🗝️ **연결 결정타:** *"마커 갱신은 테이블뷰 셀 재사용과 같은 문제입니다. 왜냐하면 재사용되는 뷰에 비동기 결과가 도착하기 때문입니다. 그래서 마커에도 식별자 일치 검증을 넣습니다."*

## ⑨ 트레이드오프
```
실시간성 ↔ 배터리/대역폭     (주기 적응 + 델타 + 백그라운드 중단)
클라 클러스터링(유연) ↔ 서버(가벼움)   → 줌 경계로 하이브리드
지도 타일 캐시 ↔ 저장공간     (오프라인 지도는 명시적 다운로드 기능으로)
정확한 위치 ↔ 프라이버시      (동의·정밀도 등급)
```

## 💪 압박 방어 — "그냥 WebSocket으로 전 차량 실시간 스트리밍하면 안 되나요?"
> *"연결은 되지만 비용 구조가 안 맞습니다. 왜냐하면 유저가 보는 건 뷰포트 안 200대인데 전국 수만 대의 갱신을 받는 건 대역폭과 배터리를 그냥 태우는 것이기 때문입니다. 그래서 저는 **구독 범위를 뷰포트로 제한**합니다. 팬하면 구독 bbox를 갱신하고, 백그라운드로 가면 구독을 끊습니다. 그리고 초기에는 폴링으로 시작해도 됩니다 — 갱신 주기가 수 초 허용이라면 폴링이 구현·디버깅이 쉽고 two-way door입니다. 실시간성이 요구사항으로 올라오면 WebSocket으로 승격합니다."*

# 💳 M2 — "차량 예약과 결제 플로우를 설계하세요" (⭐ 도메인 핵심·최고 난도)

> 📖 **초심층 확장판: [`sd-m2-payment-deep.md`](./sd-m2-payment-deep.md)** — exactly-once 불가능 · 멱등키 계약 6조 · 실패 3분류(**모호**) · **hold→capture 2단** · **웹뷰 결제 아키텍처**(내 실무 구조) · 미납 게이트 + **실무 코드 대조 4건**. 아래는 요약이다.

## ⭐ 이 시나리오의 심장

```
   유저 탭 ──► 앱 ──► 우리 서버 ──► PG(외부)
                 ①        ②           ③

   ② 나 ③에서 응답이 끊기면? "결제가 됐는지 우리도 모른다"
   → 유저가 재시도하면 이중결제. 안 하면 돈만 빠지고 예약 없음.
```

> **모바일 SD에서 "네트워크 끊김"은 로딩 스피너 문제가 아니라 **돈 문제**다.**

## ① 스코핑
```
결제수단(카드 등록형? 간편결제? 후불?) · 예약과 결제가 동시인가 분리인가(hold → 정산)
· 취소/환불 범위 · PG는 웹뷰인가 SDK인가 · 부분 결제/추가 요금 있나
```

## ② 기능 / ③ 비기능
```
✅ 차량 선택 → 시간 선택 → 요금 확인 → 결제 → 예약 확정
❌ 쿠폰 발급 · 정기권 · 기업 정산   ← 배제

비기능: 이중결제 0 · 앱 강제종료/네트워크 끊김에서 복구 · 금액은 서버가 진실 · 감사 로그
```

## ④ 상태머신 (⭐ 이걸 그리면 시니어)

```
   draft ──► held ──────► paying ──────► paid ──► active ──► completed
             (차량점유)      │              │
             │               │ 실패         │
             │               ▼              │
             │            payFailed          │
             ▼               │               ▼
          expired ◄──────────┘           cancelled ──► refunded
        (hold 만료·보상)

   ⭐ held = 차량 점유(다른 유저 못 잡게). TTL 필수 (예 10분).
      TTL 없으면 결제 이탈한 유저가 차량을 영구 점유 = 재고 사망
   ⭐ paying = 우리도 결과를 모르는 구간 → 이 상태가 존재한다는 것 자체가 설계 포인트
```

## ⑤ API 계약 — 멱등성이 전부

```
POST /reservations           Idempotency-Key: <클라 UUID>  → { reservationId, state: held, expiresAt }
POST /reservations/{id}/pay  Idempotency-Key: <클라 UUID>  → { state, paymentId, receipt }
GET  /reservations/{id}                                    → 현재 상태 (⭐ reconcile용)
GET  /payments/pending                                     → ⭐ "미확정 결제" 조회

⭐ Idempotency-Key 규칙: 재시도할 때 **같은 키를 쓴다**
   → 새 UUID를 만들면 멱등성이 무의미. 이게 실무 최다 버그.
   → 키는 "결제 시도 1건"에 묶여 로컬DB에 저장 후 재시도마다 재사용
```

## ⭐ Deep Dive 🅐 — 이중결제 방지 4중 방어

```
1층  클라 UI 락        결제 버튼 즉시 비활성 + 진행 중 재진입 차단 (최약 방어, 이것만 믿으면 안 됨)
2층  Idempotency-Key   재시도 = 같은 키 → 서버가 첫 결과를 그대로 반환 ⭐ 핵심
3층  서버 상태머신      paying/paid 상태에서 새 결제 요청 거부 (상태 기반 방어)
4층  reconcile         앱 시작/포그라운드마다 GET /payments/pending → 미확정 결제 정리 ⭐ 감별점
```

### 🅑 앱이 죽어도 복구 — reconcile 루틴
```
결제 시작 직전에 로컬DB에 기록:  {reservationId, idempotencyKey, state: attempting, startedAt}

앱 재시작 / 포그라운드 진입 시:
  ① 로컬에 attempting 인 결제 있나?
  ② 있으면 GET /reservations/{id} 로 서버 진실 조회
  ③ paid  → 로컬 정리 + 예약 화면으로 (유저에게 "완료됐습니다")
     failed→ 로컬 정리 + 재시도 안내
     paying→ 폴링 (PG 결과 대기 중) + "확인 중" UI
  ④ 절대 임의로 재결제하지 않는다 ⛔
```
> 🗝️ **이 루틴을 말하면 "결제 실무 해봤다"가 즉시 증명된다.** 대부분 여기까지 안 간다.

### 🅒 PG 웹뷰 이탈 / 백그라운딩 (모바일 특화)
```
PG 웹뷰에서 유저가 뒤로가기 · 앱 스위치 · 전화 수신 → 결제 결과를 앱이 못 받음
❌ "웹뷰 콜백"만 신뢰 → 콜백 유실 시 영구 미확정
✅ 이중화: 웹뷰 콜백(빠른 경로) + 서버 webhook(신뢰 경로) + 클라 폴링(안전망)
✅ 앱 복귀 시 항상 서버에 상태를 되묻는다 (콜백을 진실로 삼지 않음)
```

### 🅓 부분 실패 = 보상 트랜잭션
```
차량 hold 성공 → 결제 실패    → hold 해제 (보상). 안 하면 차량 재고 잠김
결제 성공 → 예약 확정 실패     → 자동 환불 or 운영 알림 (돈만 빠진 최악 케이스)
→ 모바일 클라가 분산 트랜잭션의 한 참여자라는 자각이 있어야 한다
```

## ⑨ 트레이드오프 + ⭐ optimistic 금지 구역

```
⛔ 결제·차량제어에는 optimistic update를 쓰지 않는다
   좋아요는 틀려도 롤백하면 되지만, "결제 완료"를 먼저 보여주고 실패하면
   유저는 이미 차로 걸어가고 있다. 신뢰가 깨지는 방향이 비대칭이다.

   좋아요  = optimistic (낙관)   실패 비용 낮음
   결제    = pessimistic (비관)  실패 비용 = 돈·신뢰
   차량제어 = pessimistic + ack 확인 필수
```
> 🗝️ **이 비대칭을 스스로 말하는 게 시니어 신호.** B2에서 optimistic을 옹호했던 사람이 여기서 금지한다면 = 패턴을 종교로 안 믿는다는 증거.

```
hold TTL 짧게(재고 회전) ↔ 길게(결제 여유)  → 10분 + 서버 설정값
클라 금액 계산(빠른 UX) ↔ 서버 계산(정합성) → 서버가 진실, 클라는 표시만 (M5)
```
**one-way vs two-way door:** *"멱등키를 어디서 만들고 어디에 저장하느냐는 프로토콜 계약이라 나중에 바꾸면 서버·앱 동시 배포가 필요합니다(one-way door). hold TTL 값이나 폴링 주기는 서버 설정으로 빼두면 two-way door입니다."*

## 💪 압박 방어 — "재시도하면 그만이잖아요, 뭐가 어렵죠?"
> *"재시도 자체는 쉽습니다. 어려운 건 **재시도해도 안전한가**입니다. 왜냐하면 첫 요청이 서버에 도착했는지 앱은 알 수 없기 때문입니다. 응답만 유실됐을 수도 있습니다. 그래서 멱등키를 클라가 만들어 재시도마다 같은 키를 보내고, 서버는 같은 키에 대해 첫 결과를 그대로 반환합니다. 그리고 앱이 죽어서 재시도조차 못 한 경우를 위해 포그라운드마다 미확정 결제를 조회하는 reconcile 루틴을 둡니다. 결제에서 제가 가장 경계하는 건 실패가 아니라 **결과를 모르는 상태**입니다."*

# 📍 M3 — "주행 중 트립 트래킹을 설계하세요" (오프라인 × 배터리 정점)

> 🔴 **2026-08-03 오답 교정 — 아래 M3 내용은 *라이드헤일링/배달* 앱 패턴이다. 카셰어링에는 해당하지 않는다.**
> 실무 코드 확인 결과: **백그라운드 위치 추적 코드 0건**, `주행거리`는 **서버 응답 필드**다.
> 즉 카셰어링은 **차량 텔레매틱스가 측정 → 서버가 계산 → 앱은 렌더**한다. 앱은 주행 중 GPS를 기록하지 않는다.
> 이유: 요금 근거 데이터를 **조작 가능한 사용자 기기**에 두지 않는다 (+ 배터리 0 + 앱 독립).
> 📖 **교정판이자 초심층: [`sd-m3-m5-telemetry-fare-deep.md`](./sd-m3-m5-telemetry-fare-deep.md)**
> — 측정 주체 3안 비교 · 텔레매틱스 실패 4모드 · **구간별 주행거리**(구간1/구간2/구간 외) · 요금 3단 상태 · **반납 = one-way door**
>
> ⬇️ 아래는 **"기사 폰이 유일한 센서인 도메인"에서는 여전히 정답**이므로 대조 학습용으로 남긴다.
> (`append-only = 공짜 CRDT` 개념도 유효하다. 단 적용처가 클라 버퍼가 아니라 **서버 수신 계층의 dedup**이다.)

## ⭐ 심장: 터널·지하주차장에서 네트워크가 없는데 기록은 계속돼야 한다

```
   출발 ────────────[터널 15분]────────────► 도착
        네트워크 O      네트워크 X            네트워크 O
        │               │                     │
        └─ 실시간 업로드  └─ 로컬 버퍼 적재 ⭐  └─ 배치 업로드 + 요금 확정
```

## ⭐ 핵심 설계: append-only 버퍼 = 충돌이 원천적으로 없다 (B4 연결)
```
GPS 포인트는 수정되지 않는다 → append-only
→ 병합이 "합집합"이면 교환·결합·멱등 성립 → CRDT 성질 자동 만족 ⭐
→ 즉 트립 트래킹은 CRDT를 몰라도 CRDT다. 재전송·중복 전달에 안전.
   (단, 중복 제거를 위해 포인트마다 결정적 ID: tripId + sequence)
```
> 🗝️ **B4에서 배운 걸 여기 꽂으면 도메인 연결력 만점:** *"노트앱은 같은 필드를 여러 replica가 수정해서 CRDT가 필요했지만, 트립 로그는 append-only라 합집합 병합만으로 수렴합니다. 그래서 오프라인 동기화 난도가 훨씬 낮습니다."*

## ④ 로컬 스키마 + 업로드

```
TripPoint: tripId · sequence(⭐결정적 ID) · lat · lon · ts · speed · accuracy · uploaded(Bool)
```

```
✅ 클라 계산은 "예상 요금 표시용", 서버가 원본 포인트로 재계산해 확정 ⭐
✅ 클라와 서버 결과가 다르면 서버가 진실 + 차이 로깅(관측)
```

# 🔐 M4 — "차량 문 열기/닫기(스마트키)를 설계하세요" (실패의 대가가 최대)

## ⭐ 심장: 지하주차장에서 네트워크가 없는데 문은 열려야 한다

```
   앱 ──① 서버 경로 ──► 서버 ──► 차량 통신모듈(텔레매틱스)
      └─② BLE 직결 ────────────► 차량

   ① 정확·감사로그 O, 네트워크 필수 (지하 = 실패)
   ② 네트워크 불필요, 근거리만, 키 프로비저닝·보안 부담

   → 이중 경로 + fallback 사다리 ⭐
```

## 설계 결정
```
경로 선택: 근거리 + BLE 사용가능 → BLE 우선 (지연 짧고 지하 동작)
           그 외 → 서버 경로
           둘 다 실패 → 명확한 실패 UI + 고객센터 경로 (⛔ 조용한 실패 금지)

⛔ optimistic 금지: "열렸습니다" 먼저 보여주고 실패하면 유저는 차 앞에서 발이 묶인다
✅ ack 필수: 차량이 실제 수행했다는 응답까지 받고 성공 표시. 타임아웃 명시(예 10s)
✅ 진행 중 UI: "차량과 통신 중" — 무한 스피너 금지, 남은 시간/재시도 버튼
```

## 명령 멱등성 (⭐ 재미있는 지점)
```
"문 열기" 두 번 = 이미 열린 문 → 안전 (멱등)
"문 닫기" 두 번 = 안전
그러나 "토글" 명령은 ⛔ 절대 금지 — 재시도 시 상태가 반전된다
→ 명령은 항상 **목표 상태 지정형**(lock/unlock), 토글형 아님 ⭐
```
> 🗝️ 이 한 줄이 분산 시스템 감각을 증명한다: *"재시도가 존재하는 시스템에서 토글 명령은 설계 결함입니다. 왜냐하면 재시도가 상태를 반전시키기 때문입니다."*

## 보안
```
키 프로비저닝: 예약 확정 시 시간제한 키 발급 (예약 시간 + 여유분만 유효)
replay 방지: nonce/challenge-response (같은 패킷 재전송으로 문 열림 방지)
키 저장: Keychain (⛔ UserDefaults — ios-05 사고 패턴)
탈옥/무결성: 탐지 시 정책 결정 (차단 or 서버 경로 강제)
예약 종료/취소 시 키 즉시 무효화 (서버 + 로컬 폐기)
```

## 🔬 실무 코드 대조 — BLE 스마트키 (2026-08-03 확인)

> 사내 카셰어링 iOS 앱의 BLE 모듈을 직접 확인. **익명화 규약**: 와이어 프로토콜 상수·바이트 레이아웃·키 파생 방식은 의도적으로 제외하고 **설계 패턴만** 남긴다.

### ⭐ 발견 1 — 타임아웃이 3단으로 분리되어 있다

```
   scan 타임아웃        차량을 못 찾는 경우      "주변에 차가 없습니다"
   connection 타임아웃  찾았지만 연결 실패       "연결에 실패했습니다"
   write 타임아웃       연결됐지만 응답 없음     "차량이 응답하지 않습니다"

   ⭐ 왜 분리가 중요한가: 실패 원인이 다르면 유저에게 줄 다음 행동이 다르다
      scan 실패    → "차량에 더 가까이 가주세요"
      connect 실패 → "블루투스를 껐다 켜보세요"
      write 실패   → "서버 경로로 다시 시도" (fallback 사다리 진입) ⭐

   ⛔ 단일 타임아웃이면 전부 "실패했습니다" → 유저가 뭘 해야 할지 모른다
```
> 🗝️ **면접 활용:** *"BLE는 실패 지점이 스캔·연결·쓰기로 나뉩니다. 그래서 타임아웃도 세 개로 분리했습니다. 왜냐하면 실패 원인마다 유저에게 안내할 다음 행동이 다르기 때문입니다."* → "타임아웃 넣었습니다"보다 훨씬 깊게 들린다.

### ⭐ 발견 2 — 핸드셰이크가 예약 번호에 바인딩된다

**사실(패턴):** 핸드셰이크 단계에서 **예약 식별자 + 기기 공개키 + 그 서명**을 함께 차량에 제시한다.

```
   의미:  이 키는 "이 사람"의 키가 아니라 ⭐ "이 예약"의 키다
   → 예약이 끝나면 자동으로 무효 (별도 폐기 명령 없이도 권한 소멸)
   → 키 유출 피해 범위가 그 예약 하나로 한정된다 (blast radius 축소)
   → 세션7에서 내가 예측한 "예약 확정 시 시간제한 키 발급"과 실제 구조가 일치 ✅
```

### ⭐ 발견 3 — 핸드셰이크는 평문, 명령은 암호문 (단계별 보안 등급)

```
   1단계 핸드셰이크:  평문 (아직 공유 키가 없으므로) + 공개키 서명으로 신원 증명
   2단계 명령 전송:   암호문 + 매 전송마다 IV 동봉 ⭐

   ⭐ IV를 매번 새로 보내는 이유: 같은 명령("문 열기")이 항상 같은 암호문이 되면
      공격자가 그 패킷을 녹음해서 재전송할 수 있다 (replay)
      → IV가 매번 다르면 암호문도 매번 달라져 단순 재전송 방어에 기여
```

### ⭐ 발견 4 — 프레이밍 + 체크섬을 직접 구현했다

**사실(패턴):** 패킷이 `시작 바이트 → 길이 → 타입 → 페이로드 → 체크섬 → 종료 바이트` 구조다.

```
   왜 필요한가: BLE는 "메시지"가 아니라 "바이트 스트림"에 가깝다
     · 한 write가 쪼개져 도착할 수 있고(fragmentation)
     · 두 메시지가 붙어 도착할 수도 있다
   → 시작/종료 바이트로 경계를 찾고, 길이로 완성 여부를 판단하고,
     체크섬으로 손상을 검출한다 = 사실상 미니 프로토콜 계층을 직접 만든 것

   🗝️ 면접에서: "BLE 위에 프레이밍과 무결성 검증을 직접 얹어야 했습니다.
                BLE는 메시지 경계를 보장하지 않기 때문입니다."
                → 저수준 통신 경험으로 강하게 어필되는 지점
```

### ❓ 미확인 (면접에서 단정 금지)

```
· 명령 재시도 정책 (같은 명령 재전송 시 차량 측 멱등 처리 여부)
· 서버 경로 ↔ BLE 경로 자동 전환(fallback) 로직의 존재 여부  ⭐ 확인 가치 높음
· 명령이 목표상태형(lock/unlock)인지 토글형인지  ⭐ 가장 궁금한 지점
· 탈옥/무결성 검사 유무
→ "제가 직접 만든 부분이 아니라 확인이 필요합니다"가 정직한 답
```

## 💪 압박 방어 — "그냥 서버 API 한 방이면 되는데 BLE까지 왜?"
> *"실패 지점이 유저에게 가장 잔인한 곳에 있기 때문입니다. 차량은 대부분 지하주차장에 있고 거기엔 신호가 없습니다. 서버 경로만 있으면 유저는 차 앞에 서서 아무것도 못 합니다. 그래서 근거리에서는 네트워크에 의존하지 않는 경로를 하나 더 둡니다. 대가는 키 프로비저닝과 replay 방지 같은 보안 부담, 그리고 BLE 상태머신의 복잡도입니다. 그래서 **BLE를 기본이 아니라 fallback 사다리의 한 단으로** 둡니다. 평시엔 서버 경로로 감사 로그를 남기고, 네트워크가 없을 때만 BLE로 내려갑니다."*

# 💰 M5 — "요금 계산·정산 정합성" (CS 폭탄 방지)

> 📖 **초심층 확장판: [`sd-m3-m5-telemetry-fare-deep.md`](./sd-m3-m5-telemetry-fare-deep.md)** — ⭐**구간별 거리 × 구간별 단가**라 클라 계산이 원천적으로 불가능하다는 실무 근거 · quote 수명 관리 · 임시→최종 3단 상태 · 반납 시퀀스. M3와 같은 파이프라인이라 합쳐서 다룬다.

## ⭐ 심장: 앱에 보인 금액 ≠ 실제 청구 금액 = 신뢰 붕괴

```
   ❌ 클라가 요금 로직 보유
      → 요금 정책 바뀌면 앱 배포 필요 (앱 배포는 비가역! ARCH-SD)
      → 구버전 앱 유저는 영원히 옛 요금 표시 → CS 폭탄

   ✅ 서버가 계산, 클라는 서버가 준 breakdown을 렌더만 ⭐
      → 정책 변경 = 서버 배포 (two-way door)
```

## 설계
```
GET /reservations/{id}/quote → {
   total, currency,
   breakdown: [ {label:"기본요금", amount:...}, {label:"주행요금", amount:...},
                {label:"보험", ...}, {label:"할인", amount:-...} ],
   policyVersion: "2026-07-01"      ⭐ 어떤 정책으로 계산됐는지
}
클라는 breakdown 배열을 그대로 리스트 렌더 → 항목이 추가돼도 앱 수정 불필요 ⭐
```
> 🗝️ **서버 주도 UI(server-driven breakdown)** 가 여기서 정당한 이유: 요금 항목은 정책이고, 정책은 앱보다 빨리 바뀐다.

```
예상 요금 캐시 무효화: 시간 변경·차량 변경·쿠폰 적용 시 재조회 (오래된 quote로 결제 금지)
quote 유효시간(TTL) + 결제 시 서버가 재검증 → 만료면 재확인 UI
할인/쿠폰 중복: 서버가 단일 판정 (클라에서 합산 시도 금지)
감사: policyVersion + quoteId를 결제에 동봉 → 사후 정산 분쟁 추적 가능
```

## 💪 압박 방어 — "예상 요금 정도는 클라에서 계산해도 되지 않나요?"
> *"표시용으로는 가능하지만 저는 그것도 서버 quote로 받는 걸 선호합니다. 왜냐하면 클라에 요금 로직이 한 줄이라도 생기면 **정책 변경이 앱 배포에 묶이기** 때문입니다. 앱 배포는 되돌릴 수 없고 구버전 유저는 남습니다. 그래서 요금은 서버가 계산하고 클라는 breakdown을 렌더만 합니다. 다만 네트워크 없이 대략치를 보여줘야 하는 화면이 있다면, 서버가 내려준 요금표를 캐시해서 계산하고 **'예상'임을 명시**하고 결제 시점에 반드시 서버 값으로 재확인합니다."*
