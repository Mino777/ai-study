# 🏛️ 아키텍처 카드 A3 — DI 방어 (생성자 주입 → 언제 컨테이너?)

> **왜:** `QUESTION-BANK` ⭐"의존성 주입으로 테스트 가능성 향상" 단골 + 실무 강점(RIBs·POP) 서사화.
> **최초 학습:** 2026-07-28 (세션6) · **상태:** 방어 완성(추상화 과잉 압박 방어 포함)

## 🎯 질문의 함정
```
"DI 어떻게 하세요? 어떤 프레임워크?"
❌ 바로 도구 이름 대기 → 도구는 결론이지 근거가 아님
✅ 원칙 → 도구 순서: "프레임워크 전에 생성자 주입으로 충분한지 먼저 봅니다"
```

## 1. DI의 목적 3개 (우선순위)
```
① 테스트 가능성  가짜(mock)를 끼워넣을 이음새(seam) ← 가장 중요
② 결합도 낮춤    구체 타입 대신 추상에 의존 = 의존성 역전(DIP)
③ 조립 지점 분리  "무엇을 쓸지" 결정을 조립부 한 곳으로
```
DI 없으면 `let repo = FeedRepository()` — 내부 생성 = 강결합 → 실제 네트워크를 타야만 테스트 가능(느리고 불안정).

## 2. 3가지 방식
```
생성자 주입 ⭐ 기본  init(repo: Repo)
  ✅ 컴파일타임 안전(안 넣으면 컴파일 에러) ✅ 의존성이 시그니처에 드러나 숨을 수 없음
  → 90%는 이걸로 충분
프로퍼티 주입  var repo: Repo!  ⚠️ 암묵적 언래핑 → 런타임 크래시 위험 (Storyboard VC 등 init 못 건드릴 때만)
메서드 주입    func load(with repo: Repo)  → 일회성 의존
```

## 3. 언제 컨테이너를 도입하나 (핵심 질문)
```
생성자 주입으로 버티기 어려워지는 순간:
🔺 조립 지옥 — VC→VM→UseCase→Repo→APIClient→Session 7단 수동 조립 × 화면 50개
🔺 스코프 관리 — 앱 전체 1개 / 화면당 1개 / 매번 새로
🔺 순환 의존 탐지 필요
```
**도구 선택 (컴파일타임 안전 우선):**
```
Factory              작은~중간 팀 · 컴파일타임 안전 · 경량 (기본 추천)
Needle               대형 · 컴파일타임 DI 그래프 검증 (침습적이나 가장 안전)
swift-dependencies   TCA 생태계
Swinject             ⚠️ 런타임 해결 → 등록 깜빡해도 컴파일 통과, 런타임 크래시
```
🗣️ **결정타:** *"저는 **컴파일 타임에 검증되는 것**을 우선합니다. 런타임 컨테이너는 등록을 깜빡해도 컴파일이 통과하고 런타임에 터집니다. DI의 목적이 안전성인데 안전성을 런타임으로 미루는 건 모순입니다."*

## 4. 4틀 서사
```
① 상황  모듈 50개 규모, 화면마다 다단 수동 조립 → 조립 코드 비대·보일러플레이트 반복
② 결정  Protocol 추상화 + 생성자 주입 기본, 조립은 Factory/Builder에 모아 컴파일타임 안전 유지
③ 트레이드오프  얻음=mock 주입(테스트 속도·안정성)+모듈 경계 명확
               비용=보일러플레이트·protocol 증가·조립부 복잡도
④ 방어(mitigation) ⭐
   보일러플레이트 → 코드젠/템플릿으로 흡수
   protocol 폭발  → 진짜 교체·테스트 필요한 경계만 (전부 X)
   조립부 복잡    → 모듈별 Factory로 분할, 계층 경계에만 배치
```

## 5. 테스트와의 연결
```
Repository를 추상화 → 테스트에서 Mock 주입 → 네트워크 없이 UseCase 로직만 검증(빠름·결정적)
async mock도 가능(즉시 반환) · side effect는 값으로 반환해 검증(호출 flag 대신 결과를 봄)
```

## 💪 압박 방어 — "프로토콜 만들면 파일 두 배, 추적도 어려운데 가치 있나?"

> ⚠️ **무조건 옹호 금지**(레드플래그). "맞습니다"로 인정하고 시작 → 기준선을 제시.

**핵심 프레이밍 ⭐:** *보일러플레이트의 진짜 비용은 **양이 아니라 예측 불가능성**. 팀이 합의한 패턴으로 통일되면 양이 많아도 읽는 비용은 낮다.* (비용을 없앤 게 아니라 **일관성으로 인지비용을 상쇄**)

**protocol만이 유일한 이음새가 아니다 (한 단계 위):**
```
· Protocol Witness — protocol 대신 "클로저를 담은 struct"로 주입
  → 프로토콜 파일 폭발 없이 mock 생성 (실무 무기)
· 클로저 주입 — 의존 1~2개면 init(fetch: @escaping () async -> [Post])
· 코드젠(Sourcery/매크로) — 보일러플레이트를 사람이 안 씀
```

**🎤 최종 답안:**
> "맞습니다. 저도 무조건적인 추상화는 지양합니다. 저희는 RIBs를 쓰다 보니 프로토콜 지향이 강제되는데 실제로 보일러플레이트가 많고 코드 점핑도 잦습니다.
> 다만 **보일러플레이트의 진짜 비용은 양이 아니라 예측 불가능성**이라고 봅니다. 팀이 합의한 패턴으로 통일돼 있으면 코드량이 많아도 항상 같은 자리에 같은 골격이 있어서 읽는 비용이 낮습니다. 컴파일 단계에서 구조가 강제되니 실수도 줄고, DI로 Mock·Stub을 주입할 수 있어 자연스럽게 테스트 가능한 코드가 됩니다.
> 그래서 기준은 — **확장성만을 위한 추상화는 지양하고, 테스트 이음새가 필요한 경계에만** 만듭니다. 그리고 protocol이 유일한 수단도 아닙니다. 의존이 하나둘이면 클로저 주입으로 충분하고, mock 보일러플레이트가 부담되면 **Protocol Witness**처럼 클로저를 담은 struct로 이음새를 만들 수도 있습니다. 목적은 테스트 이음새 확보이고 protocol은 수단 중 하나입니다."

> 🗝️ 유저 자력 도출(2026-07-28): "**팀원끼리 합의된 추상화 → 항상 예측 가능한 코드**" — 추상화의 가치를 유연성이 아니라 **예측 가능성(convention)**으로 재정의. 대규모 팀 경험자 시그널 👏

**박제 한 줄:** *기본은 생성자 주입(컴파일타임 안전·시그니처에 드러남). 조립지옥·스코프 생기면 컨테이너 도입하되 컴파일타임 검증되는 것(Factory/Needle) 우선 — 런타임 컨테이너는 DI 목적을 런타임으로 미루는 모순. protocol은 테스트 이음새 필요한 경계에만, 그리고 유일한 수단도 아님(Protocol Witness·클로저).*
