# 🔐 M4 — 차량 제어 (스마트키)

## 🎯 심장

```
   앱 ──① 서버 경로 ──► 서버 ──► 차량 통신모듈
      └─② BLE 직결 ──────────────► 차량

   차량은 대부분 지하주차장에 있다 = ① 이 실패하는 곳
   → ②가 없으면 유저는 차 앞에 서서 아무것도 못 한다
```

> 🗝️ **오프닝:** *"차량 제어에서 제가 가장 신경 쓴 건 성공 경로가 아니라 **실패했을 때 유저가 어디에 서 있는지**였습니다. 차 앞에 서 있는 사람에게 '실패했습니다'는 답이 아니기 때문입니다."*

## L0 — 명령 설계: 목표상태형 vs 토글 (⭐ 코드로 검증됨)

**사실:** 실제 명령 체계가 **목표상태 지정형**이다. `Lock` / `Unlock` 각각 별도 명령으로 존재하고, 토글 명령은 없다.

```
   ✅ 목표상태형:  lock  /  unlock       "이 상태로 만들어라"
   ⛔ 토글형:      toggleDoor           "지금 상태를 반대로"

   왜 토글이 결함인가:
     재시도가 존재하는 시스템에서 토글은 재시도할 때마다 상태가 반전된다
     응답이 유실됐을 때 → 재시도 → 문이 다시 잠긴다 → 유저는 열렸다고 믿고 떠난다
```
> 세션 7에서 *"토글은 설계 결함"* 이라고 예측했고, 실제 코드가 목표상태형이었다. ✅
> 🗝️ *"재시도가 존재하는 시스템에서 토글 명령은 설계 결함입니다. 왜냐하면 재시도가 상태를 반전시키기 때문입니다."*

## ⭐ 그런데 모든 명령이 멱등한 건 아니다 (여기가 진짜 깊이)

명령을 **부작용 성격**으로 분류하면 재시도 정책이 갈린다.

```
   ┌─ 상태 지정형 (자연 멱등) ─────────────────────────────┐
   │  잠금 / 잠금해제                                       │
   │  두 번 보내도 결과 동일 → ✅ 자동 재시도 안전            │
   └───────────────────────────────────────────────────────┘
   ┌─ 단방향 상태 변경 (사실상 멱등) ───────────────────────┐
   │  트렁크 열기 (열기만 존재 — 닫기는 사람이 물리적으로)     │
   │  이미 열려 있어도 "열림"이 목표 → ✅ 재시도 안전          │
   └───────────────────────────────────────────────────────┘
   ┌─ ⚠️ 이벤트형 (비멱등) ────────────────────────────────┐
   │  경적 / 비상등 (차 찾기용)                              │
   │  두 번 보내면 두 번 울린다 → ⛔ 자동 재시도 금지          │
   │  → 응답 없어도 재시도하지 않고 "다시 울리기" 버튼을 준다   │
   └───────────────────────────────────────────────────────┘
```
> 🗝️ **면접 결정타 (거의 아무도 여기까지 안 간다):** *"제어 명령을 재시도 정책 기준으로 세 종류로 나눴습니다. 잠금·해제는 목표 상태라 자연히 멱등해서 자동 재시도가 안전합니다. 트렁크 열기도 단방향이라 안전합니다. 반면 경적은 두 번 보내면 두 번 울리는 이벤트라 멱등하지 않습니다. 그래서 경적은 응답이 없어도 자동 재시도하지 않고 유저가 다시 누르게 합니다. **멱등성은 명령마다 다릅니다.**"*

## L1 — 이중 경로와 fallback 사다리

```
   경로 선택 판단
   ┌──────────────────────────────────────────────┐
   │ 근거리 + BLE 사용가능 + 유효 키 보유           │ → BLE 우선
   │   · 지하에서도 동작 · 지연 짧음                │
   │ 그 외 (원거리 / BLE 불가 / 키 없음)            │ → 서버 경로
   │   · 감사 로그 남음 · 원격 가능                 │
   └──────────────────────────────────────────────┘

   실패 사다리 (각 단에서 유저에게 줄 다음 행동이 다르다)
   ① BLE 스캔 실패      → "차량에 더 가까이 가주세요"
   ② BLE 연결 실패      → "블루투스를 껐다 켜보세요" + 서버 경로 시도
   ③ BLE 전송 실패      → 서버 경로로 폴백
   ④ 서버 경로도 실패   → ⛔ 조용히 실패 금지. 명확한 실패 + 고객센터/비상 연락 경로
```

## ⚠️ 이중 경로의 숨은 비용 (말해야 균형 잡힌 답변)
```
· 두 경로의 결과가 엇갈릴 수 있다 (BLE로 열렸는데 서버는 모름) → 상태 동기화 문제
· 감사 로그가 BLE 경로에서 누락될 수 있다 → 사후 분쟁 추적 곤란
  → 완화: BLE 성공 후 서버에 사후 보고(best-effort) + 차량이 서버에 직접 보고
· BLE 상태머신 복잡도 + 기기·OS별 편차 → 테스트 비용
  → 그래서 BLE를 "기본"이 아니라 **사다리의 한 단**으로 둔다
```

## L2 — BLE 생명주기와 단계별 에러 분리 (⭐ 실무 코드 검증)

**사실:** 콜백이 단계별로 완전히 분리되어 있고, **에러 타입도 단계마다 별도 타입**이다.

```
   초기화 ──► 스캔 ──► 연결 ──► 쓰기 ──► 수신
     │         │        │        │        │
   초기화     스캔      연결     쓰기     응답
   에러타입   실패      상태     에러타입  메시지
     └─────────┴────────┴────────┴─── 각각 별도 콜백 + 별도 타임아웃 타이머

   타임아웃도 3종 분리: 스캔 / 연결 / 쓰기
```

**왜 분리가 중요한가:** 실패 원인마다 유저에게 줄 안내가 다르다. 단일 타임아웃·단일 에러면 전부 "실패했습니다"가 되어 유저가 다음 행동을 모른다.

## ⭐⭐ 가장 중요한 발견 — "전송 성공"과 "수행 완료"는 다른 이벤트다

```
   onWriteSuccess(command)     ← 패킷이 차량에 "전달"됐다
   onReceiveMessage(response)  ← 차량이 실제로 "수행"했다는 응답

   이 둘이 별개 콜백이다 ⭐

   ❌ 흔한 버그: write 성공에서 "문이 열렸습니다" 표시
      → 전달만 됐고 차량이 거부했거나(예약 만료·시동 중) 실패했을 수 있다
   ✅ 올바른 완료 판정: 응답 메시지에서 성공 코드를 확인한 뒤 표시
```
> 🗝️ **이게 M2의 "ack 필수"가 실제로 무슨 뜻인지 보여주는 구체 사례다.**
> *"BLE에서 write 성공은 전송 성공일 뿐이고 차량이 수행했다는 뜻이 아닙니다. 그래서 완료 판정은 write 콜백이 아니라 차량 응답 메시지로 합니다. 이 구분이 없으면 '보냈으니 됐다'고 잘못 표시하게 됩니다."*

## L3 — BLE 위에 프로토콜 계층을 직접 만들어야 하는 이유

**사실:** 프레임 조립(builder) · 응답 파싱(parser) · 패킷 관리(manager) · 프레임 타입 · 프로토콜 상수 · 바이트 유틸이 **각각 별도 파일로 분리**되어 있다.

```
   BLE가 주는 것:      바이트 덩어리 (메시지 경계 보장 X)
   우리가 만들어야 하는 것:
     · 프레이밍       시작/종료 마커로 메시지 경계 찾기
     · 길이 필드      완성 여부 판단 (한 write가 쪼개져 도착 = fragmentation)
     · 체크섬         손상 검출
     · 타입 코드      명령/응답 구분
     · 조립 버퍼      두 메시지가 붙어 도착하는 경우 분리

   → 사실상 미니 전송 프로토콜을 직접 구현한 것
```
> 🗝️ *"BLE는 메시지 단위가 아니라 바이트 스트림에 가깝습니다. 한 번의 write가 쪼개져 도착하거나 두 메시지가 붙어 도착할 수 있습니다. 그래서 프레이밍과 길이 필드, 체크섬을 직접 얹어야 했습니다."* → **저수준 통신 경험**으로 강하게 어필되는 지점.

## L4 — 보안 (스마트키의 본질)

```
① 예약 바인딩 ⭐
   핸드셰이크에 예약 식별자 + 기기 공개키 + 서명을 함께 제시
   → 키가 "사람"의 키가 아니라 "이 예약"의 키
   → 예약 종료 시 자동 무효 (별도 폐기 명령 없이 권한 소멸)
   → 유출 피해 범위가 그 예약 하나로 한정 (blast radius 축소)

② 단계별 보안 등급
   핸드셰이크 = 평문 (아직 공유 키가 없음) + 공개키 서명으로 신원 증명
   명령 전송   = 암호문 + 매 전송마다 IV 동봉
   → 같은 명령이 항상 같은 암호문이면 녹음 후 재전송(replay)이 가능
   → IV가 매번 다르면 암호문도 달라져 단순 재전송 방어에 기여

③ 키 저장
   Keychain (⛔ UserDefaults — ios-05 사고 패턴)
   예약 종료·취소 시 로컬 키 즉시 폐기

④ 무결성
   탈옥/디버거 탐지 시 정책 결정 (차단 or 서버 경로 강제)
   ⚠️ 우리 코드에서 확인 못 함 → 면접에서 단정 금지
```

⛔ optimistic 금지        "열렸습니다"를 먼저 보여주면 안 된다 (M2·반납과 동일)

✅ 비멱등 명령은 수동 재시도  경적은 자동 재시도 X → "다시 울리기" 버튼

## L6 — 관측
```
· 단계별 성공률 (스캔 → 연결 → 쓰기 → 응답) = 퍼널 ⭐ 어디서 새는지 즉시 보인다
· 단계별 소요시간 p50/p95 → 타임아웃 값의 근거
· 경로 분포 (BLE vs 서버) + 폴백 발생률
· 기기·OS 버전별 실패율 (BLE는 편차가 크다)
· 최종 실패(양 경로 모두) 발생률 = 유저가 차 앞에서 막힌 횟수 ⭐ 사고 지표
```

## 🔬 실무 대조 — 같은 코드베이스인데 품질이 갈린다 (⭐ 성장 서사 최고 재료)

```
   🔐 BLE 모듈                          🗺️ 지도 모듈
   ─────────────────────                ─────────────────
   builder / parser / manager /         Provider 한 파일에
   frame 타입 / 상수 / 유틸 분리          1,800줄 전부 + 3벌 복제
   콜백·에러 타입 단계별 분리             카메라·마커·폴리곤·애니메이션·판정 혼재
   = 잘 계층화됨 ✅                      = God object ❌
```

**왜 갈렸는가 (내 해석):**
```
BLE는 프로토콜이 강제한 경계가 있었다 (조립 / 전송 / 파싱은 섞을 수 없다)
지도는 SDK가 다 해주니 경계를 우리가 만들어야 했고, 안 만들었다
→ ⭐ 교훈: "외부가 경계를 강제하지 않는 영역일수록 의도적으로 경계를 그어야 한다"
```
> 🗝️ **면접 답변 (겸손하면서 판단력을 보여준다):** *"같은 앱 안에서도 품질이 갈렸습니다. BLE 모듈은 프로토콜이 조립·전송·파싱의 경계를 강제해서 자연스럽게 계층이 생겼습니다. 반면 지도는 SDK가 다 해주기 때문에 경계를 우리가 그어야 했고, 그걸 안 해서 한 파일이 1,800줄까지 갔습니다. 그래서 저는 **외부가 경계를 강제하지 않는 영역일수록 의도적으로 경계를 먼저 정해야 한다**고 배웠습니다."*

## ✅ 세션7 미확인 항목 해소
```
✅ 명령이 목표상태형인지 토글형인지  → 목표상태형 확인 (Lock/Unlock 별도)
✅ 단계별 에러 분리 여부            → 초기화/연결/쓰기 각각 별도 에러 타입
✅ ack 확인 경로                    → write 성공과 응답 수신이 별개 콜백
❓ 여전히 미확인: 서버↔BLE 자동 폴백 로직 · 명령 재시도 정책 · 탈옥 탐지 ·
                 BLE 성공의 서버 사후 보고 여부
```

## 💪 M4 압박 방어 4종

### ① "그냥 서버 API 한 방이면 되는데 BLE까지 왜?"
> *"실패 지점이 유저에게 가장 잔인한 곳에 있기 때문입니다. 차량은 대부분 지하주차장에 있고 거기엔 신호가 없습니다. 서버 경로만 있으면 유저는 차 앞에 서서 아무것도 못 합니다. 대가는 키 프로비저닝과 replay 방지 같은 보안 부담, BLE 상태머신 복잡도, 그리고 두 경로의 상태가 엇갈릴 수 있다는 점입니다. 그래서 BLE를 기본이 아니라 **폴백 사다리의 한 단**으로 두고, 평시엔 서버 경로로 감사 로그를 남깁니다."*

### ② "명령 재시도는 그냥 하면 되는 거 아닌가요?"
> *"명령마다 다릅니다. 잠금과 해제는 목표 상태를 지정하는 형태라 두 번 보내도 결과가 같아서 자동 재시도가 안전합니다. 반면 경적은 두 번 보내면 두 번 울리는 이벤트라 멱등하지 않습니다. 그래서 경적은 응답이 없어도 자동 재시도하지 않고 유저가 다시 누르게 합니다. **멱등성을 기능 전체가 아니라 명령 단위로 판단해야 합니다.**"*

### ③ "문이 열렸는지 어떻게 확신하죠?"
> *"BLE write가 성공했다는 콜백은 전송이 성공했다는 뜻이고 차량이 수행했다는 뜻이 아닙니다. 그래서 완료 판정은 차량이 보내오는 응답 메시지로 합니다. 실제로 write 성공 콜백과 응답 수신 콜백이 별개로 분리되어 있었습니다. 그리고 optimistic으로 먼저 '열렸습니다'를 표시하지 않습니다. 잘못 표시되면 유저가 차를 못 열고 서 있게 되기 때문입니다."*

### ④ "BLE 키가 탈취되면요?"
> *"피해 범위를 좁히는 방향으로 설계했습니다. 키가 사용자에게 발급되는 게 아니라 **예약 단위로 발급**돼서, 예약이 끝나면 별도 폐기 없이도 무효가 됩니다. 그리고 명령 패킷은 매번 다른 IV로 암호화해서 패킷을 녹음해 재전송하는 공격을 막습니다. 키는 Keychain에 저장하고 예약 종료 시 즉시 폐기합니다. 다만 탈옥 탐지 같은 기기 무결성 검증은 제가 확인한 범위가 아니라 추가 확인이 필요합니다."*

# 🔎 M6 — 검색 / 목록 (지도와의 정합)

## ⭐ 핵심: 같은 데이터를 두 뷰가 본다 → SSOT

```
   ┌── 지도 (마커) ──┐
   │                 ├── VehicleRepository = SSOT ── bbox·필터·정렬 상태 소유
   └── 리스트 (셀) ──┘

   ❌ 지도용 응답과 리스트용 응답을 따로 관리 → 개수 불일치·필터 미적용 버그
      (유저: "지도엔 5대인데 목록엔 3대예요")
   ✅ 하나의 Repository를 두 뷰가 관찰 → 정의상 불일치 불가
   ⭐ 필터 상태를 뷰가 각자 들고 있으면 반드시 갈라진다 → Repository가 소유
```

## typeahead 검색 4단 방어

```
① distinctUntilChanged   같은 문자열 재입력 시 요청 생략 (중복 제거)
② debounce 250~400ms     타이핑 중 매 글자 요청 방지 ⭐
③ 이전 요청 취소          flatMapLatest / Task 취소 — 오래된 응답이 최신을 덮지 않게
④ 최소 길이 게이트        1글자 검색은 결과가 무의미 + 서버 부하 (보통 2자 이상)
```
> ①과 ②는 **다른 일을 한다.** `distinctUntilChanged`는 *같은 값*을 막고, `debounce`는 *빈도*를 막는다. ①만 있으면 "ㄱ→가→강→강남" 처럼 매 글자가 다른 값이므로 요청이 전부 나간다.

## 🔬 실무 대조 — debounce 적용이 일관되지 않다

```
재확인:  git grep -nIE "debounce|distinctUntilChanged" -- '<검색 화면들>'
```
```
✅ distinctUntilChanged 는 여러 검색 화면에 있다
⚠️ debounce 는 검색 화면 중 한 곳에만 있다 (그것도 1초 — typeahead 로는 긴 편)
⚠️ 한 화면은 distinctUntilChanged 가 주석 처리되어 있다
→ 즉 화면마다 같은 문제를 다르게(또는 안) 처리하고 있다

⭐ 개선 방향: "검색 입력 → 쿼리" 변환을 공통 오퍼레이터/유틸로 추출
   (최소길이 + distinct + debounce + 취소를 한 곳에 묶어 재사용)
   → 화면이 늘어날 때마다 각자 구현해서 새는 구조를 구조적으로 차단
```
> 🗝️ **면접 답변:** *"검색 화면이 여러 개인데 디바운스가 한 곳에만 있었습니다. 이건 개별 실수라기보다 **공통 처리 지점이 없어서 생기는 구조 문제**라고 봅니다. 그래서 저는 '입력 문자열을 검색 쿼리로 바꾸는 변환'을 공통 유틸로 빼는 걸 제안합니다. 최소 길이, 중복 제거, 디바운스, 이전 요청 취소를 한 곳에 묶으면 새 검색 화면이 추가돼도 자동으로 적용됩니다."*
> ⚠️ 정직: 1초 디바운스가 실제 UX 문제였는지는 **미측정**. "길어 보인다"까지만 말한다.

## 정렬·필터의 소유권
```
정렬(거리순)  → 클라 (내 위치가 계속 변하므로 서버 정렬은 금방 낡는다)
필터(차종·요금) → 서버 쿼리 + 클라 즉시 재적용 (M1 클러스터링 하이브리드와 같은 논리)
필터 상태 소유  → ⭐ Repository (뷰가 각자 갖지 않는다)
지도 팬 시 리스트 갱신 → 자동 갱신은 스크롤 위치가 튄다
                        → "이 지역 재검색" 명시 버튼이 UX 안전 (실무 다수 선택)
```
