# L0 — 네트워크 계층의 책임 분해

```
   ┌─ Requestable (요청 정의)        endpoint · method · body · Output 타입
   ├─ RequestFactory (조립)          URL/헤더/인증 토큰 주입 · 환경(dev/stg/prod) 분기
   ├─ Infrastructure (실행) ⭐        전송 · 재시도 · 토큰 갱신 · 에러 매핑 · 로깅 · mock 분기
   ├─ BaseResponse (공통 래퍼)        서버 공통 봉투(code/message/data) 해체
   ├─ DTO (파싱)                     Decodable + CodingKeys
   └─ Repository (도메인 경계)        DTO → Entity 변환 · 여기서부터 도메인 언어
```

> 🗝️ **경계 원칙:** DTO는 **네트워크 계층에서 죽는다.** Repository 밖으로 DTO가 새면 서버 스키마 변경이 UI까지 전파된다. (`arch-a3`의 "경계에만 추상화"와 같은 논리)

**사실:** 인프라가 기능별 extension 으로 쪼개져 있다 — 토큰 갱신 · 로깅 · mock · Rx 브릿지 · 에러 타입 · 요청 팩토리 · 공통 응답 래퍼.

# L1 — ⭐ 토큰 갱신 (single-flight) — 실무 갭 발견

## 문제: 401이 동시에 5개 터진다

```
   화면 진입 → 병렬 요청 5개 발사 → 토큰 만료 → 401 × 5
                                        ↓
                        각각 "토큰 갱신하자" → refresh × 5  ⛔

   왜 위험한가:
   ① 서버가 refresh token rotation 을 쓰면 첫 갱신이 이전 토큰을 무효화
      → 나머지 4개가 무효 토큰으로 갱신 시도 → 실패 → ⛔ 강제 로그아웃 사고
   ② 불필요한 왕복 5배
   ③ 갱신 결과를 누가 먼저 쓰느냐에 따라 저장된 토큰이 오래된 값으로 덮일 수 있다
```

## 실무 코드에서 확인한 방어 — **1초 시간 게이트**

```
   현재 구조 (확인된 사실):
     · 갱신 가능 판정 = "마지막 갱신 시각으로부터 1초 초과했는가"
     · 담아둔 타입은 actor 가 아니라 class → 격리 없음
     · lock / semaphore / in-flight Task 공유 없음

   의도는 맞다 (thundering herd 완화). 하지만 구조적으로 mutual exclusion 이 아니다:
     T0.000  요청A: lastReloadDate 읽음 → nil → "가능" → 갱신 시작
     T0.001  요청B: lastReloadDate 읽음 → 아직 갱신 전이라 nil → "가능" → ⛔ 동시 갱신
   → 401 은 보통 "거의 동시에" 오기 때문에 이 창이 자주 열린다.
   ⚠️ 실제 발생률은 **미측정**. 면접에서 "사고가 났다"고 말하지 말고 "구조적으로 창이 있다"까지만.
```

## ✅ 정답 패턴 — single-flight (진행 중 갱신을 공유)

```swift
actor TokenRefresher {
    private var inFlight: Task<Void, Error>?

    func refreshIfNeeded() async throws {
        // 이미 갱신이 진행 중이면 새로 시작하지 않고 그 결과를 기다린다 ⭐
        if let existing = inFlight {
            return try await existing.value
        }
        let task = Task { try await performRefresh() }
        inFlight = task
        defer { inFlight = nil }
        return try await task.value
    }
}
```
```
얻는 것: 동시 401이 몇 개든 실제 갱신은 정확히 1회. rotation 사고 원천 차단.
대가:   actor 도입 → 호출부가 async 여야 함 (이미 async 라면 비용 0)
추가:   갱신 실패 시 대기 중인 요청들에 같은 에러를 전파하고, 재시도 상한 + 강제 로그아웃 경로
        → 무한 갱신 루프 방지 (401 → refresh → 또 401 → …)
```
> 🗝️ **면접 답변:** *"토큰 갱신은 시간 기반 스로틀이 아니라 **single-flight** 로 풀어야 합니다. 왜냐하면 시간 게이트는 상호배제가 아니라서 동시에 도착한 401 두 개가 모두 통과할 수 있기 때문입니다. 그리고 서버가 refresh token rotation 을 쓰면 두 번째 갱신이 무효 토큰으로 실패해서 유저가 강제 로그아웃됩니다. 그래서 actor 안에 진행 중 Task 를 보관하고, 갱신이 진행 중이면 새로 시작하지 않고 그 Task 의 결과를 기다리게 합니다."*

# L2 — SSL/TLS 핸드셰이크 (iOS 갭 ④)

## 핸드셰이크 흐름

```
   TLS 1.3 (1-RTT — 현재 표준)
   클라 ──ClientHello (지원 암호군 + 키 공유(key_share))──────────► 서버
        ◄─ServerHello (선택 암호군 + 키 공유) + 인증서 + Finished──┘
   ──Finished──► 이후 애플리케이션 데이터
        ⭐ 왕복 1회. 세션 재개(PSK)면 0-RTT 도 가능.

   TLS 1.2 (2-RTT — 레거시)
   ClientHello → ServerHello+인증서 → ClientKeyExchange
   → ChangeCipherSpec → Finished  (왕복 2회)

   핵심: 인증서로 "서버가 맞다"를 검증하고, 키 교환으로 세션 키를 만든다.
        인증서는 신원 증명용이고 암호화 키 자체가 아니다.
```

## 인증서 체인 검증

```
   서버 인증서(leaf) ──서명──► 중간 CA ──서명──► 루트 CA (OS 신뢰 저장소에 있음)
                                                     ▲ 신뢰 앵커(trust anchor)

   OS가 검증하는 것: 체인 유효 · 만료 여부 · 도메인 일치(SAN) · 폐기 여부(OCSP/CRL)
   → iOS 는 이걸 기본으로 해준다. 그래서 대부분의 앱은 추가 작업이 필요 없다.
```

## Certificate Pinning — 무엇을 왜, 그리고 왜 위험한가

```
   목적: 신뢰된 CA 가 발급한 "다른" 인증서로도 뚫리는 걸 막는다
        (사내 프록시 · 기기에 설치된 악성 루트 CA · CA 침해 → MITM)

   종류
   ┌ 인증서 핀닝(leaf 고정)      갱신할 때마다 앱 배포 필요 ⛔ 운영 지옥
   └ 공개키 핀닝(SPKI 해시) ⭐    인증서를 갱신해도 키를 유지하면 핀이 유효 → 실무 표준
```

## ⚠️ 핀닝의 진짜 리스크 — 앱 배포는 비가역이다

```
   핀이 틀리면 앱이 서버에 아예 접속 못 한다 = 전면 장애
   그런데 앱은 롤백이 안 된다 (심사 + 유저 업데이트 대기)

   그래서 필수 장치:
   ① 백업 핀 (다음 갱신용 키를 미리 포함) ⭐ 없으면 인증서 교체 시 앱 사망
   ② 만료 관리 (핀·인증서 만료일 캘린더 알림)
   ③ 원격 킬스위치 (서버 플래그로 핀닝 비활성 — 단 이 채널 자체가 핀닝 대상이면 순환)
   ④ 점진 배포 + 모니터링 (핸드셰이크 실패율 급증 감지)

   ⭐ iOS 14+ 는 Info.plist 의 NSPinnedDomains 로 선언적 핀닝을 지원한다
      → 커스텀 URLSessionDelegate 로 SecTrust 를 직접 다루는 코드보다 훨씬 안전
        (직접 구현하면 검증 로직을 잘못 짜서 오히려 검증을 무력화하는 사고가 흔하다)
```
> 🗝️ **면접 결정타:** *"핀닝은 도입 자체보다 **운영 리스크가 본질**입니다. 핀이 틀리면 앱이 서버에 접속을 못 하는데 앱 배포는 되돌릴 수 없습니다. 그래서 저는 도입한다면 공개키 핀닝으로 하고, 백업 핀과 만료 알림, 그리고 iOS 14 이상이면 코드 대신 `NSPinnedDomains` 선언 방식을 씁니다. 직접 `SecTrust` 를 다루면 검증을 무력화하는 실수가 나오기 쉽기 때문입니다."*

## 🔬 실무 대조 — 확인된 두 가지

```
① cert pinning 미구현 (앱 코드 기준)
   재확인:  git grep -lIiE "pinning|serverTrust|SecTrust|publicKeyHash" -- '*.swift'
   → 히트는 전부 SwiftUI `LazyVStack(pinnedViews:)` 오탐이었다 (다각도 검증)
   → 네트워크 계층에 SecTrust/serverTrust 처리 없음. URLAuthenticationChallenge 는
     WebView 컨트롤러에 1건뿐(WKWebView 인증 챌린지 처리, 핀닝 아님)
   ⚠️ 단, 서드파티 SDK 레벨 핀닝 가능성은 미확인 → "앱 코드에서는 확인되지 않았습니다"까지만

② ⚠️ ATS 가 전역 해제되어 있다
   Info.plist: NSAppTransportSecurity → NSAllowsArbitraryLoads = true
   → 평문 HTTP 연결이 앱 전역에서 허용된다

   ⭐ 이걸 "우리 앱은 취약하다"로 말하면 안 된다. 보통 이유가 있다:
      웹뷰가 임의 외부 리소스를 로드 / 레거시 서버 / 서드파티 SDK 요구
   ✅ 올바른 프레이밍: "왜 켰는지 확인하고, 범위를 좁힌다"
      NSExceptionDomains 로 필요한 도메인만 예외 처리 → 전역 해제를 제거
      (전역 해제는 앱 심사에서 정당화 요구를 받기도 한다)
```
> 🗝️ **면접에서 이걸 말하는 법:** *"제가 코드를 훑다가 ATS 가 전역으로 해제돼 있는 걸 발견했습니다. 다만 이건 대체로 웹뷰나 레거시 서버 때문에 켜두는 것이라 '취약점'이라고 단정하기 전에 왜 켰는지를 확인해야 합니다. 제 제안은 전역 해제를 없애고 `NSExceptionDomains` 로 필요한 도메인만 예외를 주는 방향입니다. 범위를 좁히는 게 켜고 끄는 것보다 현실적입니다."*
> → **발견 + 신중한 해석 + 실행 가능한 제안**. "취약점 찾았습니다"보다 훨씬 시니어로 읽힌다.

# L3 — Codable 실전 (iOS 갭 ⑤) + silent-nil

## ⭐ 실측: DTO 188개 중 CodingKeys 보유 68개 → **120개(64%)가 미보유**

```
재확인:  git grep -lI "struct.*Decodable\|struct.*Codable" -- '<DTO 경로>' | wc -l   → 188
        git grep -lI "CodingKeys"                          -- '<DTO 경로>' | wc -l   → 68
```

## 왜 CodingKeys 없는 게 위험한가 — silent-nil

```
   서버가 필드명을 바꿨다:  "userName" → "user_name"

   ❌ CodingKeys 없음 + 옵셔널 프로퍼티
      let userName: String?
      → 디코딩 성공 ✅  userName = nil  ⛔
      → 에러 0건 · 로그 0건 · 크래시 0건 · UI 만 빈칸
      → QA 가 못 잡고 CS 로 들어온다 (그때 원인 추적 지옥)

   ✅ CodingKeys 명시
      enum CodingKeys: String, CodingKey { case userName = "user_name" }
      → 매핑이 코드에 문서화됨. 서버 변경 시 여기만 보면 됨.

   ✅ 더 강하게: 필수 필드는 non-optional
      → 없으면 디코딩이 throw 한다 = 실패가 **시끄럽게** 드러난다 ⭐
      "옵셔널은 진짜 없어도 되는 필드에만" 이 원칙
```
> 🗝️ **핵심 통찰:** 이건 `sd-b4`의 CRDT silent-nil, `sd-m1`의 GeoJSON 좌표 뒤집힘과 **같은 계열의 사고**다. 공통점은 **"에러가 나지 않고 기능만 조용히 죽는다"**. 그래서 방어도 같다 — **실패를 시끄럽게 만들기**.

## Codable 실전 함정 5개

```
① snake_case ↔ camelCase
   .convertFromSnakeCase 전략은 편하지만 예외 필드가 하나 생기면 전체가 흔들린다
   → 대규모에서는 CodingKeys 명시가 더 안전 (명시적 > 마법)

② 날짜
   서버 포맷이 ISO8601 인지 epoch 인지 밀리초인지 타임존 포함인지 확인
   → JSONDecoder.dateDecodingStrategy 를 한 곳에서 통일. DTO마다 다르면 반드시 사고
   ⚠️ 타임존 없는 문자열은 기기 로컬로 해석되어 하루가 밀린다

③ 숫자 타입 흔들림
   서버가 "123" (문자열) 또는 123 (숫자) 를 섞어 보내면 디코딩 실패
   → 관용 디코딩이 필요하면 커스텀 init(from:) 으로 명시적 처리
   ⭐ 금액은 Double 금지 (Decimal / 최소단위 정수)

④ 빈 값 표현
   null · "" · 누락(키 자체 없음) 이 서로 다르다
   → decodeIfPresent 와 옵셔널의 의미를 구분해서 쓴다

⑤ 배열 안의 일부 실패
   1000개 중 1개가 깨지면 전체 디코딩이 throw 되어 화면이 빈다
   → 실패 허용이 필요하면 요소별 lossy 디코딩(실패 요소만 버리고 카운트 로깅)
```

## 검증 장치 — 계약을 테스트로 고정

```
✅ decode 라운드트립 테스트: 실제 서버 응답 샘플(fixture) → decode → 필드 단정
   ⭐ "파싱되나"가 아니라 "값이 들어왔나"를 단정해야 silent-nil 이 잡힌다
      XCTAssertNotNil(dto) 만 하면 nil 필드를 통과시킨다 ← 흔한 무의미 테스트
✅ 3-오라클 대조: 서버 스펙(swagger) + 다른 플랫폼 구현 + 실제 응답
   → 세 개가 어긋나는 필드가 사고 후보
✅ CI 게이트: 새 DTO 에 CodingKeys 없으면 경고 (점진 도입 — 기존 120개를 한 번에는 못 고친다)
```

# L4 — 재시도 · 서킷브레이커 · 에러 계약

```
재시도 (M2 에서 이미 정립한 원칙 재사용)
  retryable(타임아웃·5xx) → 지수백오프 + jitter
  terminal(4xx 대부분)     → 재시도 X, 즉시 표면화
  ambiguous(응답 유실)     → ⭐ 재시도 X, 조회 O (비멱등 요청은 특히)
  ⛔ GET 만 안전하다고 가정하지 말 것 — 서버 구현에 따라 부작용 있는 GET 도 있다

서킷브레이커
  연속 실패 N회 → 회로 open (일정 시간 요청 자체를 안 보냄) → half-open 탐색 → close
  왜: 서버가 죽었을 때 클라가 재시도로 서버를 더 때리는 걸 막는다(retry storm)
  모바일 특이점: 유저가 화면을 계속 당겨 새로고침하면 클라가 곧 DDoS가 된다
  ⚠️ open 상태를 UX로 정직하게 표현해야 한다 ("일시적 오류" + 재시도 가능 시각)

에러 계약 (⭐ 앱 배포는 비가역)
  ❌ 에러 메시지 문자열로 분기 (문구 바뀌면 앱이 깨진다)
  ✅ { code, retryable, userMessage, supportCode } 를 서버가 내려준다
     → 새 실패 유형이 생겨도 앱 배포 없이 대응
     → userMessage 를 서버가 주면 문구 수정도 서버 배포로
```

# L5 — mock 분기 (프로덕션 유출 리스크)

**사실:** 인프라에 mock 설정과 mock 분기가 실제로 있다.

```
   장점: QA·개발이 서버 없이 화면을 검증할 수 있다 (풀사이클 진입 unblock)
   ⛔ 리스크: mock 분기가 프로덕션 빌드에 살아있으면 실데이터 대신 mock 이 노출된다
             (이건 실제로 발생하는 사고 클래스다 — 배포 전 게이트로 막아야 한다)

   방어 3층
   ① 컴파일 타임 배제      #if DEBUG 로 mock 코드 자체가 릴리스에 안 들어가게
   ② 런타임 이중 가드      릴리스 + mock 활성 조합이면 즉시 실패(fatalError 또는 강제 off)
   ③ 배포 전 스캔          release 빌드 설정에서 mock 플래그 검사 = CI 게이트
   → "설정으로 껐다"만 믿지 않는다. 설정은 사람이 되돌린다.
```

# 💪 압박 방어 5종

### ① "왜 핀닝을 안 하셨어요?"
> *"현재 앱 코드에는 없습니다. 다만 저는 핀닝을 '해야 하는데 안 한 것'으로만 보지 않습니다. 핀이 틀리면 앱이 서버에 접속을 못 하는데 앱 배포는 되돌릴 수 없어서, 백업 핀과 만료 관리 없이 도입하면 오히려 전면 장애 위험을 만듭니다. 그래서 도입한다면 공개키 핀닝 + 백업 핀 + iOS 14 이상은 `NSPinnedDomains` 선언 방식으로 갑니다. 그리고 **우선순위상 먼저 고칠 건 ATS 전역 해제**라고 봅니다. 핀닝 이전에 평문 HTTP 가 전역 허용되어 있는 게 더 넓은 노출이기 때문입니다."*
> 🗝️ "안 했습니다" 대신 **위험 순서를 매겨서** 답한다 = 판단력 신호.

### ② "DTO에 CodingKeys가 없는 게 왜 문제죠? 이름이 같으면 되잖아요."
> *"이름이 같은 동안은 문제가 없습니다. 문제는 서버가 필드명을 바꿨을 때입니다. 옵셔널 프로퍼티면 디코딩이 성공하고 값만 nil 이 됩니다. 에러도 로그도 크래시도 없고 화면만 빈칸이 됩니다. 저는 이걸 silent-nil 이라고 부르는데, QA 가 못 잡고 CS 로 들어옵니다. 그래서 매핑을 코드에 명시하고, 더 중요하게는 **필수 필드를 옵셔널로 두지 않습니다.** 없으면 디코딩이 실패해서 시끄럽게 드러나야 합니다."*

### ③ "토큰 갱신은 어떻게 처리하셨어요?"
> *"현재는 마지막 갱신 시각 기준 시간 게이트로 중복 갱신을 완화하고 있습니다. 의도는 맞지만 상호배제가 아니라서 동시에 도착한 401 이 둘 다 통과할 수 있는 창이 있습니다. 서버가 refresh token rotation 을 쓰면 두 번째 갱신이 무효 토큰으로 실패해서 강제 로그아웃까지 갈 수 있습니다. 그래서 제가 고친다면 actor 안에 진행 중 Task 를 보관하는 **single-flight** 로 바꿉니다. 갱신이 진행 중이면 새로 시작하지 않고 그 결과를 기다리게 하는 방식입니다. 실제 발생률은 제가 아직 측정하지 않았습니다."*
> 🗝️ 마지막 문장이 신뢰를 만든다. 사고가 났다고 과장하지 않는다.

### ④ "재시도만 잘 하면 네트워크 안정성은 해결되는 거 아닌가요?"
> *"재시도는 절반입니다. 나머지 절반은 **언제 재시도하지 않을지**입니다. 응답을 못 받은 모호한 상태에서 비멱등 요청을 재시도하면 중복 처리가 됩니다. 그리고 서버가 죽었을 때 모든 클라가 재시도하면 서버를 더 때립니다. 그래서 실패를 재시도 가능·불가·모호로 분류하고, 연속 실패에는 서킷브레이커로 요청 자체를 잠시 멈춥니다. 모바일에서는 유저가 당겨 새로고침을 반복하는 것만으로 클라가 트래픽 소스가 되기 때문에 더 중요합니다."*

### ⑤ "네트워크 계층을 다시 설계하면 뭘 바꾸시겠어요?"
> *"세 가지입니다. 첫째, 토큰 갱신을 single-flight 로 바꿉니다 — 지금 구조에 상호배제가 없습니다. 둘째, 에러 계약을 서버와 합의해서 코드와 retryable 플래그를 받습니다. 지금은 새 실패 유형이 생기면 앱 배포가 필요한데 앱 배포는 되돌릴 수 없습니다. 셋째, 신규 DTO 에 CodingKeys 를 강제하는 CI 경고를 넣습니다. 기존 120개를 한 번에 고치는 건 비현실적이라 새로 들어오는 것부터 막는 게 현실적인 순서라고 봅니다."*
> 🗝️ **"기존은 못 고친다, 신규부터 막는다"** 는 현실감이 시니어 신호. 전면 리팩터링을 말하면 오히려 감점.

## 📌 확정 / 미확인

```
✅ 확정: 인프라가 관심사별 extension 분리 · 토큰 갱신 = 1초 시간 게이트 + class(비격리) ·
        cert pinning 앱 코드에 없음(다각도 검증, LazyVStack 오탐 배제) ·
        ATS NSAllowsArbitraryLoads = true · DTO 188개 중 CodingKeys 68개(64% 미보유) ·
        mock 설정·분기 존재
❓ 미확인: 서드파티 SDK 레벨 핀닝 유무 · 서킷브레이커 구현 유무 · 재시도 정책의 실제 분류 ·
          ATS 전역 해제의 이유(웹뷰? 레거시 서버?) ⭐ 물어봐야 함 ·
          동시 401 실제 발생률(미측정) · mock 의 릴리스 배제 방식
```

**박제 한 줄:** *네트워크 계층 = **토큰 갱신은 시간 게이트가 아니라 single-flight** · **핀닝은 도입보다 운영 리스크**(백업 핀 없으면 앱 사망, 앱 배포는 비가역) · **CodingKeys 누락 = silent-nil**(에러 0건으로 기능만 죽는 계열) · **에러 계약을 서버가 코드로** 내려야 앱 배포에 묶이지 않는다. 그리고 **기존 120개를 다 고치는 대신 신규부터 막는다.***
