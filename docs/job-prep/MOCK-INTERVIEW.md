# 🎤 면접관 모드 — 저마찰 능동 인출 프로토콜

> **왜 만들었나:** 세션 6~8에서 문서는 17개까지 쌓였는데 **유저 능동 인출은 3회 연속 0회**였다.
> 원인은 의지가 아니라 **타이핑 마찰**이다 (유저: *"다 아는 건데 타이핑하기 귀찮아"*).
> → 그래서 **타이핑을 0~5자로 줄이면서 인출은 유지하는** 3티어 포맷을 만든다.
>
> **핵심 통찰:** 능동 인출에 타이핑이 반드시 필요한 게 아니다. **소리내어 말하고 "ㅇㅋ"만 치면 된다.**
> 그리고 면접은 애초에 *말하는* 시험이다. 타이핑 연습은 면접력과 상관이 없다.

---

## 🎚️ 3티어 (마찰 순)

```
T3 🎤 음성 완주      타이핑 0자    소리내어 말한 뒤 "ㅇㅋ" → 모범답안 펼침 → 자기 대조
                                  ⭐ 면접에 가장 가깝다. 기본값으로 권장.
T1 🎯 선택형         타이핑 1자    4택 함정 문제. 오답 선택지 = 실무에서 흔한 오해
                                  → 판별력 측정. 빠르고 진단용으로 좋다.
T2 🔑 키워드형       타이핑 3~5어  "답의 뼈대 키워드 3개만" → 내가 문장으로 확장
                                  → 생산(production)이 살아있는 최소 형태
```

**선택 기준**
```
컨디션 좋고 집중됨    → T3 (말로 완주)
피곤하거나 이동 중    → T1 (숫자만)
어중간              → T2 (키워드)
막힌 주제 발견 시     → 그 주제만 T3로 심화
```

## 🤖 Claude 운영 규약

```
1. 세션 시작 워밍업은 이 파일의 문제 은행에서 3~5개.
   ⭐ 유저가 "다 안다"고 하면 → 정답을 바로 주지 말고 T1(숫자 1자)로 강등해서 확인한다.
      (세션7에서 자평만 믿고 정답을 펼친 게 실패 사례. 자평 ≠ 인출)
2. 오답이면 그 카드는 REVIEW.md 박스 1로 리셋 + 해당 lessons 링크 제시.
3. 정답이면 박스 +1. 단 T1 정답은 T3 정답보다 약하게 취급 (recognition < production).
4. T3에서는 모범답안을 펼친 뒤 반드시 자기채점 루브릭을 함께 보여준다.
5. 한 번에 5문제 이하. 유저 피드백 "한 번에 하나씩" 존중.
6. 채점은 후하게, 기록은 정직하게. 안 한 건 안 했다고 쓴다.
```

## 📏 T3 자기채점 루브릭 (말한 뒤 스스로 체크)

```
□ 결론을 먼저 말했나           (서론부터 깔지 않았나)
□ "왜냐하면"으로 근거를 붙였나   (단정만 하고 끝나지 않았나)
□ 트레이드오프를 소리냈나        (대가 없이 장점만 말하지 않았나)
□ mitigation 까지 갔나         ("그 비용을 이렇게 줄인다"까지)
□ "언제는 반대 선택인지" 말했나  (패턴을 종교처럼 옹호하지 않았나)
□ 어미를 끊었나                ("~해서?" 아니라 "~합니다.")
□ 모르는 건 모른다고 했나        ("확인이 필요합니다")

6~7개 = 실전 통과 · 4~5개 = 보완 · 3개 이하 = 그 카드 재학습
```

# 🎯 T1 문제 은행 — 4택 함정 (숫자 1자 답변)

> **설계 원칙:** 오답 선택지는 **실무에서 실제로 흔한 오해**로 구성한다. 아무나 걸러지는 문제는 진단 가치가 없다.
> ⭐ 표시는 내가(또는 우리 코드가) 실제로 틀렸던 것.

## R1 — 모빌리티 기본 (세션 7~8)

```
Q1. 오프라인 편집 앱에서 "충돌"이 발생하는 조건은?
  ① 두 명 이상이 동시에 같은 문서를 편집할 때
  ② 오프라인 상태에서 replica 가 2개 이상일 때
  ③ 서버 시계와 기기 시계가 어긋날 때
  ④ 편집 단위가 문자 단위일 때
                                                            정답 ②  ⭐(유저 오답 이력)

Q2. 결제 요청을 보냈는데 응답이 오지 않았다. 가장 먼저 할 일은?
  ① 같은 멱등키로 즉시 재시도
  ② 서버에 결제 상태를 조회
  ③ 새 멱등키로 재시도
  ④ 유저에게 실패를 알리고 재결제 유도
                                                            정답 ②

Q3. 카셰어링에서 "실제 주행거리"는 누가 측정하나?
  ① 앱이 백그라운드 GPS 로 기록해 배치 업로드
  ② 차량 텔레매틱스가 측정하고 서버가 계산
  ③ 대여 위치와 반납 위치의 직선거리
  ④ 앱과 차량이 각각 측정해 큰 값을 채택
                                                            정답 ②  ⭐(내 오답 이력)

Q4. 차량 "경적 울리기" 명령의 응답이 오지 않았다. 올바른 처리는?
  ① 지수 백오프로 자동 재시도
  ② 자동 재시도하지 않고 유저가 다시 누르게 한다
  ③ 서버 경로로 폴백해서 자동 재시도
  ④ 멱등키를 붙여서 자동 재시도
                                                            정답 ②  ⭐(멱등성은 명령 단위)

Q5. GeoJSON 폴리곤의 좌표 순서는?
  ① [위도, 경도]
  ② [경도, 위도]
  ③ 라이브러리마다 다르다
  ④ 투영된 [x, y]
                                                            정답 ②  ⭐(우리 코드 함정)

Q6. BLE write 성공 콜백을 받았다. "문이 열렸습니다"를 표시해도 되나?
  ① 된다. write 성공 = 차량이 수행 완료
  ② 안 된다. 차량 응답 메시지를 확인해야 한다
  ③ 된다. 단 3초 뒤 상태를 재확인한다
  ④ 안 된다. 서버에 조회해서 확인해야 한다
                                                            정답 ②  ⭐(전송 ≠ 수행)
```

## R2 — 지도 심층

```
Q7. 지도 클러스터의 숫자가 계속 깜빡인다(12→11→12). 가장 먼저 볼 곳은?
  ① 클러스터 중심을 차량 평균 위치로 계산하는지
  ② 지도 SDK 버전 호환성
  ③ 마커 재사용 풀 크기
  ④ 서버 집계 캐시 TTL
                                                            정답 ①

Q8. 같은 zoom 레벨인데 m/px 가 지역마다 다른 이유는?
  ① 지도 타일 해상도가 지역마다 달라서
  ② Web Mercator 왜곡 — 위도에 따라 1/cos(φ) 배
  ③ 기기 화면 배율(@2x/@3x) 차이
  ④ 서버가 지역별로 다른 타일셋을 준다
                                                            정답 ②

Q9. 팬할 때마다 요청이 폭발한다. 가장 효과 큰 대응 하나는?
  ① 요청 타임아웃을 늘린다
  ② debounce + bbox 격자 스냅
  ③ 응답 페이로드를 압축한다
  ④ 마커 아이콘을 캐시한다
                                                            정답 ②

Q10. 전국 차량 5만 대를 지도에 보여달라는 요구가 왔다.
  ① 전부 받아서 클라에서 클러스터링
  ② 개별 마커로 그리되 화면 밖은 제거
  ③ 표현을 바꾼다 — 서버 집계 클러스터/히트맵 타일
  ④ zoom 을 강제로 낮춘다
                                                            정답 ③
```

## R3 — 결제·요금 심층

```
Q11. exactly-once 전달이 불가능한 이유는?
  ① 네트워크가 느려서
  ② "도착했는데 응답 유실"과 "도착 자체 실패"를 구별할 수 없어서
  ③ 서버가 상태를 저장하지 않아서
  ④ 클라 시계를 믿을 수 없어서

Q12. 멱등키를 재시도할 때 어떻게 해야 하나?
  ① 재시도마다 새 UUID 발급
  ② 저장해둔 같은 키를 재사용
  ③ 타임스탬프를 붙여 변형
  ④ 서버가 발급해준 키를 사용
                                                            정답 ②  (①이 실무 최다 버그)

Q13. 서버 멱등성의 "최종 방어선"은?
  ① 애플리케이션 레벨 중복 체크
  ② 멱등키 컬럼의 DB UNIQUE 제약
  ③ 요청 rate limit
  ④ 클라 UI 버튼 잠금
                                                            정답 ②  (①만으론 경합에서 뚫림)

Q14. 카셰어링 요금이 "총 주행거리 × 단가"로 계산되지 않는 이유는?

  ② 구간별로 단가가 달라서 (예상 경로 vs 구간 외)
  ③ 부가세 때문에
  ④ 쿠폰이 적용되어서
                                                            정답 ②

Q15. 반납 처리는 어느 등급으로 다뤄야 하나?
  ① 일반 조회와 같다 (읽기 위주)
  ② optimistic 으로 즉시 반영해도 된다
  ③ 결제와 같은 등급 — 되돌릴 수 없다
  ④ 실패해도 재시도하면 되니 가볍다
                                                            정답 ③
```

# 🎤 T3 음성 완주 시나리오 (타이핑 0자)

> **진행:** 시나리오를 보고 **소리내어 3~5분 답한다** → `"ㅇㅋ"` 입력 → 모범답안 + 루브릭 펼침 → 자기 대조

```
S1. "지도에 주변 차량을 실시간으로 표시하는 기능을 설계해보세요."
    → 3층 프레임으로 시작 · 스코핑 질문 먼저 · 클러스터링 하이브리드 · 배터리
    → ⭐ 오프닝을 "제가 다룬 건 클러스터링이 아니라 구역 판정이었다"로 갈 수 있으면 만점

S2. "차량 예약과 결제 플로우를 설계해보세요."
    → 상태머신 그리기 · held+TTL · 4중 방어 · reconcile · optimistic 금지

S3. "네트워크가 끊긴 상태에서 결제 버튼을 눌렀습니다. 어떻게 되나요?"
    → 모호 상태 · 멱등키 · reconcile · 절대 임의 재결제 금지

S4. "지하주차장에서 차 문이 안 열립니다. 어떻게 설계했나요?"
    → 이중 경로 · 폴백 사다리 4단 · 단계별 안내 · 전송≠수행 · 조용한 실패 금지

S5. "요금이 앱에 보인 것과 청구가 다르면요?"
    → 서버 단일 계산 · breakdown · policyVersion · 임시/최종 3단 상태

S6. (Reverse SD) "본인이 만든 시스템 중 가장 어려웠던 걸 설명해보세요."
    → 아키텍처 4틀 + mitigation + ⭐ God object 성장 서사 + "지금이라면"
```
